Fix CXL guard: use NV_CXL_INIT_SUPPORTED instead of header presence PR CXL

PR #1438 2026-10-12 | Closed (已合并至 620.xx)
修复内容: 修复 CXL 结构体编译守卫逻辑。原守卫仅检查头文件是否存在，导致在使用 stub 头文件的内核上编译失败。修改为使用 NV_CXL_INIT_SUPPORTED 能力探测，与 nv-pci.c 中的守卫逻辑保持一致。

关键修改: nv-linux.h 中的守卫条件

状态: NVIDIA 协作者 aritger 确认已有等效修复在内部树中，将在 620.xx 版本中发布。PR 已关闭。

来源: GitHub PR #1438

Fix: fix nv_cxl struct fields generation PR CXL

PR #1435 2026-10-12 | Closed (与 #1438 重复)
修复内容: 修复 nv_cxl 结构体字段生成问题。通过增加条件编译变量，使用 conftest 脚本进行配置检测，解决 Proxmox 内核上的编译失败。

状态: NVIDIA 协作者指出与 #1438 几乎相同，等效修复将在后续驱动版本中发布。

来源: GitHub PR #1435

kernel-open: allow overriding MLNX_OFED_KERNEL_DIR and KBUILD_EXTRA_SYMBOLS PR

PR #1441 2026-10-12 | Open
修复内容: 允许通过环境变量覆盖 MLNX_OFED_KERNEL_DIR 和 KBUILD_EXTRA_SYMBOLS。peer-memory 模块需要特定符号文件，当发行版在共享根目录编译模块时，配置脚本无法找到必要文件。修改涉及 kernel-open/conftest.sh 和 kernel-open/Makefile。

NVLink 相关性: Mellanox OFED 是 NVLink/InfiniBand 互联的关键依赖。此修复改善了使用自定义 OFED 路径的构建灵活性。

来源: GitHub PR #1441

本周 CXL 相关 PR 活跃度高。3 个 PR 中有 2 个已被 NVIDIA 确认将在 620.xx 版本中合并。CXL (Compute Express Link) 与 NVLink-C2C 技术路线互补，未来 Grace-Blackwell/Vera-Rubin 平台将同时受益于两种互联技术。

MMU/UVM 模块更新

本周 5 个 Issues + 6 个 PRs

RTX 5080: GPU memory pool exhaustion (NV_ERR_NO_MEMORY) BUG NEW

Issue #1437 2026-10-10 | Open
问题描述: RTX 5080 (Blackwell GB203) 在长时间使用后出现 GPU 内存池渐进式耗尽。非单次峰值导致，而是"available GPU memory appears to erode over a long session"。最终触发 NV_ERR_NO_MEMORY 和 ctxBufPoolReserve 失败。

影响版本: 615.71.09 (RPM Fusion build)

环境: Fedora Linux 44, Kernel 7.2.9

触发路径:

  • Path A (快速触发): 打开大型应用并触发突发 GPU 分配 → VA 空间损坏
  • Path B (慢速泄漏): 普通桌面/游戏/编辑器工作 24-27 小时后内存池耗尽

错误信息: Out of memory [NV_ERR_NO_MEMORY] (0x00000051) returned from ctxBufPoolReserve

关键代码路径: gpu_vaspace.c:4502 — pMapNode->gpuMask 断言失败

来源: GitHub Issue #1437

CUDA context init OOM: sysmem mmap rejection at vm_insert_page BUG NEW

Issue #1431 2026-10-08 | Open
问题描述: 在未加载模型的情况下启动 CUDA context 即触发 OOM。内核守卫阻止了零引用计数页面的插入，导致内存映射失败。

影响版本: 610.57.04

环境: Ubuntu 24.04, Kernel 6.8.0-142-generic, PyTorch 2.11.0+cu130

GPU: GeForce RTX 5060 Ti 16GB

错误信息: NVRM: Userspace mapping creation failed [-22]! → torch.AcceleratorError: CUDA error: out of memory

来源: GitHub Issue #1431

RTX 3050: VA space exhaustion → GPU lockup (Wayland) BUG

Issue #1411 2026-10-01 | Open | 多人确认
问题描述: RTX 3050 (GA106) 在 Hyprland/Wayland 下出现 dmaAllocMapping_GM107 VA 空间耗尽，导致 GPU 完全锁死。本周新增 2 名用户确认受影响 (RTX 3070 / RTX 3070 Ti)。

影响版本: 610.57.04

关键代码路径: dmaAllocMapping_GM107

社区反馈:

  • 用户 B 确认 RTX 3070 + 相同软件配置下崩溃
  • 用户 C 报告 RTX 3070 Ti 在 3.5 天后出现相同故障，含浏览器媒体线程崩溃
来源: GitHub Issue #1411

GB202: stale WPR2 after abnormal GSP shutdown blocks init BUG NEW

Issue #1442 2026-10-12 | Open
问题描述: RTX 5090 (GB202 A1) 在异常 GSP-RM 终止或固件启动失败后，残留的 WPR2 安全状态阻止后续标准驱动加载。内核模块重载和硬件重置均无法修复。

影响版本: 610.57.04 和 615.71.09

错误信息: unexpected WPR2 already up, cannot proceed with booting GSP

关键发现: 物理设备在错误状态下仍可用于标准计算任务，但固件启动路径被阻塞

来源: GitHub Issue #1442

nvidia-uvm: propagate EGM DMA mapping failures PR

PR #1423 2026-10-06 | Open
修复内容: UVM 模块中 EGM DMA 映射例程此前无论实际结果如何均返回成功码。这导致调用函数错误地记录已完成的映射，并在 API 缺失时无法触发备用路径。补丁确保返回实际记录的状态，恢复调用者的 NV_ERR_NOT_SUPPORTED 回退逻辑。

关键修改: 传播 DMA link 和 sync 失败状态

测试: 作者引入回归测试 (test_uvm_egm_dma_mapping.py)，全部 10 个测试通过。原始代码在 7 个错误路径断言中失败。

来源: GitHub PR #1423

mem_mgr: Guard PMA region walk behind INFO logging PR

PR #1428 2026-10-07 | Open
修复内容: pmaRegionPrint() 在发送 LEVEL_INFO 消息前会遍历 PMA 区域的每一帧。当分配路径调用者持有 PMA 自旋锁且中断禁用时，即使消息会被过滤，完整遍历仍会执行，导致性能损失。

关键修改: 在 helper 函数起始处添加 DBG_RMMSG_CHECK(LEVEL_INFO) 守卫检查，在第一次区域映射读取前即拦截，避免昂贵的诊断遍历。

影响: 分配和驱逐状态不变，仅优化日志路径性能。

来源: GitHub PR #1428

uvm: Guard bottom-half queue flush on suspend PR

PR #1340 Updated 2026-10-12 | Open
修复内容: 在具有活跃 UVM 设备的旧 GPU (缺乏 replayable-fault 能力) 上挂起系统时触发内核 panic。内核尝试刷新未初始化的队列，导致空指针解引用。补丁添加条件检查，仅在 replayable fault 处理活跃启用时才刷新 bottom-half 队列。

关键文件: uvm_maxwell.c 及核心 UVM 初始化/挂起例程

社区验证:

  • MathyV: 确认补丁在 GTX 980 上成功解决崩溃
  • devAgant: 提供 GTX 950 崩溃日志以验证根因
  • mysterion-rises: 报告 GTX 980 上相同故障，目前使用模块黑名单临时规避
来源: GitHub PR #1340

Add compatibility with linux-next dmem, HMM and DRM APIs PR

PR #1414 2026-10-02 | Open
修复内容: 使 NVIDIA 615.71.09 能在 linux-next (next-20261001) 上编译。添加 conftest 检测以适配 dmem_cgroup_register_region() 参数变化、VM_SPECIAL mask 移除、vma_is_hugetlb() 重命名、DRM atomic state API 变更等。

涉及模块: nvidia, nvidia-uvm, nvidia-drm

关键适配:

  • dmem_cgroup_register_region() 初始化参数从 size_t 改为 struct pointer
  • VM_SPECIAL mask 替换为组成标志位
  • vma_is_hugetlb() helper 重命名检测
  • DRM plane/CRTC atomic_create_state 独立检测
  • drm/clients/drm_fbdev_helper.h 头文件重定位检测
来源: GitHub PR #1414

本周 MMU/UVM 关键趋势: VA 空间耗尽问题持续发酵 (Issue #1411, #1437, #1396)，影响从 Ampere 到 Blackwell 多代架构。内存泄漏和引用计数问题 (#1431) 表明 UVM 内存管理路径仍有稳定性隐患。PR #1423 的 EGM DMA 映射修复和 #1428 的 PMA 性能优化是积极的社区贡献。

VA 空间耗尽问题模式分析 高频问题

GitHub Issues | 多用户确认
模式识别: 本周多个 Issue (#1437, #1431, #1411) 呈现共同的 VA 空间耗尽特征。从 RTX 3050 (Ampere) 到 RTX 5080 (Blackwell) 均受影响，表明这是 UVM 内存管理子系统的系统性问题。

共同特征:

  • 渐进式内存侵蚀而非单次峰值
  • 长时间使用后触发 (24h+)
  • Wayland 环境下尤为突出
  • 需要重启或模块重载才能恢复

趋势展望

短期 / 中期趋势 & 核心洞察

短期趋势 (1-4 周)

620.xx 驱动分支即将到来

NVIDIA 协作者确认 CXL 修复 (#1438) 将在 620.xx 中发布。预计该分支将包含 CXL 支持改进和 Linux 7.3 内核兼容性。

VA 空间耗尽问题将持续受到关注

Issue #1411, #1437, #1396 形成明显的问题集群。随着 Arch Linux 等发行版默认使用开源驱动，更多用户可能遇到此类问题，推动 NVIDIA 优先修复。

社区 PR 质量提升

PR #1423 (UVM EGM DMA) 和 #1428 (PMA region walk) 展示了高质量的代码级修复，包含完整的测试用例。这表明开源社区对 NVIDIA 内核的理解在深化。

中期趋势 (1-3 月)

Nova (Rust) 驱动将加速推进

LPC 2026 展示 Nova 驱动在 Linux 7.3 上的进展。Nova-Core + Nova-DRM 架构和虚拟化支持表明 NVIDIA 正为长期替代方案投入资源。但短期内不会影响 open-gpu-kernel-modules 的日常维护。

完全开源转型的生态效应

NVIDIA 确认不再提供专有版本发行版。这意味着 open-gpu-kernel-modules 将成为唯一选择，所有 GPU 用户（从游戏到数据中心）都将依赖开源驱动。这将加速 bug 发现和修复周期。

CXL 与 NVLink-C2C 融合趋势

本周 3 个 CXL PR 表明 CXL 支持正在快速成熟。在 Grace-Blackwell 和 Vera-Rubin 平台上，CXL 将与 NVLink-C2C 协同工作，提供 CPU-GPU-内存的统一互联。开源驱动需要同时支持两种技术。

核心洞察

1. 内存管理成为开源驱动最大稳定性挑战

本周 5 个 MMU/UVM Issue 涵盖 VA 空间耗尽、DMA 映射失败、引用计数错误和 PMA 性能问题。这些问题跨越 Ampere 到 Blackwell 多代架构，表明需要系统性的内存管理子系统审查。

2. NVIDIA 与社区的协作模式正在成熟

PR #1438 的响应时间 (2 天内确认并关闭) 和 PR #1423 的详细测试用例展示了健康的协作模式。NVIDIA 协作者 aritger 的及时反馈有助于减少社区贡献者的挫败感。

3. Blackwell 架构的开源驱动成熟度仍需提升

Issue #1437 (RTX 5080 内存泄漏) 和 #1442 (RTX 5090 GSP 恢复) 表明 Blackwell 架构在开源驱动下仍有显著的稳定性问题。这些问题在专有驱动下可能不存在或已修复，凸显开源驱动追赶的紧迫性。

4. 615.78.08 的功能分支策略值得关注

新特性 (VK_NV_low_latency2) 通过功能分支而非生产分支发布，这是 NVIDIA 驱动发布策略的转变。数据中心用户应继续依赖 610.xx/595.xx 生产分支，而桌面/游戏用户可从功能分支获益。
