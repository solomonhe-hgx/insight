NVLink 模块动态

NVIDIA 官方 2026-09-15

NVLink 6 多层弹性架构: Vera Rubin NVL72 的基础互联NEW

核心要点: NVIDIA 发布 NVLink 6 技术深度解析, 阐述如何为 AI 工厂构建 "原生无损网络"。采用轻量级前向纠错 (FEC) + 物理层重试机制, 基于信用的流量控制防止丢包。引入 "Shadow Engine Recovery" 实现推理工作负载快速恢复, 无需冷重启。该架构是 Vera Rubin NVL72 (72 GPU 单一域) 的基础。
技术细节:
  • 原生无损 Fabric: FEC + PHY Retry 组合实现零丢包传输
  • Shadow Engine Recovery: 推理引擎故障后快速切换, 无需冷重启
  • Vera Rubin NVL72: 72 GPU 单一 NVLink 域, 配合 NVSwitch 托盘
  • 与 NVIDIA Dynamo、NVLink Fusion、NMX Controller 协同工作
  • NVSwitch "Switch Admin State" 使托盘维护变为非中断操作
来源: NVIDIA Developer Blog
Bug Issue #1355 | 2026-09-11

8x B300 HGX: NVSwitch Fabric 全局故障导致 Xid 145 (NVLink RLW)

问题描述: 8x B300 HGX 系统上 NVSwitch fabric 出现全局故障, Xid 145 (NVLink RLW) 错误导致 vLLM 推理引擎崩溃。张量并行工作负载完全无法运行, fabric 损坏后无法自恢复。驱动版本 595.x。
技术分析:
  • Xid 145: NVLink Read Link Width 错误, 指示物理层链路降级
  • 影响: NVSwitch fabric 全局不可用, 张量并行工作负载崩溃
  • 环境: 8x B300 HGX, NVSwitch fabric 拓扑
  • vLLM 推理引擎直接受影响
来源: GitHub Issue #1355
本周小结

本周 NVLink 模块在 open-gpu-kernel-modules 仓库中无新的代码提交或 PR。主要动态来自 NVIDIA 官方的 NVLink 6 技术博客 (9月15日) 和 B300 HGX 系统的 NVLink fabric 故障报告 (#1355)。NVLink 6 的 "原生无损 Fabric" 设计为 Vera Rubin NVL72 平台奠定基础。

NVLink C2C 模块动态

NVIDIA 官方 平台页面更新

NVLink-C2C 平台支持扩展: DGX Spark 加入产品线

核心要点: NVLink-C2C 官方页面更新, 当前支持平台包括: Vera Rubin NVL72、GB300 NVL72、GB200 NVL72、Grace CPU Superchip、DGX Spark、NVLink Fusion。相比 PCIe Gen 6 PHY 提供 6x 能效提升和 3.5x 面积效率提升。支持 Arm AMBA CHI 和 Compute Express Link 行业框架。
平台路线图:
  • Vera Rubin NVL72: 第六代 NVLink (3.6 TB/s/GPU), NVSwitch 托盘 14.4 TFLOPS FP8
  • GB300 / GB200 NVL72: NVLink-C2C 统一内存架构延续
  • DGX Spark: 桌面级 NVLink-C2C 应用 (新增)
  • NVLink Fusion: 定制 XPU 通过 NVLink-C2C 连接到 CPU
  • 开源驱动中仍未发现独立 "NVLink-C2C" 代码目录
来源: NVLink-C2C 官方页面
本周小结

本周 NVLink-C2C 模块无开源驱动层面的代码变更。官方页面确认 DGX Spark 作为新平台加入 NVLink-C2C 支持列表。在开源驱动源码中尚未发现独立的 NVLink-C2C 代码目录, 一致性缓存功能可能以其他命名方式存在。

Bug UVM Issue #1387 | 2026-09-22

H100 8x HBM3: CAGRA 工作负载下 UVM 内核恐慌 (LIST_POISON2)NEW

严重问题: 8x NVIDIA H100 80GB HBM3 系统上运行 GPU-resident CAGRA 工作负载 (通过 Milvus), 约每 2 小时触发全系统崩溃。崩溃签名: general protection fault at __rmqueue_pcplist, RAX 包含 LIST_POISON2 值 (dead000000000122), 指示内核内存中的 use-after-free 链表损坏。发生在 UVM 超额订阅 CPU-fallback paging 和 routine munmap() 操作期间。驱动 595.71.05, 内核 7.0.0-1011-gcp。硬件已排除 (零内存错误或 Xid 错误)。
故障链分析:
  • UVM 超额订阅 → CPU-fallback paging → munmap() 触发
  • LIST_POISON2 表明已释放的链表节点被再次访问 (use-after-free)
  • 关键函数: __rmqueue_pcplist (内核内存分配器)
  • 环境: 8x H100 80GB, Driver 595.71.05, Kernel 7.0.0, Ubuntu 24.04.4
  • 影响: AI 向量搜索工作负载 (Milvus CAGRA)
来源: GitHub Issue #1387
Bug MMU Issue #1370 | 2026-09-17

A10G/T4/L40S: Xid 31 MMU Fault (FAULT_PDE) — Vulkan 会话快速轮换NEW

问题描述: 快速 Vulkan 会话轮换 (Kubernetes 环境) 触发 MMU Fault: MMU Fault: ENGINE GRAPHICS GPC9 GPCCLIENT_T1_4 faulted @ 0x100_1ec00000, 错误类型 FAULT_PDE ACCESS_TYPE_VIRT_READ。每台机器的故障虚拟地址保持一致, 表明驱动内部页表缺陷而非用户空间指针错误。驱动 610.57.04, 内核 6.17.0-1019-aws。回滚到 580.159.03 可解决。
技术分析:
  • FAULT_PDE: 页目录条目错误, 指示页表层级损坏
  • 固定 VA 地址表明驱动内部页表管理缺陷
  • 环境: A10G/T4/L40S, Kubernetes, Unreal Engine Vulkan 渲染器
  • 回滚到 580.159.03 可规避
来源: GitHub Issue #1370
PR #1383 MMU 2026-09-22 | Open

修复大页表分配触发直接压缩导致 GPU 访问阻塞NEW

修复方案: 当 pt_size >= PMD_SIZE (x86_64 上为 2MB) 时, 使用 nv_vmalloc() 替代 kvzalloc(), 避免在全局 g_RmApiLock 写锁持有期间触发 2MB 大页分配和耗时的直接内存压缩 (页面迁移 + TLB 刷新)。注册 512MB+ 内存时, 页表数组达到 2MB, kvzalloc() 强制大页分配导致其他进程 GPU 访问进入不可中断睡眠。已在 8x RTX PRO 6000 Blackwell Server Edition 上验证。
代码分析:
  • 关键函数: nvos_create_alloc(), nvos_free_alloc()
  • nv_vmalloc() 调用 __vmalloc() 不带 VM_ALLOW_HUGE_VMAP 标志
  • 使用标准 4KB 页面替代 2MB 大页, 避免直接压缩
  • 环境: 8x RTX PRO 6000 Blackwell, Linux 6.1.180-2, Driver 580.95.05
  • 作者: hyuuko1
来源: GitHub PR #1383
PR #1375 UVM + TLB 2026-09-19 | Open

UVM: TLB Batch 范围合并与最优通道选择NEW

修复方案: 两项 nvidia-uvm.ko 热路径优化: (1) 合并相邻/重叠的 TLB 失效区间, 减少不必要的批处理消耗 — 当新写入的区间与最近排队区间相邻或重叠时, 合并为单一区间 (页大小按位 OR, 保留最大内存屏障, 不增加区间计数); (2) 快速路径通道预留时分配最空闲通道, 缓解 channel-0 瓶颈。最大范围限制仍为 8。
关键文件:
  • kernel-open/nvidia-uvm/uvm_tlb_batch.c — TLB batch 合并逻辑
  • kernel-open/nvidia-uvm/uvm_channel.h / uvm_channel.c — 最空闲通道选择
  • kernel-open/nvidia-uvm/uvm_page_tree_test.c — 单元测试 (相邻/重叠/混合页大小/环绕)
  • kernel-open/nvidia-uvm/uvm_channel_test.c — 通道分配测试
  • 作者: aljojoby9
来源: GitHub PR #1375
Release UVM + MMU Driver 615.71.09

615 驱动: CDMM 成为默认内存管理 + 开源模块成标准

核心更新: GPU 内存管理默认切换为 Coherent Driver-Based Memory Management (CDMM), 取代 NUMA 拓扑方案。新增内核参数控制 UVM 迁移行为。修复了 >2GB 分配被错误阻止的缺陷 (改用替代内存路径)。开源内核模块成为数据中心驱动标准, 不再分发闭源变体。
关键变更:
  • CDMM 替代 NUMA 拓扑作为默认内存管理方案
  • 新增内核参数控制 UVM 迁移行为
  • 修复 >2GB 内存分配被错误阻止的缺陷
  • 闭源内核包不再分发, 开源变体成为默认
  • 从 ClosedRM 迁移到 OpenRM 可能导致 nvidia-smi 故障
来源: Driver 615 Release Notes PDF | Release Notes

趋势展望

短期趋势 (1-4 周)

  • Blackwell Xid 79 修复紧迫性: NVIDIA 已正式确认该 Bug, 跨所有开源驱动版本和 Windows 均可复现。预计将在后续热修复中优先处理。内部 Bug 6426268 已建档。
  • 615 驱动回归修复: DisplayPort 休眠唤醒失败和 Vulkan 管线崩溃是明确的回归, 预计 615 分支将快速发布修复版本。
  • PR #1383 和 #1375 合并预期: 两个高质量 MMU/UVM 优化 PR 已提交, 分别在 Blackwell Server 和通用 UVM 热路径上有显著性能改进。预计将在后续版本中合并。

中期趋势 (1-6 月)

  • 开源驱动成为绝对标准: 615 分支不再分发闭源内核包, 标志着开源驱动从 "可选" 到 "唯一" 的转变。这将推动更严格的代码质量要求和更频繁的社区审查。
  • CDMM 内存管理成熟: 615 驱动将 CDMM 设为默认, 取代 NUMA 拓扑。预计将带来更好的多 GPU 内存管理一致性, 但也可能暴露新的兼容性问题。
  • VA 空间耗尽问题持续: Issue #1140, #1187, #1364 和 Wayland 专属 VA 映射失败表明 VA 空间管理是系统性设计挑战, 需要架构级修复。

核心洞察

1. Blackwell 稳定性成为首要挑战: Xid 79 被 NVIDIA 正式确认, 影响 RTX 5080/5070 Ti/PRO 6000 全系列 Blackwell GPU。Xid 120 GSP 内核恐慌在 cuBLAS 持续工作负载下可确定性复现。这些问题直接威胁到 Blackwell 在 AI/ML 工作负载中的可信度。开源驱动在所有分支 (580/595/610) 上均受影响, 表明问题深植于硬件-固件交互层面。
2. 开源驱动 "唯一化" 带来质量压力: 615 分支不再分发闭源内核包, 开源模块成为数据中心唯一选择。这意味着所有数据中心用户都将直接面对开源驱动的质量问题。本周的 18 个新 Issue 和 615 回归表明, 这一转变的时机可能过于激进。
3. MMU/UVM 优化 PR 质量提升: PR #1383 (页表分配优化) 和 PR #1375 (TLB batch 合并) 展示了高质量的社区贡献。前者解决了大内存注册时的 GPU 访问阻塞问题, 后者优化了 UVM 热路径性能。这些 PR 表明开源驱动的社区生态正在成熟。
4. NVLink 6 为 Vera Rubin 奠定基础: NVLink 6 的 "原生无损 Fabric" 和 Shadow Engine Recovery 是 AI 工厂可靠性的关键创新。72 GPU 单一 NVLink 域的规模对驱动稳定性提出了更高要求。Issue #1355 (B300 fabric 故障) 提醒我们, 大规模 NVSwitch fabric 的可靠性仍是开放挑战。
