SC26NEW

NVIDIA 公布 Rubin HPC GPU：第七代 NVLink 互连首次亮相，单卡 5 万+ CUDA 核心

11 月 15-20 日芝加哥 SC26 超级计算大会上，NVIDIA 发布面向科学计算的 Rubin HPC GPU，归属 Vera Rubin 平台。单颗 GPU 超过 5 万个 CUDA 核心（约为 RTX PRO 6000 Blackwell 的两倍），支持稀疏数据加速，计算精度覆盖 FP64 到 FP4，并首次确认采用第七代 NVLink（NVLink 7）互连，预计 2028 年供应。这是继 NVLink 5（Hopper/Blackwell）、NVLink 6（Vera Rubin NVL72，3.6 TB/s per GPU / 260 TB/s per rack）之后的新一代规格披露。

来源: SC26 大会报道 (搜狐/芝能智芯) | 兴证通信 AI 日报 20261117

与现有 NVLink 代的对比

  • NVLink 5：Blackwell GB200/GB300 NVL72 采用 NVLink 5 + NVSwitch 5/6，单机架 72 GPU 统一 NVLink 域。
  • NVLink 6：Vera Rubin NVL72 每颗 GPU 3.6 TB/s 带宽、整柜 260 TB/s（NVIDIA 技术博客口径），联想已于 11 月初开始全球交付该系统。
  • NVLink 7：本周随 Rubin HPC GPU 首次公布，细节带宽参数尚未披露，2028 年随 Rubin HPC 规模化上市。

开源驱动侧对照

  • 开源内核模块中 NVLINK_DEVICE_VERSION_60（NVLink 6）已随 620.70.06 落地；NVLink 7 枚举与运行时支持预计随 Rubin HPC 开源节奏在 2027-2028 年间补齐。
  • 本周主分支仅 1 个提交（620.73.04 版本发布 commit a4b95f6a），NVLink 子系统（kernel-open/nvidia/nvlink/）无功能变更。

C2C SOFTWARE

CDMM 成为 620 分支默认：硬件一致平台（Grace/Vera 系 C2C）驱动内存管理模式切换

620.70.10 数据中心发布说明再次确认 620 分支的重要架构变化：在所有 NVIDIA 硬件一致性平台（即 CPU-GPU 通过 NVLink-C2C 类一致性互连的 Grace/Vera 平台）上，驱动默认采用 Coherent Driver-Based Memory Management (CDMM)，而不再把 GPU 内存作为 NUMA 节点上线（NUMA 模式仍完全支持，经内核模块参数 NVreg_CoherentGPUMemoryMode 切换，需重载驱动或重启）。配套 UVM 参数 uvm_disable_sam_migration 可控制 SAM 迁移行为；GDRCopy 需 2.5.1+ 才能与 CDMM 配合。这是 C2C 一致性平台上 UVM/驱动内存管理的方向性变化。

来源: 620.70.10 发布说明 CDMM 章节 | 620.70.06 发布说明（CDMM 引入）

配置与验证命令

  • 启用 CDMM：options nvidia NVreg_CoherentGPUMemoryMode=driver
  • 切回 NUMA：options nvidia NVreg_CoherentGPUMemoryMode=numa（驱动重载/重启后生效）
  • 验证：grep Coherent /proc/driver/nvidia/params 与 cat /sys/module/nvidia_uvm/parameters/uvm_disable_sam_migration
  • 注意：已有配置文件时需将选项合并到单一 options 行；升级前应先选定模式。

与 UVM 动态迁移阈值的协同

同一 620.70.10 版本引入了 UVM 动态迁移阈值（PID 控制器，详见 MMU/UVM 标签页）：在 C2C 一致性平台上，GPU-CPU 页迁移的自动调优与 CDMM 模式共同构成 Grace/Vera 世代内存管理软件栈的两大支柱。

NEW FEATURENEW

UVM 动态迁移阈值（Dynamic Migration Threshold）：PID 控制器自动调优页面迁移速率

620.70.10（11 月 23 日发布）新增 kernel-open/nvidia-uvm/uvm_perf_dynamic_threshold.c（+540 行）与配套头文件。该子系统以 PID 控制器闭环调节 UVM 页迁移阈值：订阅 VA space 迁移事件、结合 access counter 反馈，将实际迁移速率维持在目标带宽区间内（默认 10–1000 MiB/s）。默认启用（module param uvm_perf_dynamic_threshold_enable=1），这是 UVM 驱动内存管理近几个月来最大的新特性。

来源: GitHub Compare 620.70.06...620.70.10 | uvm_perf_dynamic_threshold.c 源码

关键设计参数（源码摘录）

  • 目标速率区间：UVM_PERF_DYNAMIC_THRESHOLD_MIN_RATE_MIB_PER_SEC_DEFAULT 10 ～ MAX_RATE 1000（MiB/s），上限 1 TiB/s（高于任何互连）。
  • PID 增益（单位 1/100）：KP=20 (0.20)、KI=5 (0.05)、KD=10 (0.10)；积分限幅 PID_INTEGRAL_ERROR_LIMIT 10000 防止积分饱和。
  • 阈值下限 FLOOR 192：迁移接近空闲时按默认阈值的 25% 放宽准入；上限受 16 位硬件字段限制（65535）。
  • 模块参数：uvm_perf_dynamic_threshold_enable、uvm_perf_dynamic_threshold_min_rate_mib_per_sec、uvm_perf_dynamic_threshold_max_rate_mib_per_sec（均 S_IRUGO）。
  • 配套改动：uvm_gpu_access_counters.c +101 行（迁移速率采样接入）、uvm_perf_heuristics.c +17、uvm_test_ioctl.h +25（新增测试 ioctl）。

技术意义

  • 此前 UVM 迁移阈值是静态/启发式调节；PID 闭环让阈值随负载自适应，缓解「迁移风暴」与「迁移不足」两个极端，对 HMM/sysmem backends 与 C2C 一致性平台（配合 CDMM）均有收益。
  • 积分限幅、输入/输出限幅（error 上限 2^29、单次调整上限 8192）体现保守设计，避免阈值震荡。

#1582：N1X pageable cudaMemcpy H2D 从 4 KiB 分页文件映射读取随映射增长劣化至 ~35 MB/s

PRNEW

PR #1592：修复 2 的幂 ReBAR GPU 上 Static BAR1 自动启用失败（bus 子系统）

当 GPU 物理 VRAM 容量恰为 2 的幂（8/16/32 GiB SKU + ReBAR）时，PCIe BAR1 孔径与全 FB 地址空间一致（无 512 MiB padding）；kbusIsStaticBar1Supported_TU102() 的尺寸/偏移检查假设存在 padding 而误判失败。提交者以 RTX 5080 16 GiB（GB203，BAR1 16384 MiB，总 FB 16303 MiB，GSP-RM 保留 424 MiB）+ Arch 内核 7.3.5-zen + 620.73.04 复现并给出修复。BAR1 即 GPU 内存映射到 CPU 的 MMU 孔径，此修复对 HMM/CDMM 场景的 CPU 侧访问路径有直接意义。

来源: PR #1592

#1577：620.73.04 在 RTX Spark N1X 笔记本上拒绝系统挂起（GB20B 被列入 PM-unsupported）

620.73.04 上 N1X 笔记本每次 s2idle 都在 PM notifier 阶段失败（NVRM: PM suspend notifier failed: 0x56），任何设备尚未挂起即退出；同机 615 分支可正常挂起/恢复。报告者定位根因：620.73.04 以 gpuIsPowerManagementUnsupported() 取代 PDB_PROP_GPU_POWER_MANAGEMENT_UNSUPPORTED，对原有芯片之外额外返回 NV_TRUE 的 GB20B/GB20C（见 src/nvidia/generated/g_gpu_nvoc.c）。社区已有本地 patch 强制开启 GB20B/GB20C 电源管理（Arch N1X 补丁集流传）。

趋势展望

基于本周数据的短期（1-2 月）/中期（2027-2028）趋势与核心洞察

短期趋势（未来 1-2 个月）

  • UVM 动态迁移阈值将向下/横向回移：620.70.10 引入的 PID 控制器子系统大概率随数据中心分支成熟后进入 620.73/620 后续消费级版本；关注 uvm_perf_dynamic_threshold 是否出现在 620.73.xx 的 compare diff 中。
  • 620.73 分支进入高频修复期：发布首周即暴露 #1577（N1X 挂起拒绝）与 #1587（GSP S3 超时）两类电源管理问题，预计 1-2 个版本内回归 gpuIsPowerManagementUnsupported() 的芯片范围。
  • Linux 7.4 适配补丁将落地：#1581 提前给出 procfs/dma_fence_init 两处 API 破裂的完整诊断，配合 620.73.04 已合入的 vma_is_hugetlb conftest，7.4-rc 适配窗口期正在缩短。
  • 社区修复 PR 集中涌现：#1575/#1578/#1583/#1588/#1592 五个 PR 均针对 GSP RPC 上下文、中断处理、DP 唤醒等长尾问题，NVIDIA 评审合入节奏值得关注。

中期趋势（2027-2028）

  • NVLink 7 与 Rubin HPC（2028）：第七代 NVLink 已随 Rubin HPC GPU 公布；开源内核当前仅到 NVLINK_DEVICE_VERSION_60，NVLink 7 枚举与运行时预计 2027 年末-2028 年进入 open-gpu-kernel-modules。
  • Vera HPC 机架（2027 初）：Dell/HPE/Lenovo/Supermicro 供货的 192-CPU 机架将扩大 NVLink-C2C 一致性平台装机量，CDMM + 动态迁移阈值的组合成为该平台 UVM 软件栈标配。
  • 纵向扩展网络竞争：UALink/开放方案专用交换芯片 2027 年试用、2028 年量产（Arista 口径），此前 NVLink 主导地位不变；CPO 光交换在万卡集群的渗透是网络侧最大变量。
  • 开源双轨并行：open-gpu-kernel-modules（官方开源内核）持续消化 Rubin/GR100 固件与 GSP RPC 稳定性问题；Mesa NVK 光追（TTU 已合入，完整能力预期 2027）在图形侧提供第二条开源路线。

核心洞察

  • 本周是「数据中心分支领跑内存管理、GeForce 分支修复稳定性」的典型分化周：620.70.10 的 UVM 动态迁移阈值（PID 控制器）是数月来 UVM 最大的算法级新特性，而 620.73.04 把精力放在 device P2P 生命周期与内核 7.4 兼容。
  • GR100（Rubin）GSP 固件已在 620.73.04 与 620 分支 CoRIM 修复中反复出现——开源驱动的 Vera Rubin 平台软件准备在「固件先行、运行时后至」的节奏推进，与 NVLink 6 → 7 的硬件节奏一致。
  • 社区报告质量显著提升：#1577 直接给出 nvoc 生成代码级根因，#1581 在 7.4-rc 阶段完成 procfs/dma-fence 双 API 破裂诊断——外部贡献正从「报症状」进化为「给 patch」。
  • CDMM 默认化 + 动态迁移阈值同版本出现并非巧合：C2C 一致性平台上「驱动接管内存管理 + 自适应迁移」的组合，指向 NVIDIA 在为 Grace/Vera 世代的统一内存体验做软件栈定型。
