NCCL · NVIDIA 集合通信库

最新发布 NCCL v2.31.2-1 (2026-08-11)

  • Compute Fabric Transport (CFT) via Device API — 在 Blackwell GPU 上支持寄存器窗口内存、设备端 Put/Get/Red/NVLS 操作 Release 设计原理
    CFT Device API 详细设计原理
    核心问题：传统 NCCL 集合通信由 CPU 端发起（host-side），每次通信需 CPU 介入调度，在大规模 MoE 推理中造成 SM 资源浪费和延迟瓶颈。Blackwell 架构需要一种无需 CPU 参与的纯设备端通信机制。
    设计原理：CFT 引入"指针自由通信"模型——使用抽象句柄（handle）替代传统内存指针，GPU kernel 可直接通过句柄发起 Put/Get/Reduce 操作。底层利用 Blackwell 的 TMA（Tensor Memory Accelerator）引擎和 NVLink 5 的 3.6 TB/s 双向带宽，实现设备端零拷贝数据传输。注册窗口内存通过 CUDA VMM（虚拟内存管理）API 完成，支持跨节点对称内存。
    适用场景：MoE 专家并行中的 All-to-All dispatch/combine、多节点张量重分片（resharding）、RL rollout 中的零拷贝张量传输。特别适合 Grace Blackwell GB200 NVL72 等大规模 NVLink 域。
  • Per-collective 算法选择 — 新增 ncclCollConfig_t 结构体，支持按集合操作粒度调优算法和 size 覆盖 Release 设计原理
    Per-collective 算法选择设计原理
    核心问题：NCCL 内部为每种集合操作（AllReduce、AllGather 等）维护一套代价模型来选择最优算法（ring、tree、NVLS 等），但同一模型内不同大小的张量可能需要不同算法。全局配置无法针对单个操作做精细调优。
    设计原理：ncclCollConfig_t 允许用户为特定 communicator 的特定集合操作覆盖默认算法选择和阈值参数。例如，可以为 AllGather 强制使用 NVLS 算法，而为 ReduceScatter 使用 ring 算法。这使得在已知工作负载特征的场景下（如 MoE 推理），可以绕过代价模型直接指定最优路径。
    适用场景：生产环境中已 profiling 确定最优算法的固定工作负载；MoE 推理中 dispatch（小消息）和 combine（大消息）需要不同通信策略的场景。
  • GIN 增强 — EFA GDA 后端、设备端超时机制；PAT 增强 — 节点内 NVLS 分层聚合 Roadmap 设计原理
    GIN (GPU-Initiated Networking) 设计原理
    核心问题：传统网络通信由 CPU 端代理线程驱动，GPU kernel 需要数据发送时必须先通知 CPU，引入额外延迟（通常 5-15μs）。在延迟敏感的小消息场景（如 MoE LL kernel），这一延迟占比可达 30-50%。
    设计原理：GIN 允许 GPU SM（流多处理器）直接发起网络操作（RDMA write/read），绕过 CPU 代理。GDA（GPU-Driven Architecture）是 GIN 的硬件后端，通过 Hopper/Blackwell 的 WDMA（Warp-level DMA）引擎实现。EFA GDA 后端则将这一能力扩展到 AWS Elastic Fabric Adapter，使云上实例也能享受 GPU 直接网络。PAT（Parallel Aggregated Tree）利用节点内 NVLink 做分层聚合，减少跨节点流量。
    适用场景：MoE 低延迟推理 kernel（LL kernel）、大规模训练中的小消息 AllReduce、AWS 云上 NCCL 加速。
  • NCCL RAS 诊断 — 新增 NCCL_RUN_DIAGNOSTICS=1 环境变量用于系统监控 Release

DeepEP · DeepSeek 专家并行通信库

架构重写 DeepEP V2 (2026-04-30 合入 main)

DeepEP V2 是一次完整的架构重写，通过 PR #605 合入。虽未发布新 tag，但代表了当前 main 分支的实际状态。PR #605 官网

  • 切换至 NCCL Gin 后端 — 从 NVSHMEM 迁移至 header-only NCCL Gin，完全 JIT 编译 PR#605 设计原理
    NCCL Gin 后端迁移设计原理
    核心问题：V1 使用 NVSHMEM 作为底层通信库，但 NVSHMEM 的对称内存模型与 NCCL 生态不完全兼容，且 NVSHMEM 的 CPU 端初始化路径引入额外开销。DeepSeek 需要更紧密地与 NCCL 生态集成。
    设计原理：NCCL Gin（GPU-Initiated Networking）允许 GPU kernel 直接发起 RDMA 操作，绕过 CPU 代理。DeepEP V2 使用 header-only 方式集成 Gin，避免链接复杂依赖。同时实现完全 JIT 编译，用户无需预编译 CUDA kernel，首次使用时自动编译适配当前 GPU 架构（SM90/SM100）的代码。ElasticBuffer 统一接口将高吞吐和低延迟模式合并为单一 API。
    适用场景：需要同时支持训练（高吞吐）和推理（低延迟）的 MoE 系统；需要快速适配新 GPU 架构的场景。
  • Scale-out 至 EP2048 — 支持超大规模专家并行 官网 设计原理
    EP2048 Scale-out 设计原理
    核心问题：随着 MoE 模型专家数量增长（如 Kimi K3 的 896 专家），需要跨更多 GPU 分布专家。传统 EP 实现受限于 QP（Queue Pair）数量和 NIC 资源，难以扩展到数百甚至数千 rank。
    设计原理：V2 引入解析式 SM 和 QP 计数（取代自动调优），精确计算每个配置所需的资源。高吞吐模式在 NVLink 域内先聚合 token，再通过 RDMA 跨节点传输，减少 QP 需求。低延迟模式使用直接 all-to-all RDMA+NVLink mesh 连接，配合双缓冲隐藏延迟。这种分层策略使 EP2048 在有限 QP 资源下仍可行。
    适用场景：超大规模 MoE 训练（如 DeepSeek-V3 级别的 256+ 专家跨 128+ GPU）；大规模推理服务中专家分布在多个 NVLink 域的场景。
  • 0 SM 原语 — Engram/PP/CP 使用 RDMA，CP 使用 Copy Engine，释放 SM 给计算 PR#605 设计原理
    0 SM 通信原语设计原理
    核心问题：传统 EP 通信需要占用 GPU SM（流多处理器）来执行数据搬运，在推理时这些 SM 本可用于 token 计算。V1 的低延迟 kernel 需要约 24 个 SM，严重挤占计算资源。
    设计原理："0 SM"意味着通信完全由硬件引擎（Copy Engine / RDMA NIC）完成，不占用任何 SM。Engram 使用 RDMA 直接内存访问实现 token dispatch；PP（Point-to-Point）使用 RDMA 做点对点传输；CP（Copy）使用 GPU 的 Copy Engine（CE）做异步数据搬运。这将 V3 级模型训练的 SM 占用从 24 降至 4-6，释放的 SM 可用于 FFN 计算或其他 kernel。
    适用场景：推理时延敏感场景（需要最大化计算 SM 利用率）；MoE 与 attention 重叠执行的系统（如 MegaScale-Infer）。

v3.7.0 主要特性 (2026-06-11)

  • TMA-backed NVLink 读写 — 使用 Tensor Memory Accelerator 实现高效 NVLink 传输 Release 设计原理
    TMA-backed NVLink 设计原理
    核心问题：NVSHMEM 传统的 NVLink 传输由 GPU warp 通过 store/load 指令完成，需要占用 SM 线程等待传输完成。在 Hopper/Blackwell 架构上，TMA（Tensor Memory Accelerator）是专用的异步数据搬运引擎，可以释放 SM 线程。
    设计原理：TMA 是 Hopper 引入的硬件单元，专门用于异步、bulk 数据搬运，支持 2D/3D tile 传输和自动地址计算。将 NVLink 传输从 warp-level store 改为 TMA 命令后，SM 线程发起 TMA 操作即可继续执行其他计算，实现真正的异步通信。TMA 还支持 group-level 同步（barrier arrive wait），减少全局同步开销。
    适用场景：需要高带宽 NVLink 传输且希望最小化 SM 占用的场景，如 MoE 通信-计算重叠、大规模 AllReduce 中的节点内聚合。
  • GPUNetIO 远程传输 — 新的网络传输层选项 Release 设计原理
    GPUNetIO 远程传输设计原理
    核心问题：NVSHMEM 传统的远程传输（如 ibrc）依赖 CPU 端创建和管理 QP（Queue Pair），在大规模场景下 CPU 成为瓶颈。GPUNetIO 是一种 GPU 直接操作网络硬件的传输方式。
    设计原理：GPUNetIO 允许 GPU kernel 直接向 NIC 发送工作请求，绕过 CPU 端的 libibverbs 调用栈。这减少了每次通信的 CPU 介入延迟（从 ~5μs 降至 ~1μs），同时减少了 CPU-NIC 之间的 PCIe 往返。通过 NVSHMEM_REMOTE_TRANSPORT=gpunetio 环境变量启用。
    适用场景：延迟敏感的跨节点通信、大规模 All-to-All 中需要最小化每消息开销的场景。
  • 浮点原子操作 API — 新增 FP atomic 操作支持 Release
  • 切换至 C++17 基线、许可证改为 Apache-2.0
  • NUMA-aware CPU pinning 控制
  • Python 3.14 兼容（NVSHMEM4Py 0.3.1）

重磅 torchcomms — Meta 重新定义 PyTorch 分布式通信

torchcomms 是 Meta 于 2025 年 10 月推出的全新 PyTorch 分布式通信 API，旨在最终替代现有的 c10d::Backend 接口。10 个月内已累积 3161 commits，是本周最活跃的通信库项目。GitHub 官方博客

  • 初始后端：NCCLX（Meta 内部 NCCL 扩展）、NCCL、RCCL、Gloo Blog 设计原理
    torchcomms 多后端架构设计原理
    核心问题：PyTorch 现有的 c10d 接口设计于 2018 年，使用全局函数式 API（dist.all_reduce 等），不支持 per-device communicator、单侧通信和设备端发起操作。随着 GPU 集群规模突破 10 万卡，这套接口已成为扩展瓶颈。
    设计原理：torchcomms 采用面向对象 API，每个 communicator 绑定到特定设备并支持 eager 初始化。NCCLX 后端包含 Custom Transport（CTran）栈，直接管理 NVLink、IB/RoCE 和 TCP 传输层，绕过 NCCL 的抽象层获得更精细的控制。Window API 支持动态 put/get 操作（类 RDMA 语义），Transport API 提供直接点对点操作。这种设计使 96K GPU 集群初始化从 265 秒降至 24 秒。
    适用场景：超大规模训练（10万+ GPU）；分布式推理中的灵活通信拓扑；需要单侧 RDMA 操作的 MoE 和 pipeline parallelism 场景。
  • 性能亮点：96K GPU 初始化 265s → 24s；16 主机分布式推理解码速度提升 83.3% Red Hat
  • 支持 CUDA 12.6/12.8/13.0，需 PyTorch ≥ 2.8

Meta 于 2026 年 8 月 1 日发表 HCCL 论文，描述为自研 MTIA 300 加速器共同设计的集合通信库。机架内集合通信达 940 GB/s，计算吞吐量损失 < 0.5%。Paper

新版本 UCX v1.22.0 (2026-08-02)

  • SGL datatype 支持 — 新增散射-聚集数据类型 Releases 设计原理
    SGL Datatype 设计原理
    核心问题：MPI 和 PGAS 编程模型中，scatter/gather 操作需要描述非连续内存布局的数据类型。传统实现需要在通信前将数据打包到连续缓冲区，引入额外的内存拷贝开销。
    设计原理：SGL（Scatter-Gather List）datatype 允许用户直接描述由多个不连续内存段组成的数据布局，UCX 传输层可以直接从这些段中读取/写入，实现零拷贝通信。底层利用 RDMA 的 scatter-gather SGE（Scatter/Gather Entry）能力，一次 RDMA 操作即可覆盖多个内存段。
    适用场景：结构化数据的零拷贝传输（如 MoE token 的分散存储）、HPC 中非连续数组通信。
  • 容错恢复基础 — 为 fault-tolerance 提供底层支持 Releases

  • Vera CPU 兼容 — 适配 NVIDIA 下一代 ARM CPU

新开源 MoonEP · Moonshot AI 完美均衡 EP 库

Moonshot AI（Kimi）于 2026-07-29 开源的专家并行通信库，核心创新是动态冗余专家保证完美负载均衡。GitHub 报道

  • 完美均衡：每个 rank 恰好收到 S×K 个 token，彻底消除路由倾斜影响 README 设计原理
    动态冗余专家设计原理
    核心问题：DeepEP 等库在路由倾斜时，"热门" rank 会收到远超平均的 token，导致显存碎片化和 OOM。Moonshot 实测 DeepEP 在高不均衡下会 OOM，而通信尾延迟随 maxvio（不均衡度量）增长稳步退化。
    设计原理：MoonEP 引入"动态冗余专家"——在原始 E 个专家之外，额外创建 B 个冗余专家（训练时 B=E/R，推理时 B=3-4）。当路由倾斜时，在线规划 kernel（近优解）将过载 token 重新分配到冗余专家上，保证每个 rank 恰好收到 S×K 个 token。权重存储在单个连续对称内存张量 [E+B, H, H'] 中，配合 fused permute/unpermute 实现 zero-copy 和 static shape，消除逐层 MoE 的 host 同步。
    适用场景：路由不均衡严重的 MoE 模型训练；显存受限场景（避免 OOM）；需要稳定通信延迟的推理服务。
  • H20 基准：通信时间全面低于 DeepEP V2，combine 操作显著更快 README
  • 首次开源，仅 8 commits，尚无正式版本 tag

趋势展望

本周观察

EP 通信库竞争进入白热化。NVIDIA 将 NCCL-EP 拆分至独立仓库（nccl-extensions），标志着 EP 从"实验性功能"升级为"一等公民"。与此同时，DeepEP V2 全面拥抱 NCCL Gin 后端、MoonEP 以完美均衡策略挑战 DeepEP、torchcomms 以 3161 commits/10个月的惊人速度重塑 PyTorch 分布式通信层——三条线索共同指向一个趋势：2026 年下半年，EP 通信将成为 GPU 集群性能的核心瓶颈和差异化竞争焦点。

短期趋势（1-3 个月）

  • NCCL CFT + NVSHMEM CFT 对齐 — 两个库将共享同一套"指针自由通信"抽象 设计原理
    CFT 统一趋势的设计原理
    核心问题：NCCL 和 NVSHMEM 各自实现了设备端通信机制，但 API 不兼容，用户被迫在两者之间选择，且无法在同一应用中混合使用。这增加了开发和维护成本。
    设计原理：CFT（Compute Fabric Transport）是 NVIDIA 在 Blackwell 架构上推出的统一通信抽象。它使用句柄替代指针，允许 GPU kernel 在不暴露物理地址的情况下发起跨 GPU 数据传输。NCCL 和 NVSHMEM 都在 Q3 2026 路线图中规划了 CFT 支持，意味着底层将共享同一套传输层抽象。这将简化 MoE 系统的通信栈——上层框架可以统一调用 CFT API，由运行时自动选择最优的集合或点对点传输路径。
    适用场景：Blackwell/Rubin 平台上的 MoE 训练和推理；需要同时使用集合通信（AllReduce）和点对点通信（EP dispatch）的混合工作负载。
  • torchcomms 正式发布 — 预计将在 PyTorch 2.10+ 中成为默认分布式后端
  • DeepEP V2 tag 发布 — 社区持续修复 bug，正式 tag 预计近期发布

中期趋势（3-12 个月）

  • 0 SM 通信成为标配 — DeepEP V2 的 0 SM 原语和 NVSHMEM 的 SM-initiated CE collectives 都指向同一方向：通信不再占用计算 SM
  • Rubin 架构驱动新一轮优化 — NCCL、NVSHMEM、DeepEP 都需要适配 NVIDIA Rubin 的新拓扑和互联特性
  • EP 库的"标准化"竞争 — NCCL-EP 提供官方标准 API，DeepEP/MoonEP 提供差异化创新，torchcomms 提供框架级集成——三种路径将趋于融合
  • 低精度通信 — MXFP8 和 NVFP4 集合操作进入 NCCL 考虑范围，将进一步降低通信带宽需求
  • 多厂商可移植性 — oneCCL 迁移至 UXL Foundation、torchcomms 支持 RCCL 后端，通信库正从 NVIDIA-only 走向多厂商
