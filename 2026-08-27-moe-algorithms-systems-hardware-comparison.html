一、先把三个名字对上号

你提到的三个名字，指向的其实是三个完全不同层次的东西——这本身就说明"MoE 算法"这个词在今天已经横跨了模型架构、并行系统、通信库三层。逐个考证如下：

MegaMoE ✅ 存在
= DeepSeek 的融合 MoE MegaKernel，随 DeepSeek-V4 技术报告发布，作为 DeepGEMM 的组件开源
它是什么
把 EP 的多个阶段（Dispatch → Linear-1 → Linear-2 → Combine）融合进单个 persistent CUDA kernel，让 NVLink 通信藏在 Tensor Core 计算背后。 论文原文DeepSeek-V4 报告 §3.1 列的是 4 个阶段；DeepGEMM README 描述为 5 段（把 SwiGLU 单列）。
关键机制
Expert Wave（专家波次）：把专家分批，某个 wave 的通信一完成就立刻开算，稳态下"当前 wave 计算 + 下一 wave token 传输 + 已完成专家结果回传"三者并发。 与 COMET 的"Dispatch↔Linear-1、Linear-2↔Combine 分别重叠"相比粒度更粗但覆盖更全。
成立前提
论文原文每个 token-expert 对传 3h 字节（FP8 dispatch + BF16 combine）对应 6hd FLOPs，故只要 算力/带宽比 ⩽ 2d = 6144 FLOPs/Byte，计算就是瓶颈、通信可被完全隐藏——这是它敢用较低互联带宽的理论依据。
硬件要求
DeepGEMM 整体要求 SM90 或 SM100；Mega MoE 路径仅支持 FP8×FP4、需 PyTorch ≥ 2.9、需对称内存（symmetric memory）多进程启动。 社区分析PR #316 评论区指出代码 arch gate 为 >= 1000（即 SM100/Blackwell）且重度使用 TMEM。SM90 移植见 open PR #323（改用 FP8 权重 + FP32 scale，限制 intermediate_hidden ≤ 4096）。 未公开官方 benchmark 未披露 GPU 型号；无 NVL72 硬性要求（benchmark 为节点内 EP8）。
性能
论文：通用推理 1.50–1.73×，RL rollout / 高速 agent serving 场景最高 1.96×（基线为"强非融合实现"）。 PR #316 实测（EP8）：V4-Pro 384 专家 top-6，batch 32768 达 2438 TFLOPS（1.54×）。已在 NVIDIA GPU 与华为昇腾 NPU两个平台验证。
来源
DeepSeek-V4 技术报告 arXiv:2606.19348 ｜ DeepGEMM ｜ PR #304 实现 ｜ PR #316 benchmark
MoonMoE ❌ 不存在 → 你要找的应该是 MoonEP
两轮定向检索（"MoonMoE"、"MoonMoE" MoE LLM Moonshot）只返回同名服装品牌的电商页面，无任何 AI / 系统领域命中
最可能的指代对象
MoonEP（Moonshot AI 官方仓库）。判断依据：Moon- 前缀、MoE 专家并行领域、与 MegaMoE 的对照关系（同为 MoE kernel / 通信组件）三点全部吻合。 官方定位为 "A Perfectly Balanced Expert Parallelism Library via Dynamic Redundant Experts"。
MoonEP 核心创新
动态冗余专家：不论路由多么倾斜，都保证每个 rank 恰好收到 S × K 个 token。 配合在线近优 GPU planning kernel、zero-copy 与静态 shape（从而消除逐层 MoE 的 host 同步）。 用 maxvio 度量不均衡；权重存放在单个连续对称内存张量 [E+B, H, H'] 中；训练要求 B = E/R，推理推荐 B = 3–4。
相对 DeepEP v2 的优势
官方 README在 H20 / EP=8 上，通信时间在所有不均衡等级下都低于 DeepEP v2，且随 maxvio 增长"几乎持平"，而 DeepEP v2 "稳步退化"； 端到端训练中 DeepEP 在高不均衡下会 OOM，MoonEP 不会。
硬件要求
NVIDIA GPU + NVLink + 对称内存 / VMM；README 提到 "Zhenwu PPU (under review)"。致谢中列出 DeepEP、Echo、UltraEP、阿里 AcclEP。
次可能对象
若你实际指的是模型侧，那应是 Moonshot 的 Kimi 系列 MoE（K2 / K2.6 / K3，见"模型架构对比"标签）。 相关基建仓库：Moonlight / Muon 优化器、 MoBA、 FlashKDA、 checkpoint-engine。 提示Mooncake 在 kvcache-ai 组织下，不在 MoonshotAI 组织下。
DisagMoE ✅ 存在，但它是训练系统而非推理系统
全名 "DisagMoE: Computation-Communication overlapped MoE Training via Disaggregated AF-Pipe Parallelism"，arXiv:2605.11005，2026-05-10 提交，13 位作者，基于 Megatron-LM 实现
核心创新
把 attention 层与 FFN（专家）层部署到不相交的 GPU 组上（AF-Pipe = Attention-FFN Pipeline）， 用单向 many-to-many 多阶段流水线替代双向 All-to-All，再用 计算-通信 roofline 模型在两组之间切分算力与网络带宽。
为什么要这么做
论文原文动机数据很有说服力：Qwen-3 在 8 节点上，序列从 4K 涨到 32K 时 attention 计算占比 28.38% → 50.26%，而 FFN 从 19.22% 降到 13.96%。 两类层的"计算/通信比"天生失衡，把它们放在同一批 GPU 上共用一套并行度，必然有一侧被拖累。
Roofline 如何定配比
两组各占一半 NIC 以平衡进出带宽，有效拐点分裂为 Î^A = 2m/(m+n)·Î、Î^F = 2n/(m+n)·Î。 两阶段 MILP（Gurobi）：先最小化 max(𝒯a, 𝒯f)，并列时最大化 MFU，再局部搜索。 消融结论：16K 序列下 attention:FFN = 16:10 最优（比同构 16:16 快 1.29×），而 4K 下 16:16 才最优——说明最优配比强依赖序列长度。
硬件
16 节点 × 8×H800 (80GB) = 128 卡，每节点 168 CPU + ConnectX-7 8×400 GbE，节点内 NVLink 400 GB/s。 注意论文内部规模表述不一致（profiling 写 64 卡/8 节点，实验写 128 卡，结论写 8–16 节点）；NVLink 代数与 MFU 绝对值未公开。
性能
vs Megatron-LM 1F1B interleaved overlap 最高 1.81×；vs Tutel / COMET 1.2–1.5×；vs DualPipe 1.05–1.13×。 未重叠通信量削减：vs Tutel 88%、vs COMET 75%、vs DualPipe 45%。流水线气泡约为基线的 1/4。 关键背景数字：All-to-All 占比从单节点 22% 升到 8 节点近 78%。
测试模型
DeepSeek-MoE（28 层 / 64 专家 / top-4）、GPT-OSS-120B（36 层 / 128 专家 / top-4）、Qwen3-235B-A22B（94 层 / 128 专家 / top-8），序列 4K–32K。

分析读完全部资料后最值得记住的四条判断

  1. "MoE 算法"的竞争重心已经从模型侧转到系统侧。模型架构层面已经收敛出相当一致的配方：细粒度专家 + 1~2 个共享专家 + sigmoid gating + 无辅助损失的负载均衡。真正拉开差距的是 EP 通信怎么藏、怎么均衡。
  2. 端到端加速比远小于 MoE 层加速比，这是所有论文的共同真相。HyperParallel-MoE 的 MoE-FFN 模块加速 1.58×，端到端只有 1.08–1.09×，因为 attention 与 dense 部分没动。看论文时必须区分"模块级"与"端到端"。
  3. 2026 年的分水岭是 MegaKernel 化。COMET（tile 级重叠、多 kernel）→ UniEP / MegaMoE / Mixture-of-Kittens（单 persistent kernel、warp/threadblock 角色特化、device 侧调度）。副产物是逐位确定性成了新卖点（UniEP 与 Mixture-of-Kittens 都强调，并点名 COMET 不可逐位复现）。
  4. 硬件要求的真正门槛不是算力而是"单一 NVLink 域的大小"。MegaScale-MoE 把 SP=EP=8 严格对齐 NVLink 域；Megatron-Core 官方建议 EP×TP 必须放进单节点；Mixture-of-Kittens 直接依赖 NVL72 的 72-GPU 单域。这条约束决定了架构选择，比 TFLOPS 更关键。

三、MoE 算法的分类框架：五个正交维度

"各种 MoE 算法的区别"如果只列模型名字，会看成一堆无序的参数表。真正有效的读法是把 MoE 拆成五个相互正交的设计维度——任何一个模型都是这五个维度上的一次取值组合，而每个维度都会以不同方式反作用于硬件需求。这是本报告后面所有对比表的骨架。

维度① 路由机制：谁选谁

路由是 MoE 唯一的"算法核心"，其余都是工程。按选择方向与是否可微可以分成五类，它们对系统的友好程度差异极大：

路由机制代表工作选择方向是否丢 token负载是否天然均衡对系统的影响
Token-Choice top-k
（业界唯一主流）		GShard、Switch、Mixtral、DeepSeek 系、Qwen3 系token 选专家会（超 capacity 即丢）否，需额外手段动态 shape、需要 all-to-all 前的 host 同步或 CPU-free 设计
Expert-Choice top-kExpert Choice Routing（Google）专家选 token不丢，但 token 可能 0 次被选是（每专家固定收 k 个）shape 静态、系统极友好，但破坏自回归因果性，难用于 decoder LM
确定性哈希Hash Layers按 token id 查表不丢近似均衡零路由开销、完全静态，但质量弱于学习式路由
最优分配 / 匈牙利-SinkhornBASE Layers、Sinkhorn 路由全局线性分配不丢是（严格均衡）需全局求解，训练可用、推理不可用
Soft / 全可微Soft MoE、Dense-MoE加权融合全部专家不丢是无稀疏收益，FLOPs 不省，主要用于视觉与小模型

分析为什么大模型全都选了系统最不友好的那一种

Expert-Choice、BASE、Hash 三种在系统层面都比 token-choice top-k 好得多——静态 shape、无需 host 同步、天然均衡，几乎是 MegaKernel 化的理想输入。但主流 decoder-only LLM 依然全部使用 token-choice，原因是：Expert-Choice 需要看到整个 batch 内所有 token 才能挑选，违反自回归因果性，逐 token decode 阶段根本无法实现；BASE 的全局分配在推理时无从下手；Hash 牺牲了路由的语义。
这就是整个 MoE 系统领域存在的根本原因：算法层选了对质量最优、对系统最恶劣的方案，代价被完整地转移给了系统层。后面几个标签里所有的重叠、均衡、MegaKernel 技巧，本质都在偿还这一笔债。

维度② 负载均衡：从辅助损失到无辅助损失

token-choice 会自我强化——被选得多的专家训练得更好，于是被选得更多，最终坍缩到少数专家。三代解法：

第一代：辅助损失（GShard / Switch，2020–2021）

在主损失外加一项，惩罚"路由概率"与"实际分配比例"的乘积和：

L_aux = alpha * N * sum_{i=1..N} ( f_i * P_i )

  N     = 专家数
  f_i   = 分配给专家 i 的 token 比例（实际频率，不可微）
  P_i   = 路由器给专家 i 的平均概率（可微，梯度从这里回传）
  alpha = 权重系数

论文原文GShard 与 Switch Transformer 都取 alpha = 0.01。这个乘积形式很巧妙：f_i 不可微只当常数，梯度全部经 P_i 回传，效果是把概率质量从过热专家上推走。代价它是一项与语言建模目标直接冲突的正则——调大则均衡但掉质量，调小则质量好但严重倾斜。

第二代：Expert Capacity + Token Dropping

给每个专家设容量上限 C = capacity_factor * (T * k / N)，超出的 token 直接跳过该专家（走残差）。分析这是纯工程兜底：它保证了静态 shape 与显存上界，代价是训练/推理不一致且丢 token。capacity_factor 通常取 1.0–1.25，是典型的"质量换确定性"旋钮。现代大模型（DeepSeek-V3 起）在训练中已不丢 token。

第三代：无辅助损失（Aux-Loss-Free，2024 起成为主流）

思路是把"均衡"从损失函数里彻底拿掉，改成对路由打分加一个可动态调节的偏置，且该偏置只参与 top-k 的选择、不参与最终加权：

选择阶段:  top_k_indices = TopK( s_i + b_i )        # b_i 影响谁被选中
加权阶段:  y = sum_{i in topk} ( s_i * Expert_i(x) )  # 权重仍用原始 s_i, 不含 b_i

偏置更新:  专家 i 过载 -> b_i -= u
          专家 i 欠载 -> b_i += u        (u = 更新速度, 无梯度)

论文原文出自 Auxiliary-Loss-Free Load Balancing Strategy for MoE（arXiv:2408.15664），在 DeepSeek-V3 中大规模落地。它的优势在于梯度完全干净——均衡不再向模型参数注入任何与语言建模冲突的梯度，只是在选择环节做了一次无梯度的"配额调度"。这一条已成为 2025–2026 年新模型的默认配方（具体采用清单见下一标签）。

要点负载均衡的三个层次不要混淆

  • 训练时的算法均衡：aux-loss / bias 调节，目的是让所有专家都被训练到。作用于模型质量。
  • 训练时的系统均衡：capacity、drop-and-pad、以及 sequence-wise 而非 batch-wise 的均衡约束。作用于显存与吞吐。
  • 推理时的部署均衡：EPLB（专家并行负载均衡器）、冗余专家复制、MoonEP 的动态冗余专家。此时模型权重已固定，无法再改路由分布，只能改专家的物理摆放。这是 2026 年最活跃的战场——因为它是唯一一个"不动模型就能拿到收益"的层次。

维度③ 共享专家：一半是质量设计，一半是系统设计

DeepSeekMoE（arXiv:2401.06066）提出的两大支柱之一。设 1～2 个对所有 token 恒定激活的专家，用来承载通用知识，让路由专家专注差异化，缓解"知识冗余"。

分析但它在系统上的价值常被低估：共享专家的计算完全不需要 All-to-All（数据本来就在本地），因此它是一块天然的、时长可预测的本地计算，正好可以用来掩护路由专家的通信。几乎所有重叠系统都会显式利用这一点。反过来，Qwen3 系列刻意不设共享专家（明确列为与 Qwen2.5-MoE 的差异），意味着它少了这块免费的掩护物，对通信重叠的要求更高。

维度④ 专家粒度：细粒度化的收益与账单

在总参数量不变的前提下，把每个专家的中间维度 d_ff' 切小、专家数 N 等比放大、k 同步放大。收益是组合数爆炸式增长：

Mixtral 8x7B      : N=8,   k=2   -> C(8,2)   = 28 种专家组合
DeepSeek-V3       : N=256, k=8   -> C(256,8) ~ 4.1e14 种组合

同样的激活参数量，表达能力天差地别。但账单在系统侧：单个专家的 GEMM 变小，M 维（该专家收到的 token 数）从数千掉到数十～数百，Tensor Core 利用率显著下降，且 kernel 数量与 launch 开销线性增长。这正是 Grouped GEMM、MegaBlocks 的块稀疏化、以及 2026 年 MegaKernel 路线要解决的问题——细粒度专家是模型侧的胜利，也是 kernel 侧的债务。

维度⑤ 稀疏度：直接换算成互联带宽需求

稀疏度 = 激活参数 / 总参数。它决定训练与推理的 FLOPs，但对硬件更直接的传导是每层每 token 的 All-to-All 字节数：

dispatch 字节/token = k * h * bytes_per_elem      # FP8 时 bytes=1
combine  字节/token = k * h * bytes_per_elem      # 通常 BF16, bytes=2

例: h=7168, k=8, dispatch FP8 + combine BF16
    -> 8*7168*1 + 8*7168*2 = 172 KB / token / 层
    再乘以 MoE 层数与 batch 内 token 数, 就是单层 All-to-All 的总流量

对照MegaMoE 论文把这条关系写成了一个漂亮的判据：每个 token-expert 对传 3h 字节（FP8 dispatch + BF16 combine）对应 6hd FLOPs，因此只要机器的算力/带宽比 ⩽ 2d（V4 配置下为 6144 FLOPs/Byte），通信就一定能被计算完全掩盖。这条判据的实用价值极高：它把"我的集群互联够不够"从玄学变成了一次除法——拿单卡 TFLOPS 除以单卡可用 NVLink 带宽，与 2d 比大小即可。

分析五个维度里，唯一被系统层"倒逼"改回去的是维度⑤

模型侧的自然倾向是稀疏度越低越好（同样激活参数换更大总容量）。但 k 一大，All-to-All 流量线性上涨；专家一多，EP 度必须跟着涨，而 EP 一旦跨出单一 NVLink 域，带宽就从 数百 GB/s 掉到 RDMA 的几十 GB/s，出现断崖。于是出现了 node-limited routing（DeepSeek-V3：限制每个 token 最多送往 4 个节点）这类纯粹为硬件拓扑而生的算法约束——路由自由度被主动砍掉一块，换取通信量的可控。这是模型与硬件之间最典型的一次妥协，也说明"MoE 算法"这件事已经不可能脱离硬件单独设计。

本标签的一句话结论

2026 年主流大模型在五个维度上已经高度收敛：路由用 token-choice top-k（维度①）、均衡用无辅助损失 bias（维度②）、多数配 1～2 个共享专家（维度③）、专家一律细粒度化（维度④）、稀疏度压到 3%～6%（维度⑤）。模型架构的差异化空间正在快速收窄——真正的分野已经转移到注意力机制（MLA / 线性注意力混合 / 稀疏注意力）以及后面几个标签讨论的系统层。

4.2 五条已经收敛的设计选择

分析2026 年的头部 MoE 已经在这五点上高度一致

  1. 共享专家从"可选"变成"默认"。DeepSeek 全系、Kimi 全系、GLM 全系、Llama 4 全系都带 1 个（K3 是 2 个）常开专家。反例只剩 Qwen3 主线、MiniMax、gpt-oss、Mixtral、Arctic、DBRX——注意 Qwen3-Next 与 Qwen3.5 已经加回了共享专家，说明连 Qwen 也改了主意。
  2. sigmoid + 无辅助损失，正在取代 softmax + 辅助损失。DeepSeek（noaux_tc）、Kimi（noaux_tc + 极小 seq_aux）、GLM-5（从 4.5 的未标注切到明确 sigmoid + noaux_tc）、MiniMax-M2（use_routing_bias）全在这一侧。仍用辅助损失的是 Qwen3 全系（0.001）、Llama 4（0.001）与 gpt-oss（0.9，比别人高两到三个数量级，值得单独注意）。
  3. 专家数量往上、top-k 相对往下、专家变窄。从 Mixtral 的 8 专家 / FFN 14336，到 Kimi-K3 的 896 专家 / FFN 3072、Qwen3.5 的 512 专家 / FFN 1024。专家总数涨了两个数量级，单专家宽度掉了一个数量级。
  4. MTP（多 token 预测）成了大模型标配。DeepSeek 全系、GLM 全系、Qwen3.5、MiniMax-M2（3 个模块）都开。反例是 Kimi 全系（num_nextn_predict_layers: 0）与 Llama 4、gpt-oss。
  5. 注意力不再是 MHA/GQA 二选一，而是"稀疏或线性混合"。2026 年的四条路：DSA 稀疏注意力（DeepSeek-V3.2/V4、GLM-5）、KDA（Kimi-K3）、线性混合（Qwen3-Next/3.5、MiniMax-M1）、滑窗交替（gpt-oss、Llama 4 iRoPE）。而 MiniMax-M2 从 M1 的线性混合退回了全 full attention——这是全表里唯一一次明确的架构回退。

为什么"专家变多变窄"对系统是坏消息

NVIDIA 在 MoE Parallel Folding 里给出了直接证据："fine-grained MoE models achieve lower training efficiency compared to coarse-grained MoE models across all parallelism strategies" （arXiv:2504.14960）。原因是同样的 token 数被切成更多、更小的 GEMM，每个 GEMM 的 M 维变小，Tensor Core 利用率下降，而 All-to-All 的消息数量却按专家数线性增长——模型侧为了质量做的细粒度化，成本全部转移给了系统侧。这就是 TAB ⑥ 和 TAB ⑦ 里所有工程复杂度的来源。

4.4 注意力这一侧正在抢走时间预算

过去讨论 MoE 只看 FFN，但长上下文把这个假设打破了。DisagMoE 给出的实测很直接：Qwen-3 在 8 节点上，序列从 4K 涨到 32K 时 attention 计算占比从 28.38% 升到 50.26%，而 FFN 从 19.22% 降到 13.96%（arXiv:2605.11005）。

这解释了为什么 2026 年几乎所有新模型都在动注意力：不动注意力，MoE 优化的天花板就被 Amdahl 定律锁死。四条路线各有代价：

MegaScale-MoE：把 NVLink 域大小写进了设计假设
arXiv:2505.11432 ｜ 字节 Seed + 北京大学 ｜ 生产系统，1440×H800
最值得抄的一条设计决策
对 attention 用序列并行（SP）、对专家用专家并行（EP），完全不用 TP。理由是 TP 的 all-reduce 在每层都要跑两次，而 SP+EP 的通信量更低。消融数据：论文原文SP+EP 相对 TP+TP 的 MFU 高 14.9%–32.9%。
硬件假设是显式写出来的
"Assuming the model is trained on a NVIDIA Hopper GPU workstation with an NVLink domain of size 8"——整套并行度是按"NVLink 域 = 8"设计的。这是全部 MoE 系统里最值得记住的一句话：并行度不是调出来的，是被互联拓扑决定的。
MFU 随规模下降，作者自己解释了原因
"the MFU ... declines from 32.48% to 27.89%"（240→1440 卡，全局 batch 固定 720）。归因于固定 batch 导致 micro-batch 变少、流水气泡增多。
一条反直觉的观察
论文原文"the MFU value decreases as GPU compute capability increases"——GPU 越强 MFU 越低，因为 routing / scatter / gather 这些 memory-intensive 算子受显存带宽限制，算力涨了它们不涨。这与 TAB ⑦ 的"带宽台阶"是同一个道理的两种表述。
激活显存
SAR（选择性激活重算）相对不用 SAR 降低激活显存 45.5% / 57.2%。
正文瑕疵
注意正文称 "across the four kinds of GPUs"，但 Table 4 只列了 H800 / A100 / H20 三种，存在文内不一致。

UniEP：把"架构调参"变成"参数搜索"

与 COMET 的分界线
COMET 是"多 kernel + tile 级重叠"，UniEP 是两个 MegaKernel：一个融合 Dispatch+GroupGEMM，一个融合 GroupGEMM+Combine。kernel 内部动态给 SM 分配"算/通"角色，用片上 scoreboard 在 token 粒度管依赖。
为什么强调确定性
保持 deterministic token ordering，从而避免拆 micro-batch 带来的数值不确定性。分析这与 Mixture-of-Kittens 强调"完全确定性"是同一个卖点——2026 年"逐位可复现"从学术洁癖变成了工程需求，因为大规模训练的 loss spike 排查依赖它。
Relay Worker
做 intra-rank multicast 以节省 NVLink 流量：同一节点内多个 rank 需要同一份 token 时，只跨节点传一次再在节点内转发。
消融链条很清晰

5.4 一个必须单独警告的数字：FlashDMoE 的 6×

FlashDMoE 的 kernel 数对比很有说服力，但加速比要打问号

它最有价值的贡献是把"GPU 算子数量"这个指标摆到台面上：FlashDMoE 1 个 GPU op，COMET 33 个，Megatron-CUTLASS 85 个，Megatron-TE 261 个，Megatron+DeepEP 432 个，DeepSpeed-MoE 550 个。这直观解释了 MegaKernel 化的动机——每次 kernel launch 都是一次 CPU 参与和一次同步点。

分析三代演进背后是同一条被反复触碰的墙

每一代都在解决上一代暴露的问题：第一代用多 stream 重叠，但被 kernel launch 开销和 CPU 同步卡住；第二代切到 tile 级，但 kernel 数量爆炸（Megatron+DeepEP 达 432 个 GPU op）；第三代干脆把一切塞进一个 kernel，代价是编程复杂度与硬件绑定——MoK 直接要求 Blackwell SM100/SM103 + NVL72，MegaMoE 要求 SM90/SM100 + 对称内存。

六、推理服务系统：一切复杂性都源于一条不等式

6.1 先把这条不等式写清楚：b ⩾ F / B

MoE 推理的所有工程复杂度，都可以从一条不等式推出来。MegaScale-Infer 把它写成了闭式：

"a GPU requires that 2bhn/F ≥ 2hn/B, i.e., b ≥ F/B, to fully utilize its matrix multiplication capability."
"For an A100 GPU, the batch size at least needs to be 156 tokens (312 TFLOPS / 2 TB/s)."
— MegaScale-Infer, arXiv:2504.02263

也就是说，要让 GEMM 从带宽受限翻到算力受限，每张卡上聚起来的 token 数必须至少等于"算力 ÷ 带宽"。这个门槛与 MoE 无关，任何 dense 模型都一样。MoE 的问题是它在这个门槛上又乘了一个稀疏度：

"given a batch size of 156, the average number of decoding tokens dispatched to each expert is 156 × topk/#expert = 156 × 2/8 = 39, with the theoretical Model Flops Utilization (MFU) for FFN modules of 2/8 = 25%."
— 同上

把这个逻辑套到 2026 年的模型规模上，数字变得非常刺眼。Janus 给出了 H100 上的版本：

"Under this roofline, DeepSeek-V3 would require a batch size of about 18k (5k) tokens to operate in the compute-bound regime on H100 (A100) GPUs, which is hardly achievable for many real-world inference scenarios where batch sizes are often below 100."
— JANUS, arXiv:2512.13525

把这三段连起来，就是整个 MoE 推理领域的问题陈述

H100 上需要 18000 token 才能进入算力受限区，而真实线上请求的 batch 常常低于 100——差了两个数量级以上。而且即使凑够了 batch，FFN 的理论 MFU 上限仍被稀疏度锁死在 topk / #expert。MoE 省下的是 FLOPs，但 decode 阶段的瓶颈从一开始就不是 FLOPs。后面所有系统——大规模跨节点 EP、PD 分离、attention/FFN 解耦、专家 offload——都是在回答同一个问题：怎么把足够多的 token 聚到同一个专家上。

核心机制

七、EP 通信库：2026 年真正的胜负手

如果只看模型卡片，MoE 看起来是个模型问题。但把 EP 拉到 32 卡以上，它就变成了一个纯粹的通信库问题。 这一层的库不到二十个，却决定了上面所有训练/推理系统的性能天花板——因为 All-to-All 在 8 节点 EP 下已经占到执行时间的近 78%（DisagMoE 实测）。

分析先说结论：这一层在 2026 年发生了三件事

  1. 后端从 NVSHMEM 迁向 NCCL GIN。这不是审美问题。DeepEP V2 的 release note 直接写了迁移理由， UltraEP 也在 README 里预告了同样的迁移路线。NVSHMEM 是一个完整的 PGAS 运行时， 而 MoE 只需要它的一小块能力，NCCL 从 2.28 起把这块能力单独暴露成了 device API。
  2. 优化目标从"峰值带宽"变成"倾斜路由下的带宽稳定性"。 MoonEP 和 UltraEP 的 benchmark 横轴都不是 token 数，而是 router imbalance。 这是一个很本质的转向：在真实负载下，慢的那一个 rank 决定一切。
  3. 瓶颈从带宽转向同步开销。UBEP 论文把这个现象命名为"synchronization tax"， 并给出了最有说服力的数字对比（见 §7.5）。当链路从 50 GB/s 涨到 392 GB/s 时， 真正贵的东西已经不是搬数据，而是 flag、barrier 和 kernel launch。

7.3 均衡派：MoonEP 与 UltraEP 把横轴换成了 imbalance

MoonEP — 用动态冗余专家换取"完美均衡"
Moonshot AI 出品 ｜ 默认分支为 master
一句话定位
官方文档README 原文： "keeps token loads perfectly balanced across ranks via dynamic redundant experts"。 它不是在"更快地搬倾斜的数据"，而是在"让数据不再倾斜"。
核心机制
每个 rank 收到 S × K 个 token，用一块 [E+B, H, H'] 的对称张量承载 E 个主专家 + B 个冗余专家。训练时 B = E/R，推理时 B = 3–4 即可。 分析训练和推理的 B 差了一个量级，说明训练侧的倾斜比推理侧严重得多——这与"训练要跑满长序列、推理 batch 很小"的直觉一致。
关键结论
官方文档"MoonEP's comm time stays almost flat as maxvio grows, while DeepEP v2 — whose latency is set by the hottest rank — degrades steadily"。 benchmark 条件是 "run on H20 with EP=8, sweeping the router imbalance"， 并且在所有倾斜水平上都胜过 DeepEP v2，而 DeepEP 在极端倾斜下直接 OOM。 未公开但绝对 GB/s 数值、SM 门槛、CUDA / PyTorch 最低版本一概未给。
硬件要求

使用陷阱
官方文档零拷贝视图"alias buffer state that the next dispatch / combine overwrites — do not hold them across communication calls"。 分析这是所有零拷贝 EP 库的共同雷区，接入时最容易踩。

核心论点（原文）
论文原文"as link bandwidth scales in superpods, the relative cost of synchronization primitives, such as flags, barriers, and kernel launches becomes dominant, a phenomenon we term the 'synchronization tax'"。
为什么在 superpod 上才暴露
论文原文"On the CM384 architecture, however, the bandwidth increases by over an order of magnitude to 392 GB/s. As a result, token dispatch reaches bandwidth saturation very quickly, leaving phase-level synchronization as the dominant constraint." 对比锚点很清晰：CM384 的 UB 总线 392 GB/s vs IB/RoCE v2 的 50 GB/s。 分析这解释了一个反直觉的现象——网络越快，通信库越难写。带宽富裕之后，所有固定开销都变成了瓶颈。

7.7 这一层的三条硬约束

分析选库之前先看这三件事，比看带宽表有用

  1. NVLink 域能不能装下你的 EP 组。这是全层最强的约束，反复出现在三处独立证据里： HybridEP 在 GB200 上 EP8→EP64 只涨 1.7×，在 H100 上涨 7.0×； UltraEP 承认 "When the NVLink domain is smaller than the EP group, the achievable imbalance floor sits slightly above the ideal 1.0"； DeepEP SM100 纯 NVLink EP8 能跑 726 GB/s，一旦跨节点就掉到 61–90 GB/s。 同一个库在域内域外差一个数量级，选型时这条比 TFLOPS 重要得多。
  2. 你的 router 有多倾斜。如果倾斜稳定在 1.5 以下，DeepEP V2 够用； 一旦 maxvio 上到 2–4，就必须考虑 MoonEP / UltraEP / ECHO 这类"复制热专家"的方案—— 因为 DeepEP 的延迟由最热的 rank 决定，MoonEP 的文档明确说了在极端倾斜下 DeepEP 会 OOM。
  3. 你能付多少 SM。2026 年这一层的共同 KPI 已经不是带宽而是 SM 占用： DeepEP V2 省 4×、HybridEP 用 TMA 做到 minimal SM、fabric-lib 做到 SM-free。 原因很实在——MegaKernel 化要求通信和计算挤在同一个 persistent kernel 里，通信占的 SM 就是计算失去的 SM。

分析一个容易被忽视的结论：官方库跑不过民间库

NCCL EP 是 NVIDIA 用自家 device API 从零重写的 MoE 库，硬件是 576 节点的 EOS 集群， 结果 combine 落后 DeepEP 5–12%、vLLM 端到端落后 7–10%，而且这些数字是 NVIDIA 自己写进论文的。 同时 DeepEP 的 README 里明确写着它依赖 PTX 未定义行为 （ld.global.nc.L1::no_allocate.L2::256B 读 volatile 数据）并提供了关闭开关。 这两件事放在一起看，结论是：当前 EP 通信的性能领先，有一部分来自愿意越过规范边界的工程胆量， 而这部分优势本质上是不可持续的——它会随着 NCCL GIN 这类"官方通路"成熟而被抹平， 代价是短期内损失 5–12% 性能，换来向前兼容与可维护性。选库时要清楚自己在这条权衡上站哪一边。

为什么"算力/带宽比"是比 TFLOPS 更好的指标

MegaMoE 给出的判据值得单独拎出来当成通用工具：每个 token-expert 对的通信量是 3h 字节，对应计算量是 6hd FLOPs（d 为专家中间维度），于是

若  单卡算力 / 单卡可用互联带宽  <=  2d   ->  计算是瓶颈, 通信可被完全隐藏
若  单卡算力 / 单卡可用互联带宽  >   2d   ->  通信是瓶颈, 再怎么重叠也藏不住

举例(概念性推算, 非论文数字):
  H100 BF16 稠密 ~ 990 TFLOPS, NVLink4 单向 450 GB/s
  -> 比值 ~ 2200 FLOPs/Byte, 而 2d (d=3072) = 6144  ->  节点内 EP 计算受限, 可藏
  同一张卡若走 RDMA 50 GB/s
  -> 比值 ~ 19800 FLOPs/Byte  >>  6144            ->  通信受限, 必然暴露

分析这个除法解释了本报告里几乎所有系统的设计选择：节点内 EP 天然处在"计算受限"区间，所以 MegaKernel 类方案（MegaMoE、UniEP、Mixture-of-Kittens）都把 benchmark 放在节点内或单一大 NVLink 域里，就能拿到接近理想的重叠；一旦跨节点进入"通信受限"区间，纯重叠失效，必须换武器——要么削减通信量本身（DisagMoE 用单向多对多替代双向 All-to-All），要么改变部署形态（attention/FFN 分离），要么在算法侧限制路由跨度。换句话说：重叠类工作和分离类工作并不是竞品，它们分别属于台阶的两侧。

显存这一侧：容量与带宽的两笔账

阶段显存主要被什么占用MoE 特有的放大因素缓解手段
训练参数 + 梯度 + 优化器状态 + 激活总参数量远大于激活参数量，但显存按总参数算——这是 MoE 最贵的地方（671B 总参即使只激活 37B，权重依然要全部放下）EP 切分专家（每卡只放 N/EP 个专家）、ZeRO-1/ZeRO-3、FSDP+EP、重计算
推理 prefill权重 + 大批 token 的激活专家权重必须常驻，且路由倾斜时某些卡的临时缓冲显著变大FP8/MXFP4 权重量化、大 EP 度摊薄权重、静态 shape 预分配
推理 decode权重 + KV cache每 token 只算 k/N 的专家，算术强度极低，几乎纯粹是权重搬运受限大 batch 聚合提高强度、MLA 压缩 KV、PD 分离、低延迟 EP kernel

分析MoE 在 decode 阶段的处境最尴尬

稠密模型 decode 时每张卡要读全部权重、算全部 FLOPs；MoE decode 时每张卡仍要"准备好"自己那份专家权重，但每步只有一小部分被真正用到。算术强度（FLOPs / Byte）被稀疏度直接除掉了一遍，于是 decode 变成极端的带宽受限场景。这正是"低延迟 EP kernel"（DeepEP 的 low-latency 模式）和 PD 分离必须存在的原因：只有把足够多的请求聚到一起，才能把每份专家权重的一次搬运摊到更多 token 上。MoE 省的是 FLOPs，但 decode 阶段瓶颈本来就不是 FLOPs——这是理解 MoE 推理部署一切复杂性的起点。

九、横向对比与选型：怎么读这些倍数，以及该选谁

最重要的一条阅读纪律不要跨论文比较加速比

本报告出现的倍数从 1.05× 到 20.76× 不等，但它们互相不可比，原因有三层： （1）基线不同——TileLink 的 20.76× 对的是"完全不重叠"，DualPipe 的 1.05–1.13× 对的是已经高度优化的 1F1B interleaved； （2）测量层级不同——有的是 MoE 层，有的是 MoE-FFN 模块，有的是端到端； （3）硬件不同——同一个库在 GB200 和 H100 上的表现差 4 倍以上。 唯一正确的读法是：只在"同基线、同层级、同硬件"的三元组内部比较。下面第一张表就是为了让这条纪律可执行。

分析模型侧的收敛，恰恰是系统侧最难做的那一侧

2026 年的模型配方已经高度一致：细粒度窄专家 + 1~2 个共享专家 + sigmoid gating + 无辅助损失的均衡（bias 校正）。 问题是这四条每一条都在给系统增加难度：细粒度让每次 All-to-All 的消息更小更碎（带宽利用率下降）； 共享专家引入了一条必须与路由专家并行的额外计算路径；sigmoid + 无辅助损失让路由分布更自由、也更容易倾斜； top-k 变大直接乘倍通信量。 换句话说，模型侧的每一次"质量提升"，都是系统侧的一张账单——这正是为什么 MoE 的竞争重心已经从模型架构转移到了通信库和 kernel。

9.5 趋势展望：2027 年会发生什么

分析从这批 2026 年工作里能读出的五条趋势

  1. 后端统一到 NCCL device API。证据链已经很完整：DeepEP V2 已迁移（"switched from the NVSHMEM backend to the more lightweight NCCL Gin backend"）， UltraEP 预告要迁（"will switch to the more lightweight NCCL GIN in future"），NCCL EP 是原生实现， NVIDIA 还给 Blackwell 准备了下一代 CFT 模块。 分析代价是短期性能倒退 5–12%，换来的是不必再依赖 PTX 未定义行为。 预计 2027 年这个差距会被抹平，届时 DeepEP 的"手工优化护城河"会显著变浅。
  2. 优化目标从带宽转向"同步开销"。UBEP 的 synchronization tax 是一个会被反复引用的概念： 当链路从 50 GB/s 涨到 392 GB/s，token dispatch 几乎瞬间打满带宽， "leaving phase-level synchronization as the dominant constraint"。 NVL72、CM384 这类 superpod 越普及，这个问题就越突出。 2027 年的论文标题里出现 barrier / flag / kernel-launch 的频率会明显上升。
  3. "少占 SM"取代"跑满带宽"成为 EP 库的第一 KPI。 DeepEP V2 省 4× SM、HybridEP 用 TMA 做到 minimal SM、fabric-lib 做到 SM-free while RDMA transfer—— 三家不同出品方在同一年给出同一个方向。原因是 MegaKernel 化把通信和计算挤进了同一个 persistent kernel， 通信占的每一个 SM 都是从计算那里抢的。
  4. 逐位确定性从"学术洁癖"变成产品特性。UniEP 与 Mixture-of-Kittens 都把 bit-wise reproducibility 写进卖点，并且都点名 COMET 不可逐位复现。 分析这背后是 RL / RLHF 的现实需求：训练与 rollout 的数值不一致会直接导致策略漂移， 而 MegaMoE 恰好报告了 RL rollout 1.96× 的收益——两件事指向同一个市场。
  5. attention 会抢走 MoE 的风头。最硬的数字是 DisagMoE 的 28.38% → 50.26%。 当 attention 吃掉一半时间预算，继续优化 MoE 通信的边际收益就很低了。 2026 年已经出现 DisagMoE、MegaScale-Infer、JANUS、FinDEP、vLLM AFD 这一整批分离系统， 以及 DSA / KDA / Gated DeltaNet 这批注意力改造—— 预计 2027 年的重心会是"attention 与 FFN 各用什么硬件"这个部署问题，而不再是"All-to-All 怎么更快"。

分析最后一条给决策者的提醒

本报告最反直觉的一条结论是：官方库跑不过民间库，而且差距的来源是"愿不愿意越过规范边界"。 NCCL EP 在 576 节点 EOS 集群上、由 NVIDIA 亲手用自家 device API 重写， combine 仍落后 DeepEP 5–12%、vLLM 端到端落后 7–10%，且这些数字是 NVIDIA 自己披露的； 而 DeepEP 的 README 明确写着它用 ld.global.nc.L1::no_allocate.L2::256B 读 volatile 数据， 并提供 DISABLE_AGGRESSIVE_PTX_INSTRS=1 作为逃生开关。 选型时必须自己决定站哪一边：要那 5–12%，还是要升级 NCCL 时不用重新验证正确性。 对多数团队，后者更值钱。
