NCCL (NVIDIA Collective Communications Library)

Release 2026-09-17

NCCL v2.32.3-1: Vera Rubin 支持 + CFT Counted-Write + TLS 加密HOT

核心要点：引入 Vera Rubin (sm107) 架构初步支持，新增 CFT counted-write 和 wait 原语，Socket GIN 支持 TCP 自定义内核，可选 TLS 加密传输，增强诊断工具（Watchdog DMA 镜像、ATTN 日志级别），修复多个关键缺陷。
  • Vera Rubin 平台支持: 初步支持 Rubin GPU 架构 (sm107)，包含 CX9 rail/plane 检测和 MPS+MLoPart。性能模型调优将在后续版本完成。 Release Notes 设计原理
    Vera Rubin 平台支持设计原理
    核心问题：NVIDIA 下一代 Vera Rubin GPU 引入新的计算架构 (sm107) 和互联拓扑（CX9 交换机），现有 NCCL 内核和传输层需要适配新的硬件特性，包括新的 SM 架构、 rail/plane 拓扑检测逻辑，以及 MPS (Multi-Process Service) 与 MLoPart (Multi-Logical Partition) 的协同。
    设计原理：采用渐进式支持策略：首先在 v2.32.3-1 中添加基础架构识别（sm107 编译目标、CX9 路由检测），确保 NCCL 能在 Rubin 平台上正确初始化和运行。性能模型调优（如 CTA 大小、通道数、算法选择）将在后续版本中基于实际硬件基准测试完成。当前需要用户手动增加 CTA 数量以获得更好性能。
    适用场景：NVIDIA Vera Rubin GPU 集群的早期部署和测试。为下一代 AI 超级计算机提供软件就绪支持。
  • CFT Counted-Write + Wait: Device API 新增 counted-write 和 wait 原语，支持构建自定义同步机制。Socket GIN 支持 TCP 自定义内核创建。 CFT 文档 设计原理
    CFT Counted-Write 设计原理
    核心问题：Compute Fabric Transport (CFT) 在 v2.31.2-1 中引入了基本的 Put/Get/Red/NVLS 操作，但缺乏高效的同步机制。在自定义内核中，需要一种轻量级的"计数写入"原语来通知远端 GPU 数据已就绪，以及"等待"原语来阻塞直到条件满足。
    设计原理：Counted-write 是一种原子递增操作，写入端每次完成数据填充后递增远端的计数器。Wait 原语让读取端自旋等待计数器达到预期值。这种设计类似于硬件信号量，但利用 CFT 的单边写入能力直接在远端内存执行，无需 CPU 参与。与 Socket GIN 结合，允许用户通过 TCP 创建自定义传输内核，扩展 CFT 到非标准网络环境。
    适用场景：自定义通信-计算重叠内核（如 MoE dispatch/combine 与 GEMM 重叠）、非标准集合操作、需要细粒度同步的 device-initiated 通信模式。
  • TLS 加密传输: 通过 OpenSSL3 为 Socket 流量提供可选 TLS 加密，增强多租户环境下的数据安全。 Release Notes 设计原理
    TLS 加密传输设计原理
    核心问题：NCCL 的 Socket 传输层（用于 TCP 网络通信）默认以明文传输数据。在多租户云环境或跨数据中心通信场景中，GPU 间传输的模型参数、梯度等敏感数据可能被窃听。
    设计原理：集成 OpenSSL3 库，在 Socket 传输层之上添加 TLS 1.3 加密层。加密是可选的（通过环境变量启用），避免对单租户高性能场景的性能影响。TLS 握手在 NCCL 初始化阶段完成，证书验证通过 NCCL 的 bootstrap 机制分发。加密粒度为整个 communicator 级别，而非单个连接。
    适用场景：多租户 GPU 云环境、跨数据中心的联邦训练、需要合规性认证的企业部署。在单租户 InfiniBand/RoCE 环境中建议禁用以保持最佳性能。
  • 增强诊断工具: 新增 ATTN 日志级别（关键非致命事件）、GPU-resident 进度计数器（检测冻结任务）、Watchdog DMA 镜像（诊断停滞内核）、NVLink/NIC 状态诊断、降级带宽检测。 Release Notes 设计原理
    增强诊断工具设计原理
    核心问题：大规模 GPU 集群（1000+ GPU）中，通信停滞、NVLink 降级、NIC 故障等问题难以定位。传统日志级别（INFO/WARN/ERROR）无法有效区分"需要立即关注的非致命事件"和"纯信息性日志"。GPU kernel 冻结时，CPU 端无法感知。
    设计原理：(1) ATTN 日志级别介于 WARN 和 INFO 之间，专门用于标记"不终止任务但需要运维关注"的事件（如降级带宽、版本不匹配）。(2) GPU-resident 进度计数器让每个 GPU kernel 在执行过程中递增一个 GPU 可见的计数器，watchdog DMA 引擎定期镜像这些计数器到 CPU 可访问的内存，CPU 端监控线程比较时间戳差异来检测冻结。(3) NVLink/NIC 状态诊断通过 NVML 和 ethtool 查询硬件寄存器，检测物理层降级。
    适用场景：大规模训练任务的运维监控、长时间训练的故障预警、多租户环境下的性能问题排查。
  • 关键缺陷修复: 修复 H100 PAT+NVLS 性能下降、对称窗口注册地址空间耗尽、PAT 连接死锁、B40 TMA 内核崩溃、profiler 开销等问题。实验性 Windows NetworkDirect 传输。 Release Notes

DeepEP (Expert-Parallel Communication Library)

Release 2026-09-16

DeepEP v1.2.1: Topk10 低延迟内核支持NEW

核心要点：新增 topk10 支持到低延迟 dispatch/combine 内核，将 MoE 推理支持的 top-k 范围扩展到 10。社区反响热烈（5 thumbs-up, 2 rocket）。
  • Topk10 低延迟内核: 扩展低延迟 dispatch/combine 内核支持 top-k 值到 10，覆盖更多 MoE 模型配置（如 top-10 路由策略）。 Release Notes 设计原理
    Topk10 低延迟内核设计原理
    核心问题：MoE 模型的路由策略决定了每个 token 被发送到多少个专家（top-k）。DeepEP 的低延迟内核之前仅支持 top-k ≤ 8 的配置，但新一代模型（如某些 671B 参数模型）开始使用 top-10 甚至更高的路由策略，需要扩展内核支持。
    设计原理：低延迟内核使用 TMA (Tensor Memory Accelerator) 和共享内存进行节点内通信，RDMA 进行节点间通信。top-k 值影响每个 GPU 需要接收/发送的 token 数量，进而影响缓冲区大小和同步逻辑。扩展到 topk10 需要重新计算缓冲区布局、调整 TMA 传输粒度、修改 doorbell 同步机制以处理更多的完成通知。PR #403 实现了这些修改，同时保持了与之前 topk 配置的向后兼容性。
    适用场景：使用 top-10 路由策略的 MoE 推理场景，特别是 DeepSeek-V3 及类似架构的模型。低延迟模式针对推理优化，优先减少端到端延迟而非最大化吞吐量。

torchcomms Meta | 活跃开发

torchcomms: Collective Tuner + AllReduce 自动选择 + 稀疏 RDMAACTIVE

核心要点：本周 torchcomms 高度活跃，新增 Collective Tuner 接口和 v1 阈值规则、AllReduce 算法/协议自动选择、稀疏 RDMA IB 配置、IB NIC 能力验证。修复 bootstrap 死锁和 folly 依赖。
  • Collective Tuner 接口 (Sep 18): 引入 v1 阈值规则，允许根据消息大小和网络条件自动选择最优集合算法。 Commits 设计原理
    Collective Tuner 设计原理
    核心问题：不同集合操作（AllReduce、AllGather、ReduceScatter）在不同消息大小、网络拓扑、GPU 数量下的最优算法差异巨大。Ring 适合大消息，Tree 适合小消息，但手动选择算法对开发者不友好。
    设计原理：Tuner 接口提供一个抽象层，在运行时根据消息大小、参与 GPU 数量、网络带宽等参数，通过预定义的阈值规则（v1 rule）自动选择最优算法和协议。类似于数据库查询优化器的概念——基于代价模型选择执行计划。v1 阈值规则是基础版本，后续将支持更复杂的机器学习驱动的调优。
    适用场景：大规模训练中需要自动性能优化的场景，特别是消息大小变化频繁的工作负载（如 MoE 路由、动态 batch 推理）。
  • AllReduce 算法自动选择 (Sep 20): 从 tuner 中选择 AllReduce 算法和协议，实现运行时自适应优化。 Commits
  • 稀疏 RDMA + IB 验证 (Sep 18): 允许稀疏 RDMA IB 配置、验证 IB NIC 能力、外部 IB 配置覆盖。 Commits
  • 关键修复: 修复非对称子组创建后的 bootstrap 死锁 (#4151)、移除最后一个 folly 依赖、替换虚拟 QP 业务卡中的 JSON 处理。 Commits
  • 架构清理: 删除 CTRAN PRiMS 运行时、将 direct-PRiMS CVARs 移入 MCCL 命名空间、切断最后的 PRiMS 构建边缘。 Commits

趋势展望

短期趋势 (1-3 个月)

  • NCCL 2.33 + Rubin 性能优化: 预计 10 月发布，将包含 Vera Rubin GPU 的完整性能模型调优，以及 Device API 对传统 TREE/RING 内核的迁移。
  • MoE 通信竞争加剧: DeepEP、NCCL EP、UCCL-EP 三方竞争，推动 MoE 通信原语标准化和性能优化。
  • torchcomms 走向成熟: Collective Tuner 和自动算法选择将使 torchcomms 成为 PyTorch 分布式训练的默认通信层。

中期趋势 (3-12 个月)

  • 统一通信栈: NVIDIA 的 NCCL + NIXL + NVSHMEM 三者协同覆盖训练、推理和 HPC，形成完整生态护城河。
  • 低精度集合操作: MXFP8/MXFP4/NVFP4 集合操作将成为下一代训练的关键特性，减少通信带宽需求。
  • 跨厂商可移植性: UCCL-EP 和 torchcomms 的多后端支持推动通信库跨 NVIDIA/AMD/Intel 硬件的可移植性。
  • 计算-通信重叠深化: Entwine 等论文推动 tile-level 的细粒度重叠，从操作级走向数据级。
本周观察：通信库生态正经历"三代同堂"格局——NCCL 巩固训练通信霸主地位（Rubin 支持 + TLS 加密），DeepEP 在 MoE 细分领域建立优势但面临 NCCL EP 和 UCCL-EP 的夹击，torchcomms 作为 PyTorch 原生通信层快速崛起。NVSHMEM 在 HPC 领域保持稳定但 AI 场景存在感减弱。未来竞争焦点将从"单一集合操作性能"转向"计算-通信-内存三位一体优化"。
