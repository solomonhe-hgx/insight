一、30 秒读懂这篇专利

一句话

在"统一内存寻址（unified memory addressing）"的大 GPU 里，NVIDIA 增加了一个由页表项里单个比特控制的 本地化地址映射视图：打开后，一段 64MB 对齐的显存不再被细粒度地交织（stride/interleave）到 全部 uGPU 的 DRAM 上，而是"前 32MB 全在 uGPU0、后 32MB 全在 uGPU1"；同时用早已存在的 GPC affinity mask 把 kernel 的 CTA 限制在同一个 uGPU 的 GPC 上执行。 结果是计算和它的数据被钉在同一个 die / 同一个 crossbar 域内，跨 uGPU 的延迟、半带宽损失与 LTC（末级缓存）重复缓存全部被消除；而当应用确实需要更大算力/容量时，又可以把该属性关掉退回全交织模式。

为什么值得重点关注

  • 它是"多 die 单逻辑 GPU"路线的必然补丁。NVIDIA 一直对外强调多 die 封装在软件视角是"一颗 GPU"，但这篇专利在背景部分把代价写得非常直白：跨 uGPU 只有约一半带宽、C2C 路径延迟更差、末级缓存出现双份副本。这等于官方承认单逻辑 GPU 内部已经是 NUMA。
  • 它把 NUMA 亲和性从"驱动内部黑盒"提升为"应用可声明的分配属性"。权利要求 3/10/20 明确写了"localization attribute 来自应用"，说明 NVIDIA 打算把这条路径通过新的 CUDA API 暴露给用户。
  • 实现代价极低，因此专利价值高。不改 crossbar、不改 HBM、不改物理拓扑，只在 MMU 的 AMAP 单元里加一套映射视图 + PTE 借用一个空闲高位 + XAL 接口加宽 1 bit。这种"低成本高收益"的点子最容易成为对手的必经之路。
  • 独立权利要求 1 写得极宽——"GPU 地址映射硬件，被配置为选择性地把应用的内存访问范围限制到该核本地连接的内存"，几乎覆盖了所有"硬件层面做 GPU 内部内存亲和"的实现。分析这也是它目前还在审查（美国同族 2026-03-30 刚答复非最终审查意见）的原因之一。

一、专利认定的硬件前提：GPC → uGPU → 多 die GPU

专利原文 说明书用相当篇幅重述了 NVIDIA GPU 的层级结构，这部分是理解发明动机的关键：

  • SM：包含 CUDA core、Tensor Core、寄存器堆、纹理单元、一个 RT Core，以及 L1 / shared memory。
  • GPC（Graphics Processing Cluster）：包含多个 SM、光栅引擎（raster engine）、ROP 分区、PolyMorph 引擎。说明书给出的示例量级是每 uGPU 约 4 个 GPC、每 GPC 约 8 个 SM。
  • uGPU（micro-GPU，微 GPU）：说明书明确指出，在大 die 上做"每个 GPC 到整个存储子系统的全连接 crossbar"造价过高、不可能建（too costly to build）。因此 NVIDIA 把若干 GPC 连同一组 L2 / LTC slice 挂到自己的一个 crossbar 上，构成一个 uGPU。
  • uGPU 之间：通过 L2 NOC（片上网络） 或 C2C（chip-to-chip）链路缝合成一颗对软件呈现为单一实体的大 GPU。
  • 封装：多个 uGPU 可以位于不同的 die，与 HBM（3D 堆叠 SDRAM）一起放在 interposer 上，再封装到基板并焊在 PCB。

专利原文 说明书同时交代了两项已有能力作为发明的"地基"：一是 统一虚拟寻址，让每个处理器看到同一份一致的内存映像； 二是 P2P 直接访问，GPU0 可以直接 load/store 到 GPU1 的显存，CPU 也可以寻址任意 GPU 的显存。 本发明要解决的正是"统一寻址很方便，但物理上的远近差异被抹平后带来的性能陷阱"。

二、跨 uGPU 访问的三笔账（发明动机）

专利原文说明书把远端访问的代价拆成三条，非常适合直接引用：

① 带宽腰斩

跨 uGPU 的流量相比本地访问"只能得到降低了的（例如一半）带宽"。原因是数据必须穿过 uGPU 边界， 受限于 L2 NOC / C2C 的横截带宽，而不是本地 crossbar 到 HBM 的全带宽。

② 延迟抬升（C2C 更糟）

访问必须走"间接路径"——L2 NOC 或 NVLINK，而经由 C2C（跨 die）时更差。 这条对多 die 产品尤其关键：die 内 NOC 的额外跳数还能忍，跨 die 的 SerDes / 封装级链路在延迟上是另一个量级。

③ LTC 双份副本（最容易被忽略的一条）

远端数据会在末级缓存（LTC）里被复制两次：远端 uGPU 的 LTC 缓存一份（因为它是该 DRAM 的 home）， 请求方 uGPU 的 LTC 又缓存一份。结果是有效缓存容量被浪费、功耗被无谓抬高。

分析为什么第三条才是这篇专利的"隐藏主线"

带宽与延迟问题，业界的常规解法是"加粗互联"（更宽的 C2C、更多 NOC 通道），本质是花面积和功耗买回来。 但LTC 重复缓存是拓扑无关的结构性浪费：无论互联做多宽，只要一条 line 同时被两侧 LTC 持有， 片上缓存的有效容量就是打折的。对于 LLM / MoE 这类权重复用率高、缓存命中率决定 roofline 位置的负载， 消除双份副本相当于凭空扩大了末级缓存。这也解释了为什么专利在"有益效果"里把 "高效利用缓存容量（efficient use of cache capacity）"与延迟、带宽并列。

三、现有手段为什么不够用

已有机制能做什么为什么解决不了本问题
GPC affinity mask
见引证 US8253749、WGL_NV_gpu_affinity		 把执行限制到指定的 GPC / GPU 节点上 只管算在哪，不管数据落在哪。地址仍然被细粒度交织到所有 uGPU 的 DRAM，所以计算被钉住之后反而更容易频繁跨域取数
Stride / interleave 地址映射（传统默认视图） 把线性地址均匀铺到全部 DRAM 通道，最大化聚合带宽、避免热点 它的设计目标就是"打散"，与"局部性"天然对立；且为避免 L2 slice camping 还要做 swizzle，软件根本无法推算某个地址归属哪个 uGPU
MIG / 多实例分区
见引证 US11663036、US11249905		 把一颗 GPU 切成多个互相隔离的"独立处理器" 是硬隔离：切开之后就不是一颗大 GPU 了，失去了"需要时可以把资源合起来用"的弹性。本专利要的是按分配、按 64MB 块、可混用的软隔离
软件侧页迁移 / first-touch NUMA 策略 操作系统式的按需搬页 搬运本身消耗带宽与功耗，且对 GPU 上百万级并发线程的访问模式反应太慢；分析本专利选择了"不搬数据，改地址视图"这条零拷贝路线

一、方案总纲：两个机制的合体

专利原文本发明由两个互相配合的机制构成，缺一不可：

  1. AMAP 地址映射硬件（新增）——位于 uGPU 的 MMU 内部，为同一段可寻址范围额外提供一套 本地化（localized）视图，与传统的 stride / 交织视图并存。
  2. GPC affinity mask（已有）——把执行限制在属于目标 uGPU 的那些 GPC 上。

只有"数据映射本地化"而不限制执行位置，线程仍会从别的 uGPU 发起访问； 只限制执行位置而不改地址映射，数据仍被交织到远端。两者同时打开，才形成 FIG. 6B 中那道把两半应用隔开的"围栏"。

关键工程取舍：什么都没改

专利原文 本方案不重新设计 crossbar、也不改动 HBM，整个可寻址空间始终是可达的（remains reachable）。 受影响的硬件单元只有两处：MMU（新增 AMAP 视图 + FLA 中的 localization bit）与 XAL（GPU 与 PCIe/CPU 的接口，位宽 +1 bit）。 分析这种"最小侵入式"实现是它最具威胁的地方——代价低到几乎没有理由不做。

二、两套地址映射视图的差异

模式 0：传统 stride / 交织视图

专利原文 线性地址以某个 uGPU stride 为单位被细粒度地条带化（striping）到整个 GPU 存储系统的所有 DRAM 上， 并且对 uGPU 的选择施加 swizzle（打散），以避免 L2 slice "camping"（某几个切片被反复命中形成热点）。

模式 1：本地化视图

专利原文 在 64 MB 对齐的区域上做重映射：前 32 MB 半区映射到 uGPU0，后 32 MB 半区映射到 uGPU1 （偶数半区 → uGPU0，奇数半区 → uGPU1）。此模式下不施加 swizzle， 因此软件可以直接计算"地址 → uGPU 归属"，这是让应用能自己做亲和性编排的前提。

三、模式开关：PTE 地址域里的 localization bit

专利原文 模式选择由存放在 MMU 页表项（PTE）地址字段中的一个 localization attribute（本地化属性，1 bit / flag）决定，其位置由一个宏定义给出： LOCALIZATION_MODE_BIT_IN_ADDRESS_OFFSET。

图 C · localization bit 在 PTE 地址域中的位置与语义 PTE 地址字段（为"远端寻址"预留的位宽 > 本地最大容量所需位宽 ⇒ 存在空闲高位） ┌───────────────────────────────────────────────────────────────────────────┐ │ 空闲高位 │ LOCALIZATION │ 物理页帧号 (PA / GPA / FLA) │ ... │ │ │ MODE BIT │ │ │ └────────────┴──────┬───────┴──────────────────────────────────────────┴─────┘ │ 位置 = LOCALIZATION_MODE_BIT_IN_ADDRESS_OFFSET │ ┌───────────┴────────────┐ 0 = stride 交织视图 1 = localized 本地化视图 ★ 关键设计：该位被当作"属性(attribute)"而非"地址位(address bit)" ⇒ MMU 做地址边界检查(bounds check)时必须把它剔除，否则会误判越界 ⇒ RM 的查表/反查代码必须"知道"这一位的存在 ⇒ XAL（GPU↔PCIe/CPU 接口）位宽 +1 bit 以承载它

为什么"借位"是可行的（专利给出的理由）

专利原文 PTE 的地址字段位宽是按远端内存寻址的需求设计的，而本地可支持容量所需的位数更少， 因此天然存在空闲高位可供借用。 分析这是一个非常典型的"零成本硬件扩展"套路：不新增页表字段、不改 PTE 格式版本、 不影响 TLB entry 尺寸，因此对现有 MMU 流水线的扰动几乎为零；代价只是所有解析该地址域的软硬件都必须同步认识这一位， 这恰恰是后面"一致性与 Peer 访问"一节里所有麻烦的根源。

二、四步流程（对应 FIG. 7 的 1002 / 1004 / 1006 / 1008）

① 1002 — 指定目标 uGPU / GPC 节点

专利原文 应用通过 affinity mask 指名要绑定的 uGPU（或 GPC 节点）。 这一步复用已有机制，不需要新硬件。

② 1004 — 带本地化属性的显存分配

专利原文 分配时置上 localization attribute；CUDA 驱动请求 RM / AMAP 在 64 MB 对齐（且为其整数倍）的空间上建立本地化映射； 随后 RM 从该 64MB 单元中子分配（sub-allocate）属于所选 uGPU 的那个 32MB 半区。

③ 1006 — 用 affinity mask 约束 CTA 派发

专利原文 驱动利用 affinity mask，使 CWD（Central Work Distributor，中央工作分发器） 只把 CTA（thread block，线程块）派发给该 uGPU 所属的 GPC。

④ 1008 — 访问被自然收敛到本地 DRAM

专利原文 此时线程发出的内存访问被限制在直接连接的 DRAM 上，跨 uGPU 边界的往返被消除。

典型用法：一分为二

专利原文 说明书给出的典型场景是把工作拆成两批体量相当的批次，每个 uGPU 各跑一批—— 即 FIG. 6B 相对 FIG. 6A 的差别。此外还提到"智能驱动（intelligent / smart driver）"变体： 由驱动自行分析应用特征，自动决定用本地化还是非本地化模式，无需应用显式声明。

三、编程模型层面的形态推演

专利原文说明书明确提到"新增 CUDA API"，并把它描述为内建于设备分配调用（cudamalloc）中的 API， 同时施加 GPC affinity mask 与逐次分配的 localization 属性。专利未给出具体函数签名，以下伪代码为分析推演，仅用于说明形态：

// ——— 推演形态（非专利原文 API）———
// 1) 查询本 GPU 有几个 uGPU 域，以及每个域的本地 DRAM 容量
int nUgpu; cudaDeviceGetAttribute(&nUgpu, cudaDevAttrLocalityDomainCount, dev);

// 2) 声明"把这块内存本地化到 uGPU k"
void *pA;
cudaMallocWithLocality(&pA, bytes,        // 内部按 64MB 对齐向上取整
                       /*localityDomain=*/0,
                       /*flags=*/cudaMemLocalizedMode);   // → PTE localization bit = 1

// 3) 把 kernel 的 CTA 限制在同一个 uGPU 的 GPC 上（affinity mask 语义）
cudaStream_t s0; cudaStreamCreateWithAffinity(&s0, /*ugpuMask=*/0b01);

// 4) 两个域各跑一半工作 —— 对应 FIG.6B
kernel<<<grid/2, block, 0, s0>>>(pA);   // uGPU0：算与数据同域
kernel<<<grid/2, block, 0, s1>>>(pB);   // uGPU1：算与数据同域

// 反例：本地化了内存但没约束执行域 ⇒ 一半线程变成纯远端访问，
//       比全交织模式更慢（因为交织至少是"两边都各占一半"的均摊）

三条工程约束（直接来自专利文本，实现时躲不开）

  • 对齐与粒度：本地化映射必须建立在 64 MB 对齐的整数倍空间上；单个 uGPU 实际拿到的是其中 32 MB 半区。这意味着小分配用不了这条路径，或者必须由分配器做二级 suballocator。
  • 同块同模式：同一个 64 MB 对齐块内的所有页必须使用相同模式，否则产生地址别名（aliasing）。
  • 块间可混用：不同的 64 MB 块可以各用各的模式，且重映射一个块"不应影响相邻内存区段的地址"——这是该方案能在真实驱动里增量启用的关键。

一、为什么"改地址视图"必然引出一致性难题

分析 本地化模式的本质是：同一个物理页，在开启/关闭 localization bit 时对应的物理落点不同。 换句话说，地址的语义依赖于"由谁、按哪套视图去解释"。凡是绕过 GPU MMU 直接持有/传递物理地址的路径 （CPU 侧访问、缓存 probe、NVLink peer 报文、RM 的反查表）都会因此看到不一致的地址。 专利说明书用了相当篇幅逐一处理这些路径，这部分恰恰是最能反映真实工程难度的地方。

二、CPU 侧与一致性系统（coherent system）

专利原文在 CPU 操作系统拥有内存分配权的一致性系统里，处理方式是：

  1. RM 取走一块 64 MB；
  2. 向操作系统标记该块为 offline（离线），使 OS 不再把它当作可分配内存；
  3. RM 用带 localization bit 的 PTE 格式自行建立 GMMU 映射；
  4. RM 自身的查表代码必须感知 localization bit。

CPU 的访问权限被明确收窄

专利原文 CPU 可以对本地化内存执行 prefetch（预取），但被描述为无法访问 / 无修改权限， 原因就是重映射之后 CPU 看到的地址视图与 GPU 不同。

为让缓存 probe 仍能正确解析，方案依赖反向映射 r2p（reverse map）总是"去本地化（de-localize）"探测地址， 从而把 probe 还原到原始地址上，使被缓存的行能被正确定位。

替代实施例：把标志位暴露给 CPU OS

专利原文 说明书同时给出另一种实施方式——把 localization 标志位对 CPU 操作系统可见， 以支持真正的共享 / 一致性内存操作。分析这条替代路径在 Grace-Hopper / Grace-Blackwell 这类 CPU-GPU 一致性平台上意义更大：一旦 CPU 页表与 GPU 页表共享同一套 localization 语义，就可以把 GPU 内部的 uGPU 亲和性一路上升为"整机 NUMA 拓扑"的一部分。

三、Peer 访问：GPA 与 FLA 两条路径的差别

映射类型页表位于本地化模式下能否工作（专利结论）
GPA
(Guest / GPU Physical Address peer 映射)		 源 GPU（发起方） 专利原文有条件可行：需要 NVLink 报文中存在一个空闲比特来携带 localization 信息。 分析因为翻译发生在源侧，本地化语义必须"随包传输"到目标侧才能被正确解释——这等于对链路协议提出了要求。
FLA
(Fabric Linear Address)		 目标 GPU（被访问方） 专利原文直接可行：FLA 的 PTE 就住在目标 GPU 上，且其编程方式与本地显存相同， 因此 FLA 能够支持本地化的 peer 映射。受影响单元列表里也明确提到"FLA 中的 localization bit"。

分析这条对比揭示了 NVIDIA 的架构偏好

"翻译放在目标侧（FLA）就天然兼容，翻译放在源侧（GPA）就要改链路协议"——这正是 Fabric Attached Memory 类架构（见引证 US11182309） 把地址翻译责任下推到目标/fabric 侧的价值所在。本专利相当于给出了一个新证据： 当 GPU 内部开始出现多套地址视图时，"谁负责翻译"决定了新特性能否零协议改动地扩展到 scale-up 域。 对自研 scale-up 互联的团队而言，这是一条应当提前对齐的设计决策。

  • MMU：新增 AMAP 本地化视图；FLA 中承载 localization bit；地址边界检查必须排除该位。

  • CUDA 驱动：新 API；向 RM 请求本地化映射；把 affinity mask 传给 CWD。
  • CWD：按 affinity mask 限制 CTA 派发范围。

二、独立权利要求逐条解析

CLAIM 1 · 装置

专利原文（要点转述） 在一个使用统一内存寻址的 GPU 系统中——多个处理核共享统一的内存视图，且能够访问彼此本地连接的内存—— 包含"GPU 地址映射硬件，其被配置为选择性地将运行在某处理核上的应用的内存访问范围限制到该核本地连接的内存"。

解析

  • 前序限定了适用场景：必须是"统一内存寻址 + 多核可互访彼此本地内存"的系统。纯粹的硬分区（切开后互不可见）不落入该前序。
  • 技术特征只有一条：地址映射硬件 + "选择性限制访问范围到本地内存"。分析没有限定 64MB/32MB、没有限定 PTE、没有限定 swizzle，因此保护范围相当宽——任何"在地址映射硬件层面把访问收敛到本地内存"的做法都可能被覆盖。
  • 分析"选择性（selectively）"是这条要求的重心：它把本发明与"固定分区/固定映射"区分开来。也就是说，规避设计如果做成"始终本地化、不可切换"，反而可能不落入 claim 1。
CLAIM 8 · 方法

专利原文（要点转述） 在某处理核上启动应用的执行，并选择性地把其内存访问范围限定到该核本地连接的内存。

解析

分析方法项把"启动执行"这一步显式写进来，实际上锁定了 "执行位置选择 + 访问范围限制"这对组合动作，正对应说明书 FIG.7 的 1006 + 1008。 对软件栈（驱动 / runtime / 编译器）实现者而言，方法项通常比装置项更值得关注。

CLAIM 15 · GPU 器件（结构最具体）

专利原文（要点转述）一个 GPU，包含：

  • 第一簇（含第一处理核）、第一 DRAM、把二者相连的第一 crossbar；
  • 第二簇、第二 DRAM、第二 crossbar；
  • 两个 crossbar 之间的互联，使任一簇都能访问另一簇的 DRAM；
  • 位于第一簇内、耦合到第一 crossbar 的地址映射器（address mapper），其被选择性地配置为： 使第一簇产生的地址本地化到第一 DRAM，且不访问第二 DRAM。

解析

  • 这条把 FIG.5 的硬件结构完整写进了权利要求，包括"地址映射器在簇内、耦合到该簇的 crossbar"这一位置限定。分析这暗示实现上 AMAP 是每 uGPU 一份、位于 MMU/crossbar 前端，而不是集中式的一份。
  • "并且不访问第二 DRAM"是一个强限定：分析它要求在该配置下形成真正的封闭访问域，而非"优先本地、必要时溢出"的软亲和策略。
  • 从属项 17（不同芯片 + chip-to-chip 互联）与 18（簇即 uGPU）合起来，把保护范围明确覆盖到 chiplet / 多 die GPU 形态。

三、行业背景：竞品在同一问题上的公开做法

AMD：把分区做成产品级配置项

AMD Instinct MI300X 在产品文档层面直接暴露了计算分区（SPX / CPX 等）与 内存分区 NPS（NUMA Per Socket，如 NPS1 / NPS4）两组正交模式，由 BIOS / 驱动配置， 本质上是把"XCD 与 HBM stack 的亲和关系"变成用户可选的运行模式。 分析与本专利相比，AMD 的方案是粗粒度、静态、整卡级（切换通常需要重置设备、且以整个分区为单位）， 而 NVIDIA 这篇专利是细粒度、动态、逐分配级（64MB 块，可与交织模式在同一进程内混用）。 方向一致，颗粒度与灵活性差一个层级。
来源：AMD Instinct MI300X GPU Partitioning Overview ｜Quick Start Guide to Partitioning MI300X GPUs ｜专利侧参考 AMD US11841803B2 · GPU chiplets using high bandwidth crosslinks

NVIDIA 自家产品线：这篇专利要落到哪里

NVIDIA 官方对 Blackwell / Blackwell Ultra 的描述是两颗接近光罩极限的 die 通过超高带宽 die-to-die 互联封装、对软件呈现为单一 GPU。 分析本专利（优先权 2023-08-29）的时间点与 Blackwell 的开发周期高度吻合，说明书里的"两个 uGPU、各自 crossbar、经成对 LTC slice 走 C2C" 几乎就是双 die 产品的抽象描述。学术界的微基准测试工作也已经开始量化这类多 die GPU 的内部非均匀性。
来源：NVIDIA Developer Blog · Inside NVIDIA Blackwell Ultra ｜arXiv · Microbenchmarking NVIDIA's Blackwell Architecture

四、影响分析

① 对编程模型：CUDA 将出现"GPU 内 NUMA"语义

一旦 claim 3/20 所述的"由应用声明 localization"落地为公开 API，CUDA 开发者就要开始像写 CPU NUMA 代码那样思考 "这块 buffer 属于哪个 uGPU、这个 kernel 在哪个 uGPU 上跑"。 分析这会连带影响到所有把 GPU 当作均匀设备的上层框架： 显存分配器（PyTorch caching allocator、vLLM 的 KV Cache 池）、通信库（NCCL 的 buffer 放置）、 以及编译器的 tiling 策略，都需要引入"locality domain"这一维。

② 对 LLM / MoE 负载：最直接的受益点

  • 分析MoE 专家权重天然可按专家切分并绑定到某个 uGPU，配合 CTA 亲和，让每个 die 只读自己的专家权重——这正是专利"拆成两批相近工作"的理想实例。
  • 分析KV Cache 是 32MB 粒度友好的大块分配，且访问具备明确的 per-request 局部性，很适合本地化；同时它对末级缓存容量高度敏感，消除 LTC 双份副本收益明显。
  • 分析反面案例：需要全 GPU 带宽的大 GEMM / 集合通信收发缓冲应当保持交织模式。这正解释了为什么专利坚持"逐 64MB 块可混用"——真实负载必然是两种模式共存。

③ 对竞争格局：抬高了"多 die 单逻辑 GPU"的软件门槛

分析多 die 拼一颗大 GPU，硬件上是封装与互联的问题，但要真正跑出接近单 die 的效率， 必须解决"软件看不见的 NUMA"。本专利把这条路径上最便宜的一个解法（借 PTE 一位 + 复用 affinity mask）圈了起来。 对同样走 chiplet 路线的团队而言，这意味着要么绕开，要么在地址映射之外另找抓手。

④ 风险提示：这套机制会把性能悬崖交到应用手里

分析本地化模式下如果 affinity mask 与内存 locality 不匹配（内存钉在 uGPU0、CTA 跑在 uGPU1）， 性能会比全交织模式更差——交织至少保证"两边各摊一半"，而错配的本地化是"100% 远端"。 专利提到的"智能驱动自动选模式"正是为了缓解这一点。 启示：任何暴露此类语义的 API，都必须同时提供"归属查询 + 错配检测/告警"配套能力，否则用户必然踩坑。

一、可直接借鉴的五个设计要点

① 用"地址视图切换"代替"数据迁移"

这是本专利最值钱的思想：不动数据，只改解释数据落点的规则。 在自研加速器上，若已有多套 memory partition，完全可以在 MMU / 地址交织单元里预留第二套映射函数， 并用页表属性位选择——实现成本远低于任何形式的页迁移引擎。

② 用"对齐大块 + 二分"换取软件可推算性

本地化模式刻意不做 swizzle，就是为了让软件能自己算出地址归属。 这提示一条通用原则：凡是希望软件参与优化的硬件机制，其地址映射函数必须是软件可预测的闭式表达。 硬件里那些为了避免热点而做的哈希 / 打散，在需要暴露局部性的路径上必须可关闭。

③ 属性位与地址位的严格区分

把 localization bit 放在地址域里却当属性处理，并要求边界检查时剔除该位—— 这是一条容易被漏掉的实现细节，也是最容易产生安全隐患（越界检查被绕过）的地方。 自研 MMU 若采用同类技巧，必须在 RTL 与驱动两侧建立"属性位掩码"的单一真源。

④ 把翻译责任放在目标侧，为新特性留出扩展空间

FLA（目标侧翻译）天然支持本地化 peer 映射，而 GPA（源侧翻译）需要链路报文有空闲比特。 结论：scale-up 互联协议设计时应预留若干"语义扩展比特"，否则未来每加一个内存语义都要改协议版本。

⑤ 双模式并存 + 逐块混用，是增量落地的唯一现实路径

专利反复强调"重映射某块不影响相邻区段"、"不同块可用不同模式"。 这让特性可以从少数关键分配（如 KV Cache）开始灰度启用，而不必一次性切换整个显存布局—— 任何要在成熟软件栈上落地的内存新特性都应遵循这一约束。

二、规避设计思路（供研发参考）

分析 · 非法律意见 以下仅为基于公开权利要求文本的技术性讨论，实际方案必须结合最终授权的权利要求与专业 FTO 分析：

  • 避开"选择性"这一重心：claim 1/8/15 都以"selectively（选择性地）"为核心。若采用固定的、上电期确定且运行时不可切换的本地化映射，与"选择性限制"的距离更远，代价是失去弹性。
  • 避开"访问范围被限制到本地内存"：claim 15 要求"不访问第二 DRAM"。若实现为优先本地、容量不足时自动溢出到远端的软亲和策略（类似 CPU NUMA 的 preferred 而非 bind），则不构成封闭访问域。
  • 避开属性位的存放位置：claim 4/11 限定属性位在页表项中。改由独立的区间描述符表（range table / 段寄存器）或per-kernel 配置寄存器承载模式选择，可与该从属项区分。
  • 把决策上移到分配器而非地址映射硬件：不改地址映射函数，而是让驱动 / 固件在物理页选择阶段只从目标 uGPU 作为 home 的通道里挑页（保持单一交织函数，通过挑选物理页号实现亲和）。难点在于交织函数带 swizzle 时可选页集合稀疏。
  • 把亲和性下沉到互联 / 内存侧：由 fabric 或内存控制器侧做归属重定向，而非 GPU 内的地址映射器，同时不涉及"簇内耦合到 crossbar 的映射器"这一结构限定。

三、趋势展望

趋势一：GPU 内部 NUMA 从"隐藏"走向"公开"

路线非常清楚：MIG（硬分区）→ affinity mask（只管算）→ 本专利（算与数一起管、逐块可选）。 分析下一步很可能是把 locality domain 变成一等公民：设备属性可查询、分配可指定、 kernel launch 可绑定、profiler 可显示"跨域访问占比"。CPU 世界花了十几年走完的 NUMA 之路，GPU 会在两三代产品内压缩走完。

趋势二：die 数量继续增加，"两分法"会被推广为 N 分法

分析本专利的映射规则是"64MB 二分给两个 uGPU"。 一旦 die / uGPU 数量超过 2（4 die、8 die 封装），这套规则必然要扩展为 "对齐窗口大小 = N × 每域块大小、按窗口内序号取模映射"。 届时对齐单元会随 N 线性增大（例如 4 域 → 128MB 对齐）， 大页 / 大对齐带来的内碎片问题会成为新的工程矛盾——这是值得提前布局的专利空间。

趋势三：末级缓存的"单一 home"语义会被显式管理

分析专利把"消除 LTC 双份副本"列为核心收益。 沿着这条线往下走，自然会出现缓存归属（cache home）的显式控制： 让软件声明某段数据"只在某个 LTC 域内缓存"，从而把片上缓存当作可分配资源来编排。 这与 Hopper 引入的 L2 persisting / 访存策略窗口是同一趋势的不同侧面。

趋势四：编译器与运行时会接管"模式选择"

专利已经明确提到"智能驱动"变体。分析让应用手工声明亲和性在真实工程中难以推广， 最终形态更可能是：编译器分析访存模式 + 运行时按 profile 反馈自动切换， 应用层只保留"提示（hint）"级别的接口。这也意味着竞争的关键会从硬件机制转移到"自动决策质量"上。
