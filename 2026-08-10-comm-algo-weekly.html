NCCL Roadmap Aug-Oct 2026 (#2272) 持续更新

2026-08-07 更新

NCCL Aug-Oct 2026 Roadmap 持续更新，规划 NCCL 2.31 及后续版本：

  • NCCL 2.31 (开发中): Compute Fabric Transport、EFA GDA 支持、Cost-model 重构、Per-collective 可配置性、JIT 重编译、Host-side 统一、RAS 诊断Roadmap
    • 设计原理
    NCCL 2.31 设计原理
    核心问题：NCCL 当前存在多条 kernel 路径（legacy collective paths 和新的 Device API 路径），维护成本高且性能不一致。随着 Blackwell/Rubin 架构引入新硬件特性（CFT、symmetric memory），需要统一编程模型。
    设计原理：通过 Device API 统一所有 collective 路径，使 CFT (Compute-Communication Fusion) 通过标准化 API 暴露。Cost-model 重构基于更精确的拓扑感知和负载模型自动选择最优算法。RAS diagnostics 提供运行时健康检查，帮助大规模集群快速定位通信故障。
    适用场景：10K-100K+ GPU 大规模训练集群，需要统一 API 管理多种硬件拓扑（NVLink、NVSwitch、IB/RoCE）；需要低精度训练（MXFP8/MXFP4）的 MoE 模型。
  • 秋季 2026: Rubin 架构支持、统一 legacy kernels、Symmetric A2A kernel、MIG 支持、NCCL Notify
  • 未来规划: MXFP8/MXFP4/NVFP4 低精度、Rust bindings (nccl4rust)、Windows 支持、SM-initiated CE collectives

2026-08-04~07 | New PRs

  • Spilled Allocation 内存泄漏修复 (#2328) — 修复 allocateSpilled 中的内存泄漏PRIssue
    • 设计原理
    Spilled Allocation 内存泄漏修复设计原理
    核心问题：NCCL 在 communicator 初始化时可能将 buffer spill 到 host memory（当 GPU 内存不足时）。Issue #2324 报告 allocateSpilled 函数在分配路径中未正确释放已失败的分配，导致内存泄漏。
    设计原理：在 allocateSpilled 的错误路径中添加正确的清理逻辑，确保当后续分配失败时，之前成功分配的 spill buffer 被正确释放。使用 RAII 模式或显式 cleanup 标签（goto cleanup）来保证所有错误路径都执行释放。
    适用场景：长时间运行的训练作业中，communicator 反复创建/销毁时，内存泄漏会逐渐累积导致 OOM。修复后提升大规模集群的长期稳定性。
  • Profiler Proxy 初始化失败处理 (#2326) — 处理 profiler proxy 初始化失败的情况PR
  • GIN GDAKI Init Hang 修复 (#2318) — 避免 gin gdaki init 中的无限 hangPR
    • 设计原理
    GIN GDAKI Init Hang 修复设计原理
    核心问题：GIN (GPU-Initiated Network Interface) 的 GDAKI (GPU Direct Access Kernel Interface) 初始化过程中，在某些拓扑或负载条件下可能出现无限等待，导致 communicator 初始化 hang。
    设计原理：添加超时机制和错误恢复路径。当 GDAKI init 在预期时间内未完成时，触发 fallback 路径而非无限等待。同时修复竞争条件，确保所有 rank 的初始化顺序一致。
    适用场景：使用 GIN 后端的大规模 MoE 训练，特别是 NVSwitch + IB 混合拓扑下的初始化阶段。

关键 Issues: RoCEv2 死锁 + EP/M2N 仓库迁移

2026-08-06~09
  • RoCEv2 接收死锁 (#2334) — 4x GB10 + ConnectX-7 RoCEv2 上 tensor-parallel LLM 推理时，RDMA write 完成到已释放 slot 导致永久 freezeIssue
    • 设计原理
    RoCEv2 接收死锁设计原理
    核心问题：在 RoCEv2 网络上的 NCCL collectives 中，接收方处理已完成 RDMA write 的 completion 时，发现对应的 request slot 已被标记为"未使用"。这种 stale completion 处理导致同步状态损坏，进而永久死锁。
    设计原理：根本原因是 completion 处理与 request slot 回收之间的竞争条件。修复方向包括：1) 为 completion 添加 generation tag 以检测 stale completion；2) 在 slot 回收前确保所有 in-flight completions 已处理；3) 添加超时检测以从死锁中恢复。
    适用场景：GB10/GB200 + ConnectX-7 RoCEv2 环境上的 tensor-parallel 推理，特别是双 200G 链路配置。
  • NCCL EP & M2N 迁移至 nccl-extensions (#2308) — EP 和 M2N 原语从 contrib/ 迁移到独立仓库 NVIDIA/nccl-extensionsAnnouncement
    • 设计原理
    NCCL EP/M2N 仓库迁移设计原理
    核心问题：NCCL EP (Expert Parallelism) 和 M2N (mesh-to-mesh) 作为实验性贡献放在 NCCL 主仓库的 contrib/ 目录下，但它们的发布节奏、API 稳定性和 issue 跟踪需求与 NCCL 核心不同。
    设计原理：迁移到独立的 NVIDIA/nccl-extensions 仓库，允许独立的版本管理、issue 跟踪和开发节奏。这类似于 Linux kernel 中 staging drivers 移到独立仓库的模式。同时保持与 NCCL 核心 API 的兼容性。
    适用场景：MoE 训练框架开发者需要跟踪 EP 原语的最新进展；M2N 用户需要独立的 issue 跟踪和更快的修复周期。

本周 4 Merged + 5 Open: NVSHMEM 3.7 适配 + HybridEP 路由

2026-08-01~10 | PRs

DeepEP 本周 4 个 PR 已合并 + 5 个新 PR 开启：

  • NVSHMEM 3.7 适配 (#711) — 适配 NVSHMEM 3.7 API 变更PR
    • 设计原理
    NVSHMEM 3.7 适配设计原理
    核心问题：NVSHMEM 3.7.0 引入了 API 变更（如 C++17 强制要求、heap registration 重构、flush API 新增），DeepEP 的 V2 架构依赖 NVSHMEM 底层 API 进行 GPU-initiated 通信，需要适配这些变更。
    设计原理：更新 DeepEP 的 NVSHMEM 调用层以匹配 3.7 的新 API。包括：使用新的 heap registration backend、适配 transport capability view、更新 flush API 调用（nvshmemx_flush 用于 source-buffer 复用）。同时保持对 NVSHMEM 3.5.x/3.6.x 的向后兼容。
    适用场景：使用 NVSHMEM 3.7+ 的 MoE 训练环境，需要 DeepEP 与新版本 NVSHMEM 保持兼容。
  • HybridEP Dense Top-K 路由扫描 (#673) — 为 HybridEP 添加 dense top-k routing scan pathPR
    • 设计原理
    HybridEP Dense Top-K 路由扫描设计原理
    核心问题：HybridEP 需要支持 dense top-k 路由（每个 token 路由到 top-k 个 expert），但当前的 scan 路径仅支持 sparse/moe routing。Dense top-k 要求对所有 token 进行全量扫描以确定 top-k 选择，计算量和通信模式与 sparse routing 不同。
    设计原理：添加专用的 dense top-k scan kernel，利用 warp-level reduction 和 shared memory 进行高效 top-k 选择。对于 top-2 routing，每个 token 需要比较所有 expert 的 score 并选择最高的 2 个。kernel 使用 bitonic sort 或 radix select 算法在 GPU 上高效实现。
    适用场景：Mixtral 等使用 top-2 routing 的 MoE 模型训练，需要在 dispatch 前进行高效的 dense top-k 路由计算。
  • GIN Barrier System-Scope Release (#715) — 跨 NVLink/RDMA scaleup 时在 GIN barrier 前添加 system-scope releasePR
    • 设计原理
    GIN Barrier System-Scope Release 设计原理
    核心问题：当 DeepEP 的 scaleup 同时跨越 NVLink（节点内）和 RDMA（节点间）时，GIN barrier 的内存可见性需要 system-scope 保证。缺少 system-scope release 会导致跨节点的 barrier 信号在其他 GPU 上不可见。
    设计原理：在 GIN barrier 信号发送前添加 system-scope release fence（__threadfence_system），确保 barrier 信号对所有 GPU（包括不同节点上的）可见。这是 CUDA 内存模型中最强的可见性保证，对应 system-scope acquire 在接收端。
    适用场景：多节点 MoE 训练，NVLink 域跨越 2+ 节点（如 DGX SuperPOD 的 NVSwitch 互联），需要保证跨节点 barrier 的正确性。
  • Overflow Flag 零初始化 (#709) — 零初始化 overflow_flag 防止残留垃圾值PR

Devel 分支 35 Commits: Heap 重构 + Rust Bindings + Fortran CI

2026-07-15~28

NVSHMEM devel 分支 35 commits 聚焦三大方向：

  • Heap Registration 重构 (7 commits) — 引入 transport capability view、standalone heap handle table、heap registration backend、symmetric heaps 路由Commits
    • 设计原理
    Heap Registration 重构设计原理
    核心问题：NVSHMEM 3.7 之前的 heap 管理将注册逻辑分散在各个 transport 中，导致代码重复且难以扩展新的 transport 类型（如 GPUNetIO、libfabric）。每次添加新 transport 都需要修改核心 heap 管理代码。
    设计原理：引入独立的 heap registration backend，将 transport 相关的 heap 操作抽象为 capability view。每个 transport 声明自己支持的 heap 类型和操作（如 P2P、VMM、GDRCopy），heap 管理核心通过 backend 接口统一调度。standalone heap handle table 将句柄管理从 transport 解耦，支持跨 transport 的 heap 共享。
    适用场景：需要多种 transport 共存的异构集群（如 NVLink + IB + EFA），以及需要动态注册/注销 heap 的弹性训练场景。
  • Rust Bindings — 添加独立 NVSHMEM Rust bindings 贡献Commits
    • 设计原理
    NVSHMEM Rust Bindings 设计原理
    核心问题：随着 Rust 在系统编程中的普及（NCCL Roadmap 也列出了 nccl4rust），NVSHMEM 需要提供 Rust 语言绑定以支持 Rust 编写的高性能通信应用。
    设计原理：通过 Rust FFI (Foreign Function Interface) 封装 NVSHMEM 的 C API，提供 safe Rust wrapper。使用 Rust 的 ownership 和 lifetime 系统确保 symmetric memory 的安全使用，避免 use-after-free 和数据竞争。
    适用场景：Rust 编写的分布式推理服务、高性能计算应用，需要与 NVSHMEM 的 GPU-initiated 通信能力集成。
  • Fortran Bitcode CI — 添加 CUDA Fortran bitcode smoke testCommits
  • TMA Block Limit 运行时可配 — Make TMA block limit runtime configurableCommit
  • NVSHMEM4Py 增强 — 修复 peer-access 示例、添加 initialization 示例Commits

    NIXL EFA Hang 修复设计原理
    核心问题：NIXL 使用 libfabric 的 FI_MORE batching 机制将多个小消息合并为一次提交，减少内核调用开销。但在某些网络 provider（特别是 EFA）上，batch 未正确关闭导致跨节点传输 hang。
    设计原理：实现 per-rail flush 策略：每个 NIC rail 独立管理 FI_MORE batch，在 batch 关闭时确保该 rail 上所有 pending 操作被 flush。这保持了 batching 的吞吐优势，同时保证每个 rail 的 batch 正确关闭。
    适用场景：使用 AWS EFA 或类似 fabric 的跨节点训练，需要可靠的大批量小消息传输。

    NCCL2 Nonblocking Communicator 设计原理
    核心问题：PyTorch c10d 的 NCCL communicator 创建是阻塞操作，需要所有 rank 同步完成初始化。在弹性训练或动态 subgroup 创建场景中，阻塞初始化会导致性能瓶颈。
    设计原理：将 communicator 创建改为非阻塞模式：init 阶段只分配本地资源，实际的 NCCL communicator 在首次使用时 lazy-init。使用 split_from 语义支持 eager new_group 创建，允许部分 rank 先开始初始化。
    适用场景：弹性训练（rank 动态加入/离开）、MoE 训练中动态创建 expert group communicator。

    OneCCL 2022.1.0 GPU_RDMA 设计原理
    核心问题：OneCCL 的 point-to-point 操作之前只支持 CPU buffer，GPU 数据需要先拷贝到 CPU 再发送，增加了延迟和 CPU 开销。
    设计原理：添加 GPU_RDMA 支持，允许 GPU buffer 直接通过 RDMA 发送，绕过 CPU staging buffer。这利用 GPU Direct RDMA 技术，将 GPU 内存直接暴露给 NIC，减少一次 CPU-GPU 内存拷贝。
    适用场景：Intel GPU (Data Center GPU Max系列) 配合 Intel E810/E830 NIC 的 RDMA 环境。
