NCCL (NVIDIA Collective Communications Library)

Release 2026-08-11

NCCL v2.31.2-1: CFT 支持 Blackwell + Per-Collective 配置HOT

核心要点：引入 Compute Fabric Transport (CFT) 支持 Blackwell GPU，新增 Per-Collective 算法选择配置，GIN 后端增强（AWS-EFA GDA 支持），PAT 增强改善中小消息性能。
  • Compute Fabric Transport (CFT): 新增 CFT Host 和 Device API，管理窗口内存并执行 Put/Get/Red/NVLS 操作。需要 Blackwell GPU + CUDA Toolkit 13.3+。 官方文档 设计原理
    Compute Fabric Transport 设计原理
    核心问题：随着 Blackwell 架构引入新的 GPU 互联拓扑，传统 NCCL 传输层（如 NVLink、PCIe、网络）无法统一抽象 GPU 间的计算织物（Compute Fabric）。需要一种新的传输层来管理跨 GPU 的窗口内存，支持单边操作（Put/Get）和集合操作（Reduce/NVLS），同时充分利用 Blackwell 的硬件特性。
    设计原理：CFT 采用分层设计：Host 端负责窗口内存的分配和管理（通过 ncclCollConfig_t 配置），Device 端提供轻量级 API 直接执行 Put/Get/Red/NVLS 操作。CFT 利用 Blackwell 的硬件对称内存（Symmetric Memory）特性，允许 GPU 直接访问远端 GPU 的注册窗口，实现零拷贝单边通信。与传统的 NCCL 集合操作不同，CFT 支持 Per-Collective 粒度的算法选择和参数调优。
    适用场景：Blackwell GPU 集群上的大规模 LLM 训练（如 B200/GB200），需要高效利用 NVLink-C2C 和 NVLink 5.0 拓扑的场景。特别适合需要混合单边/集合通信模式的 MoE 模型训练。
  • Per-Collective 配置: 通过 ncclCollConfig_t 和 nccl*Config API 实现每个集合操作的独立算法选择、CTA/CGA 大小覆盖，以及 profiler 的 userTag 支持。 Release Notes 设计原理
    Per-Collective 配置设计原理
    核心问题：传统 NCCL 对所有同类型集合操作使用统一的全局配置（如算法、通道数、CTA 大小）。但在实际训练中，不同集合操作（如 AllReduce vs AllGather）的消息大小、拓扑敏感度差异巨大，统一配置无法为每个操作选择最优算法。
    设计原理：引入 ncclCollConfig_t 结构体，允许用户在发起每个集合操作时指定：(1) 算法选择（如 Ring、Tree、PAT）；(2) CTA/CGA 大小覆盖（控制 GPU SM 资源分配）；(3) userTag 用于 profiler 标识。NCCL 内部根据配置动态选择最优内核和调度策略，而不影响其他操作的默认行为。
    适用场景：大规模训练中需要精细调优特定集合操作性能的场景，如 AllGather 在大 batch 推理时的延迟优化，或 ReduceScatter 在 FSDP 训练中的带宽优化。
  • GIN 增强: AWS-EFA 团队贡献 GDA 后端（支持 Put/Signal/Flush），新增 per-DevComm GIN 后端选择、设备端超时、QP 使用优化、乱序交付(DDP)支持、GRH 支持及自动路径 MTU 发现。 Release Notes 设计原理
    GIN (GPU-Initiated Networking) 设计原理
    核心问题：传统网络通信需要 CPU 参与数据路径（Host-initiated），每个通信操作都需要 CPU 发出命令、等待完成，导致延迟高且占用 CPU 资源。在大规模 GPU 集群中，CPU 成为通信瓶颈。
    设计原理：GIN 允许 GPU 直接发起网络操作（GPU-Initiated），绕过 CPU 数据路径。GDA（GPUDirect Async）后端让 GPU kernel 直接通过 RDMA 发送/接收数据。AWS-EFA 团队贡献的实现支持 Put/Signal/Flush 三个原语，其中 Signal 用于轻量级通知机制。Per-DevComm 后端选择允许不同设备使用不同的 GIN 后端实现，增加了灵活性。QP（Queue Pair）使用优化通过 railed GIN 减少 InfiniBand 资源消耗。
    适用场景：大规模 GPU 集群（1000+ GPU）上的训练任务，特别是 AWS EFA 环境下的 RoCE 网络。适合需要低延迟、高吞吐的集合操作，以及需要减少 CPU 干预的 device-centric 通信模式。
  • PAT 增强: ReduceScatter/AllGather 使用分层内核（节点内 NVLS + 节点间 PAT），改善中小消息性能。默认禁用。 Release Notes 设计原理
    Parallel Aggregated Tree (PAT) 设计原理
    核心问题：传统的 Ring 算法在小/中等消息大小下延迟较高（需要 O(N) 步完成一圈），而 Tree 算法虽然延迟低但带宽利用率有限。对于 ReduceScatter 和 AllGather 这类操作，需要一种既能利用 NVLink 高带宽（节点内），又能高效跨节点聚合的算法。
    设计原理：PAT 采用分层策略：节点内使用 NVLS（NVLink Large-Scale）利用 NVLink 的高带宽（900 GB/s per GPU on Blackwell）进行快速数据交换；节点间使用 Parallel Aggregated Tree 拓扑，多个 Tree 并行执行以最大化网络带宽利用率。这种分层设计将节点内和节点间通信解耦，避免了跨节点瓶颈。目前默认禁用，因为 H100 平台上存在已知的性能回退问题。
    适用场景：多节点大规模训练（8+ 节点），特别是 ReduceScatter/AllGather 密集的工作负载（如 FSDP、MoE 路由）。在 Blackwell 平台上效果最佳（NVLS 硬件支持更完善）。

DeepEP (Expert-Parallel Communication Library)

V2 Release DeepSeek

DeepEP V2: 从 NVSHMEM 迁移到 NCCL GIN，性能提升 1.3xMAJOR

核心要点：完全重构 Expert Parallelism 模块，从 NVSHMEM 迁移到更轻量的 NCCL GIN 后端（header-only），实现 Fully JIT 编译，统一 ElasticBuffer 接口。性能提升最高 1.3x，SM 占用降低最高 4x。
  • 后端迁移: 从 NVSHMEM 迁移到 NCCL GIN 后端（header-only），复用现有 communicator，减少依赖。 GitHub 设计原理
    后端迁移设计原理
    核心问题：V1 基于 NVSHMEM 实现，NVSHMEM 作为完整的 PGAS（Partitioned Global Address Space）运行时，包含了大量 DeepEP 不需要的功能（如对称内存管理、信号量原语等），导致二进制体积大、编译复杂、SM 资源占用高。MoE 通信只需要高效的 All-to-All 和低延迟点对点传输。
    设计原理：NCCL GIN 后端是 header-only 的轻量级实现，直接复用 NCCL 已建立的 communicator 和网络连接，无需额外的初始化和资源管理。GIN 的 GPU-initiated 网络模型与 DeepEP 的 hook-based 通信-计算重叠策略天然契合。迁移后，DeepEP 可以直接使用 NCCL 的网络栈优化（如 EFA GDA、QP 复用等），同时减少了 SM 占用（从 24 降到 4-6）。
    适用场景：所有使用 DeepSeek-V3 架构的 MoE 训练场景，特别是需要最大化 GPU 计算资源利用率的大规模训练任务。
  • ElasticBuffer 统一接口: 将高吞吐和低延迟 API 统一到单一 ElasticBuffer 接口，新增 GEMM layout 支持。 GitHub 设计原理
    ElasticBuffer 设计原理
    核心问题：V1 中高吞吐（HT）和低延迟（LT）模式使用完全不同的 API 和缓冲区管理，用户需要根据场景手动切换，增加了使用复杂度。同时两种模式的缓冲区无法共享，导致内存浪费。
    设计原理：ElasticBuffer 将 HT 和 LT 模式抽象为统一的缓冲区接口，内部根据运行时参数（消息大小、网络拓扑、SM 可用性）动态选择最优传输路径。新增 GEMM layout 支持使得缓冲区可以直接与矩阵乘法操作对接，减少数据重排开销。弹性（Elastic）体现在缓冲区大小可以根据 EP 域大小（最高 EP2048）动态调整。
    适用场景：MoE 模型的训练和推理，特别是需要同时使用高吞吐（训练阶段 All-to-All）和低延迟（推理阶段 token dispatch）的混合场景。
  • 性能提升: 峰值性能提升 1.3x，SM 占用降低 4x。V3-like 训练 SM 使用从 24 降到 4-6。 GitHub 设计原理
    性能优化设计原理
    核心问题：V1 需要 24 个 SM 用于通信，严重挤占了计算可用的 SM 资源（Blackwell GPU 共有 192 个 SM）。在 MoE 训练中，通信和计算需要交替执行，通信占用过多 SM 会导致计算阶段性能下降。
    设计原理：V2 通过三个关键优化实现 SM 降低：(1) 利用 NCCL GIN 的 GPU-initiated 网络，通信操作由少量 SM 发起后自动完成，无需持续占用 SM 轮询完成状态；(2) 解析式确定 SM 和 QP 数量（不再需要 auto-tuning），避免过度分配；(3) 新增 0 SM Engram（通过 RDMA）和 0 SM CP（通过 Copy Engine）模式，部分操作完全不需要 SM 参与。最终将 SM 使用从 24 降到 4-6，释放了 18+ 个 SM 给计算使用。
    适用场景：所有 MoE 训练场景，特别是在 Blackwell GPU 上训练超大规模 MoE 模型（如 671B 参数），需要最大化计算吞吐量。
  • 实验性功能: 0 SM Engram (RDMA)、0 SM PP (RDMA)、0 SM CP (Copy Engine)。支持 EP 域最高 EP2048。 GitHub

论文 arXiv 2602.00509v2

PROBE: 基于 DeepEP 的 MoE 推理优化系统

核心要点：PROBE 使用 Continuous Lookahead Pipelining 优化 MoE 推理，基于 DeepEP 作为通信后端。Prefill 延迟降低 1.32x，解码吞吐提升 1.26x。
  • Gate-Initialized Lookahead Predictor: 克隆 router 层预测下一轮 expert 激活，高精度低开销。 设计原理
    Lookahead Predictor 设计原理
    核心问题：MoE 推理中，continuous batching 导致 expert 流行度快速变化，产生计算和网络的双重瓶颈。传统方法在当前轮次才知道 token 路由目标，无法提前准备数据传输。
    设计原理：通过克隆 MoE 层的 router（门控网络），在路由决策完成前就预测下一轮 token 将被分配到哪些 expert。预测器与主路由共享输入特征，但提前一个时间步执行，为数据传输提供"提前量"。
    适用场景：高动态负载的 MoE 推理服务，特别是 continuous batching 环境下 expert 流行度快速变化的场景。
  • Phase-Locked Co-Scheduling: 双轨执行模型，数据传输与计算重叠，避免带宽争用。 论文

Release 2026-06-11 (v3.7.0-0)

NVSHMEM 3.7.0: TMA 支持 + GPUNetIO 远程传输 + 浮点原子操作

核心要点：引入 TMA-backed NVLink 读写实现、GPUNetIO 远程传输（GPU 发起网络）、半/单/双精度浮点原子加操作，最低要求 C++17，许可证切换至 Apache-2.0。
  • TMA-backed NVLink: 通过 NVSHMEM_TMA_POLICY 设置启用 TMA 加速的全局/共享缓冲区读写。 Release Notes 设计原理
    TMA (Tensor Memory Accelerator) 设计原理
    核心问题：Blackwell 架构引入了 TMA 硬件单元，专门用于高效的数据搬运（global ↔ shared memory）。传统 NVSHMEM 的 NVLink 读写使用普通 load/store 指令，无法利用 TMA 的硬件加速能力，导致 NVLink 带宽利用率不足。
    设计原理：TMA-backed 实现将 NVSHMEM 的全局/共享缓冲区读写操作映射到 TMA 硬件指令。TMA 可以异步执行数据搬运，不占用 SM 计算资源，且支持 2D/3D tile 形状的数据传输模式。通过 NVSHMEM_TMA_POLICY 环境变量控制启用策略，允许用户根据工作负载选择最优的数据搬运方式。TMA 的异步特性使得通信和计算可以更好地重叠。
    适用场景：Blackwell GPU 上的 PGAS 编程模型，特别是需要大量全局/共享内存数据搬运的 HPC 应用（如流体力学模拟、分子动力学）。在 NVLink 密集型拓扑下效果最佳。
  • GPUNetIO 远程传输: GPU 发起的网络通信，集成 DOCA SDK，实现设备端直接网络访问。 Release Notes 设计原理
    GPUNetIO 远程传输设计原理
    核心问题：传统 NVSHMEM 的网络传输需要 CPU 参与（Host-initiated），GPU 数据需要先拷贝到 CPU 缓冲区，再由 CPU 发起网络操作。这增加了延迟和 CPU 开销，在大规模集群中成为瓶颈。
    设计原理：GPUNetIO 允许 GPU 直接发起网络操作（类似 GPU-initiated networking），通过集成 NVIDIA DOCA SDK，GPU kernel 可以直接操作网络接口卡（NIC）发送和接收数据。这消除了 CPU 数据路径，实现了真正的 device-centric 通信。远程传输模式意味着 GPU 可以直接读写远端节点的对等内存，无需远端 CPU 参与。
    适用场景：多节点 HPC 集群上的单边通信模式，如远程原子操作、远程 PUT/GET。特别适合需要低延迟跨节点通信的 PGAS 编程模型应用。
  • 浮点原子操作: 新增半精度(FP16)、单精度(FP32)、双精度(FP64)原子加操作，支持 peer-to-peer 和 proxy-backed 传输。 Release Notes
  • 其他更新: 新增 nvshmemx_flush 命令（源缓冲区复用）、实验性 endpoint handles、team-based bootstrapping、GID 路由（IB）、C++17 最低要求、Apache-2.0 许可证。 Changelog

torchcomms HOT Meta

torchcomms: Meta 开源新一代 PyTorch 通信 API + NCCLX 后端

核心要点：Meta 发布 torchcomms，旨在替代现有 c10d 接口。支持 NCCLX（Meta 扩展的 NCCL）、原生 RCCL 后端、Gloo。核心特性：扩展至 100K+ GPU、异构硬件支持、容错集合通信、单边通信（Window API）、设备中心集合操作。
  • NCCLX 后端: Meta 内部生产验证（Llama3/Llama4 训练），支持可扩展初始化、零拷贝/SM-free 通信、自定义集合算法、网络流量负载均衡、单边通信、GPU-resident 低延迟集合操作。 官方博客 设计原理
    NCCLX + CTran 设计原理
    核心问题：NCCL 的初始化模型（lazy init）在扩展到 100K+ GPU 时遇到瓶颈：communicator 创建延迟高、点对点操作并发语义有限、NVLink 缓冲区分配不够灵活。Meta 需要在超大规模训练中获得更好的资源控制和可预测性。
    设计原理：NCCLX 在 NCCL 基础上增加了 Meta 的优化：(1) 可扩展初始化（eager init），用户显式管理 communicator 资源；(2) 零拷贝/SM-free 通信，通过 custom transport (CTran) 实现直接 RDMA 和 NVLink 传输；(3) 自定义集合算法（针对 Meta 的网络拓扑优化）；(4) 网络流量负载均衡（动态 QP 调度）。CTran 包含独立的 NVLink、IB/RoCE 和 TCP 传输层，支持更底层的通信原语。
    适用场景：超大规模 LLM 训练（10K-100K+ GPU），需要精细控制通信资源分配的场景。也适用于需要容错能力的大规模训练任务。
  • Window API: 动态 put/get 操作，基于 RDMA/NVL 传输的零拷贝单边通信，支持原子信号机制。 官方博客 设计原理
    Window API 设计原理
    核心问题：传统集合操作（AllReduce/AllGather）需要所有参与者同步执行，但某些场景（如 checkpointing、异步梯度更新、RL 中的参数服务器模式）只需要单边发起的 put/get 操作，不需要对端同步参与。
    设计原理：Window API 允许用户跨多个 rank 创建共享内存窗口（GPU 或 CPU 内存），窗口创建后自动注册到底层 RDMA/NVL 传输。用户通过 Put/Get API 直接读写远端窗口内存，实现零拷贝单边通信。原子信号机制用于异步通知，避免轮询开销。这与 NVSHMEM 的 PGAS 模型类似，但集成在 PyTorch 生态中。
    适用场景：分布式 checkpointing、异步梯度聚合、强化学习中的参数服务器模式、任何需要单边通信的异步工作负载。
  • 容错后端: 基于 CTran 构建，提供故障检测、超时、错误恢复和安全重配置。支持容错 HSDP 和 Streaming DiLoCo。 官方博客

    SGL Datatype 设计原理
    核心问题：传统 RDMA PUT 操作要求数据在内存中连续存放，但实际应用中数据经常分散在多个不连续的内存区域（如 struct 中的多个字段、非连续 tensor 的多个 slice）。用户需要先拷贝到连续缓冲区再发送，增加了延迟和内存开销。
    设计原理：SGL（Scatter-Gather List）允许用户在一次 PUT 操作中指定多个不连续的内存段（地址+长度对），UCX 底层自动将这些分散的数据打包成 RDMA 操作。非阻塞（non-blocking）语义意味着发起 PUT 后立即可继续执行计算，无需等待传输完成。UCX 内部通过 IB 的 SGE（Scatter-Gather Entry）硬件特性实现零拷贝聚合发送。
    适用场景：非连续 tensor 的分布式训练、struct 数据的远程更新、任何需要发送分散内存数据的场景。

    GPUDirect Async (GDA) 设计原理
    核心问题：AMD GPU 的通信传统上需要 CPU 参与数据路径（Host-initiated），GPU 数据先拷贝到主机内存，再由 CPU 通过 RCCL/rocSHMEM 发起网络操作。这在大规模集群中导致高延迟和 CPU 瓶颈。
    设计原理：GDA 后端允许 AMD GPU（特别是 MI300X/MI350 系列）直接通过 RDMA 网卡（RNIC）发送和接收数据。GPU kernel 可以直接将数据写入 RDMA 发送缓冲区并发起传输，无需 CPU 介入。这通过 AMD 的 ROCm RDMA 驱动和 rocSHMEM 的 device-initiated 路径实现。节点内通过 NVLink-like 互联（Infinity Fabric），节点间通过 RDMA/RoCE。
    适用场景：AMD MI300X/MI350 集群上的大规模训练，需要低延迟跨节点通信的场景。与 NCCL 的 GIN/GDA 功能对标。

核心要点：NVIDIA 开源 NIXL（NVIDIA Inference Xfer Library），专为 disaggregated inference 设计。支持 RDMA、GPUDirect Storage、NVMe、S3 等多种后端，默认使用 UCX。提供 NIXLBench 和 KVBench 基准测试工具。

    NIXL 架构设计原理
    核心问题：Disaggregated inference 将 LLM 推理的 prefill（prompt 处理）和 decode（token 生成）阶段分离到不同的 GPU 上。这需要高效的 KV Cache 迁移、权重传输和中间结果交换，但现有通信库（NCCL/NVSHMEM）主要面向训练集合通信优化，不支持推理场景的多样化传输需求（GPU 内存 ↔ 存储 ↔ 云存储）。
    设计原理：NIXL 采用 conductor + transfer agent 架构：Conductor 负责调度任务，Transfer Agent 执行实际数据传输。Agent 内部使用 Memory Section 管理本地内存分配，Metadata Handler 管理远端节点信息。用户通过 descriptors 描述数据位置（GPU 内存、CPU 内存、NVMe、S3 等），NIXL 自动选择最优传输路径。异步执行和零拷贝设计确保通信不阻塞推理计算。
    适用场景：Disaggregated LLM inference、KV Cache 跨节点迁移、弹性推理扩展、checkpoint 到对象存储的异步写入。与 NCCL（训练集合通信）和 NVSHMEM（HPC 单边通信）形成互补。
  • 基准测试工具: NIXLBench（框架无关的吞吐/延迟测试）和 KVBench（LLM KV Cache 追踪）。 GitHub

本周观察

通信库领域正在经历从"训练专用"到"全栈覆盖"的范式转变。NVIDIA 通过 NCCL（训练）+ NIXL（推理）+ NVSHMEM（HPC）构建了完整的通信栈护城河，而 Meta 的 torchcomms 则试图在 PyTorch 生态中建立统一的通信抽象层，直接挑战 NCCL 作为唯一后端的地位。

DeepEP V2 从 NVSHMEM 迁移到 NCCL GIN 是一个值得关注的信号——它表明在 MoE 通信这个细分领域，NCCL 的网络栈正在成为事实标准，即使是 DeepSeek 这样的非 NVIDIA 生态玩家也在向 NCCL 靠拢。与此同时，torchcomms 的 NCCLX 后端（Meta 内部扩展的 NCCL）支撑了 Llama3/Llama4 的 100K+ GPU 训练，证明 NCCL 生态的扩展性仍有巨大潜力。

竞争格局的核心矛盾在于：NVIDIA 希望通信栈垂直整合（NCCL+NVSHMEM+NIXL 全自研），而开源社区（Meta/AMD/UCX）则倾向于水平分层（统一抽象层 + 可替换后端）。torchcomms 的出现可能成为后者的关键转折点。
