615.71.10 默认切换为 CDMM 内存管理模式 IMPORTANT

615.71.10 Coherent Driver-Based Memory Management
重大变更: 615.71.10 将默认内存管理模式从 NUMA node 方式切换为 Coherent Driver-Based Memory Management (CDMM)。驱动现在直接管理 GPU 内存，不再通过 OS 的 NUMA 节点暴露。580.196.07 同步引入 CDMM 用于 GB200 配置。

NVLink-C2C 相关性: CDMM 与 NVLink-C2C 的 CPU-GPU 统一内存架构理念一致。通过驱动层直接管理内存一致性，减少了 CPU-GPU 之间的数据拷贝和一致性协议开销。这是 NVLink-C2C 在软件栈层面的重要配套变更。

UVM 参数: 可通过 uvm_disable_sam_migration=false 控制 UVM 模块的 SAM 迁移行为。

来源: 615.71.10 Release Notes | 580.196.07 Release Notes

PR #1483: Fix VA space bookkeeping corruption on partial unmaps PR NEW

2026-10-24 Open | 影响 4GB/8GB GPU
修复内容: 修复内存压力下的 VA 空间记账损坏。三层映射追踪机制 (页表 gpu_vaspace、DMA 映射列表、intermap) 在部分 unmap 时出现不一致，导致 gpu_vaspace.c:4586 断言失败和桌面/游戏卡顿数秒。

根因分析: dmaFreeMapping_GM107() 按页大小对齐失效范围，而 virtmemUnmapMemoryDma() 按客户端请求的精确字节范围分割。当部分 unmap 不覆盖完整映射页时，VA 被释放但 DMA 映射列表仍声称拥有该页。

关键代码路径:

  • gpu_vaspace.c:4586 — _gvaspaceMappingRemove() 断言
  • dmaFreeMapping_GM107() — 错误路径调用 vaspaceFree
  • intermapRegisterDmaMapping() — 重叠页对齐键拒绝
来源: GitHub PR #1483

Issue #1499 + PR #1500: Blackwell Locality-Domain 分配开销异常 BUG FIX NEW

B200 / B300 CUDA 13.4 Locality Domain 特性
问题描述: 在 B200 和 B300 上，使用 CUDA 13.4 新发布的 Locality Domain 特性的 VMM 分配比原生分配更慢，当 Create Size 超过 32 MiB 时延迟急剧增加 (B300 上 Create 延迟达原生的 16.33 倍)。

根因 (PR #1500): _kbusUpdateStaticBar1VAMapping_TU102() 在 kern_bus_tu102.c 中更新静态 BAR1 页表。LD 分配需要不同的映射属性，即使小的连续分配也需要: (1) 页表更新调用 (2) 内存屏障/刷新 (3) TLB 失效。超过 32 MiB 时 PMA 无法返回物理连续范围，导致多次更新序列。

修复方案: PR #1500 提出合并静态 BAR1 更新，减少重复的页表写入和 TLB 失效操作。

来源: Issue #1499 | PR #1500

mmuWalkUnmap 失败 → UVM fatal error 0x60 (RTX 5090) BUG

Issue #1342 Open | 本周活跃更新
问题描述: RTX 5090 在 PyTorch LLM 推理 (KV-cache 分配/释放) 期间触发 mmuWalkUnmap 失败，级联为 TLB 失效 → GPU lost from the bus → UVM fatal error 0x60。需完全重启恢复。

错误链:

  • mmuWalkUnmap: Failed to unmap VA Range (0x00000040)
  • kgmmuInvalidateTlb_GM107: TLB invalidation failed
  • GPU lost from the bus [NV_ERR_GPU_IS_LOST]
  • uvm encountered global fatal error 0x60

关键代码路径: mmuWalkUnmap → kgmmuInvalidateTlb_GM107 → nvGpuOpsReportFatalError

来源: GitHub Issue #1342

615.71.10: 修复 TMA multicast 导致的内存系统挂起 BUG FIX

615.71.10 影响多 GPU NVLink 系统
修复内容: 修复内核使用 TMA (Tensor Memory Accelerator) multicast 到多个 CTA 时可能导致内存系统挂起的罕见问题。主要影响 Blackwell 架构的多 GPU NVLink 系统 (HGX B300, HGX H100 等)。

MMU 相关性: TMA 通过内存描述符访问 GPU 内存，multicast 模式下的挂起表明内存管理单元在处理多 CTA 并发访问时存在边界条件。此外，Blackwell GPU 上使用特定 tensor map 编码的应用可能遇到 MMU fault (Xid 13)。

趋势展望

短期趋势 (1-4 周)

620.xx 分支将整合 CXL 和 NVLink 修复

上周 PR #1438 和 #1435 的等效修复将在 620.xx 中发布，解决 CXL 编译和结构体字段问题。预计也将包含本周 #1483 (VA 空间) 的修复。

Xid 79 问题需要 NVIDIA 关注

本周 #1495 和持续的 #1151 表明 Blackwell 架构的 PCIe/NVLink 稳定性是开源驱动面临的最紧迫问题。AER RxErr 突发暗示可能是硬件层或固件层问题。

ARM64 页大小兼容性改善

PR #1480 (16K) 和 #1481 (64K DMA) 表明社区正在积极解决 ARM64 平台上不同页大小的兼容性问题，这对 Grace CPU 平台尤为重要。

中期趋势 (1-3 月)

CDMM 成为默认内存管理模式

615.71.10 和 580.196.07 均引入 CDMM 作为默认模式。这将改变 GPU 内存的管理方式，减少 NUMA 节点暴露，与 NVLink-C2C 的统一内存架构方向一致。

NVLink Fusion 生态加速

Marvell、D-Matrix、MediaTek 的加入表明 NVLink Fusion 正在成为开放互联标准。开源驱动需要支持更多第三方设备的 NVLink 拓扑识别和管理。

Vera Rubin 平台驱动准备

NVLink 6 (3.6 TB/s) 和 Rubin GPU (336B 晶体管) 将在 2026-2027 年量产。开源驱动需要提前准备 NVLink 6 Switch 和 NVLink-C2C 的支持代码。

核心洞察

1. 四版本同周发布彰显 NVIDIA 开源驱动投入力度

本周 4 个新发布横跨 3 个分支 (595.x, 615.x, 580.x)，加上一个 Vulkan Beta 预发布。580.196.07 包含 110 个文件变更，595.44.16 包含 98 个文件变更。NVLink、NVSwitch 和 GMMU 的代码变更在多个分支同步进行，表明 NVIDIA 正在积极将内部修复回溯到开源驱动。

2. Blackwell 架构的 PCIe 稳定性成为最大隐患

Xid 79 "fallen off the bus" 在 RTX 5090 (#1495) 和 RTX 5080 (#1151) 上集中爆发，伴随 AER RxErr 物理层错误。这些问题在开源驱动中独有 (Blackwell 无专有驱动可选)，且可在空闲状态下触发，严重影响数据中心推理服务器的可靠性。

3. 内存管理子系统面临系统性审查需求

本周的 MMU/UVM 问题覆盖 VA 空间记账 (#1483)、mmuWalkUnmap 失败 (#1342)、Blackwell LD 分配开销 (#1499)、ARM64 页大小兼容 (#1480/#1481)、挂起时内存分配失败 (#1309) 等多个维度。加上 615.71.10 的 TMA multicast 内存挂起修复，表明需要系统性的内存管理代码审查。

4. NVLink Fusion 正在重塑 GPU 互联生态格局

MediaTek 获得 35 亿美元投资整合 NVLink Fusion，D-Matrix 的 Raptor 推理引擎 (4nm, 100TB/s) 加入生态，Marvell 的互联技术整合 — 这些发展表明 NVLink 正从 NVIDIA 专有技术演变为开放互联标准。开源驱动中的 nvlink_caps.c 新增能力探测代码正是为支持更复杂的多厂商 NVLink 拓扑做准备。
