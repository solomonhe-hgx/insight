Issue #1504: RTX 5070 Mobile (GB206M) Xid 79 — D3cold 恢复时 NVLink/PCIe 总线断开 BUG NEW

2026-10-30 Blackwell Mobile / 615.78.08
问题描述: 启用动态电源管理 (NVreg_DynamicPowerManagement=0x02) 后，RTX 5070 Mobile 从 D3cold 深度休眠恢复时触发 Xid 79 "GPU has fallen off the bus"，伴随 KBIF BAR 防火墙超时。禁用动态电源管理 (0x00) 可恢复正常。

错误序列:

  • Unable to change power state from D3cold to D0, device inaccessible
  • kbifPollBarFirewallDisengage_GB202: Timeout polling CFG BAR firewall disengage
  • Xid (PCI:0000:01:00): 79, GPU has fallen off the bus
  • 后续触发 Xid 143 和 Xid 154 (FSP 微码超时)

NVLink 相关性: Xid 79 通常与 GPU 互联 (NVLink/PCIe) 物理层稳定性相关。这是 Blackwell 架构在开源驱动中反复出现的最严重问题之一，影响数据中心和移动平台的可靠性。

NVLink C2C 模块更新

Vera Rubin C2C 1.8 TB/s 规格确认 / C2CServe 论文发表

Vera Rubin 平台 NVLink-C2C 规格确认 OFFICIAL

2026 GTC 1.8 TB/s coherent / 统一地址空间
核心规格: NVLink-C2C 在 Vera Rubin 平台提供 1.8 TB/s 一致性带宽，连接 Vera CPU (88 Olympus 核心, 1.5TB LPDDR5X) 与 Rubin GPU (224 SMs, 288GB HBM4)。CPU 与 GPU 共享统一地址空间，对操作系统和上层软件透明。

平台参数:

  • Vera CPU: 88 NVIDIA Olympus 核心 (Arm v9.2), 176 SMT 线程, 2MB L2/核心, 164MB 统一 L3
  • Rubin GPU: 224 SMs, 第 5 代 Tensor Core, 336B 晶体管 (双 die), 288GB HBM4, 22 TB/s
  • C2C 带宽: 1.8 TB/s 一致性互联, 统一虚拟地址空间
  • CPU 内存: 最高 1.5TB LPDDR5X, 1.2 TB/s 带宽
来源: NVIDIA Blog: Vera Rubin Platform | NVLink-C2C 官方页面

C2CServe: 面向 Serverless 推理的 C2C 共享机制 RESEARCH

~900 GB/s C2C link / HybridGEMM / 多租户隔离
研究亮点: C2CServe 论文展示了通过 NVLink-C2C 实现约 900 GB/s 的 serverless 推理共享链路。针对多租户干扰问题，提出 HybridGEMM 内核级缓解方案，在共享 C2C 链路上实现隔离的性能保障。

开源驱动影响: 当前 open-gpu-kernel-modules 仓库中无独立的 C2C 源文件 (无 "c2c" 命名文件)。NVLink-C2C 支持可能通过现有 NVLink 代码路径处理，或尚未在开源驱动中显式实现。随着 Vera Rubin 平台量产，预计开源驱动将新增 C2C 专用模块。

MMU/UVM 模块更新

本周 5 个 MMU 相关 Issue/PR + BAR1 性能突破

PR #1500: BAR1 静态映射合并优化 — 1 GiB 分配 9.14x 加速 PR PERF

2026-10-27 kern_bus / BAR1 / TLB invalidate / B200 验证
核心优化: _kbusUpdateStaticBar1VAMapping_TU102() 函数在处理 >32 MiB 局部性分配时，原先逐页 (2 MiB) 同步 TLB invalidation，1 GiB 需 512 次 HAL 调用。新方案合并物理连续页，延迟 TLB invalidation 至循环结束后单次执行。

技术细节:

  • 文件: src/nvidia/src/kernel/gpu/bus/arch/turing/kern_bus_tu102.c
  • 通过检查实际物理地址 (而非逻辑偏移) 分组合并连续页
  • 循环内使用 DMA_DEFER_TLB_INVALIDATE 延迟同步
  • 循环后单次 PTE_DOWNGRADE 刷新 + TLB invalidation
  • 释放路径同样应用批量合并策略

性能数据 (B200 GPU):

  • 1 GiB 创建: 7175 μs → 785 μs (9.14x 加速)
  • 1 GiB 释放: ~5x 加速
  • 小分配 (<32 MiB) 性能无影响
来源: PR #1500 | 关联 Issue #1499

Issue #1513: Chromium GPU 映射耗尽 BAR1 VA 空间导致系统锁死 BUG NEW

2026-11-01 RTX 3060 / 615.78.08 / Arch Linux / Kernel 7.2.8
问题描述: Chromium 浏览器的 GPU 加速渲染耗尽 BAR1 (256 MiB) 的虚拟地址空间。dmaAllocMapping_GM107 无法分配 VA 空间后，图形通道锁死而非优雅降级，导致显示 modeset 无法提交，系统完全冻结，只能物理重启。

错误序列:

  • NVRM: dmaAllocMapping_GM107: can't alloc VA space for mapping
  • Assertion failed: Out of memory [NV_ERR_NO_MEMORY]
  • [drm] Failed to apply atomic modeset. Error code: -11
  • RC watchdog: GPU is probably locked!

Issue #1516: nvidia-drm 原子提交触发 OOM Killer (order-3 kzalloc 碎片化) BUG NEW

2026-11-02 RTX 3070 Ti / 615.78.08 / Fedora 44 / Kernel 7.2.13 / Wayland
问题描述: nv_drm_atomic_state_alloc() 在每帧渲染时请求 order-3 (32 KiB) 物理连续内存。在内存碎片化场景下 (即使有 ~1.9 GB 空闲)，触发 PAGE_ALLOC_COSTLY_ORDER 重试，最终激活全局 OOM killer 终止无关应用。

建议修复:

  • 使用 kvzalloc() 替代 kzalloc()，允许虚拟内存回退
  • 或预分配 per-device 状态结构，避免热路径高阶请求
来源: Issue #1516

Issue #1502: RTX PRO 6000 Blackwell 首次 CUDA 上下文触发 NV_ERR_NO_MEMORY BUG

2026-10-29 RTX PRO 6000 Blackwell / 580.178.04 / 97887 MiB VRAM

核心洞察

1. 本周无新发布但社区活跃度不减 — 20 个 Issue/PR 聚焦内存与稳定性

虽然 GitHub main 分支本周无新 commit (上次 Oct 7)，但社区提交了 10 个 Issue 和 10 个 PR。问题集中在 MMU/UVM 内存管理 (#1513 VA 空间耗尽, #1516 OOM, #1502 NV_ERR_NO_MEMORY, #1499 BAR1 性能) 和 Blackwell 稳定性 (#1504 Xid 79, #1515 GSP RPC 超时)。PR #1500 (BAR1 合并优化, 9.14x 加速) 是本周最重要的代码贡献，直接解决 #1499 的性能问题。

2. Blackwell 架构的 PCIe/电源稳定性仍是开源驱动最大隐患

本周 #1504 (RTX 5070 Mobile D3cold 恢复触发 Xid 79) 和 #1515 (GB10 GSP RPC 超时导致内核 Oops) 表明 Blackwell 家族在开源驱动中的电源管理和硬件初始化路径仍需大量稳定化工作。这些问题在 Blackwell 上独有 (无专有驱动可选)，且可在空闲或日常使用中触发，严重影响数据中心推理服务器和移动工作站的可靠性。

3. 内存管理子系统面临系统性审查 — 从碎片化到性能优化

本周的 MMU/UVM 问题覆盖多个维度: VA 空间记账 (#1513, BAR1 耗尽致系统锁死)、order-3 碎片化 (#1516, OOM killer 误触发)、大块页分配策略 (#1502, NV_ERR_NO_MEMORY 日志误报)、Locality Domain 性能 (#1499, 49x 回退)。PR #1500 的 BAR1 合并优化是首个针对性修复，但 #1516 建议的 kvzalloc() 回退和 CDMM 默认模式切换表明需要更系统性的内存管理代码审查。

4. 完全开源转型标志 NVIDIA 驱动生态新纪元

NVIDIA 论坛确认 615 分支起不再提供专有模块包，Arch Linux 和 Ubuntu 已通过官方仓库分发 615.78.08。这标志着 NVIDIA 向完全开源驱动的重大转变。然而，kernel taint 标志仍是社区摩擦点。随着开源驱动成为唯一选项，社区 PR (如 #1500 BAR1 优化, #1518 位扫描加速) 的质量和数量将成为生态健康的关键指标。
