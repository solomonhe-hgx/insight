620.70.06 — R620 新分支首发开源版本 (Nov 5)

自 615.78.08 之后 main 分支第一个 commit e6a2e015，NVIDIA 发布 R620 分支首个生产驱动 620.70.06，替换 R615 成为当前生产分支。GitHub Release 与 NVIDIA 驱动页同步上线，开源代码一次引入 300 个文件变更。

来源: GitHub Release 620.70.06 | NVIDIA 驱动页 283867

NVLink 相关代码级变更

  • src/common/nvlink/interface/nvlink.h: 新增 NVLINK_DEVICE_VERSION_60 (0x9) — NVLink 6 (Rubin 代) 设备版本号枚举正式进入开源驱动，标志着 NVL6 拓扑支持开始落地。
  • src/common/nvlink/kernel/nvlink/core/nvlink_discovery.c: NVL6 强制拓扑发现 — 当存在未连接端点 (notConnectedEndpoints > 0) 时自动触发 bForceDiscovery，并在强制发现时复位 packet_injection_retries 计数，解决 NVL6 AN0 包注入重试耗尽导致链路枚举失败的问题。
  • src/common/nvlink/inband/interface/nvlink_inband_msg.h: Multicast 团队协议 v2 — 请求结构新增 numUnitMin/numUnitMax (资源单元数协商)，响应新增 numUnitAllocated，让 Fabric Manager 可以按单元粒度分配 multicast slot，替代旧的 8 字节保留字段；宏改名 NVLINK_INBAND_MAX_NUM_HSHUB/NVLMUX。
  • src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080nvlink.h: 新增 NVLE (NVLink Encryption) 字段 — bNvleSelectiveEncryptionEnabled (选择性加密) 与 bNvleModeReady (加密就绪状态)；端口事件新增 timeToLinkUpMs (NVL6+ 链路训练耗时, ms)，链路诊断能力增强。
  • kernel-open/nvidia/nvlink_caps.c/.h (+26 行): 新增 nvlink_cap_validate() — 验证 fabric management capability fd 是否仍然有效，配合 NVSwitch fabric manager 状态检查 (见 NVSwitch 页)。

版本要点 (官方渠道)

  • Linux 驱动发布日 2026-11-04 (Windows 621.14 同步)；数据中心版本说明同步上线。
  • Wayland 高帧率基准下 explicit sync 性能改进；修复 595 系列引入的《刺客信条：影》Vulkan device lost 挂起、FF7 Rebirth 崩溃。

  • 数据中心版修复: Blackwell B40 GPU attestation 失败、SIGINT 终止后 GPU 利用率卡 100% (FECS ucode 保存序列末尾 context reset)。

fabric-management capability 生命周期加固 (linux_nvswitch.c + nvlink_caps.c)

NVSwitch 内核接口围绕 fabric manager capability fd 新增多重防护：nvswitch_os_acquire_fabric_mgmt_cap() 现在拒绝重复获取 (-NVL_ERR_STATE_IN_USE)，nvswitch_os_is_fabric_manager() 通过新的 nvlink_cap_validate() 实时验证 fd 有效性，防止使用已被释放的 capability 判定 fabric manager 身份。

来源: Compare 615.78.08...620.70.06

代码级细节

  • kernel-open/nvidia/linux_nvswitch.c (18/-10): nvswitch_device_release 在移除 client events 时新增 device_mutex 持锁，修复与设备状态变更的竞态；capability_fds.fabric_mgmt > 0 判断改为 >= 0，fd 0 不再泄漏 (fd 0 是合法的 dup 结果)。
  • nvswitch_os_acquire_fabric_mgmt_cap: 若 fabric_mgmt >= 0 直接返回 -NVL_ERR_STATE_IN_USE — 防止多次 acquire 导致旧 fd 泄漏。
  • nvswitch_os_is_fabric_manager: 新增 nvlink_cap_validate() 调用，fd 失效时返回 0 — 修复"fabric manager 释放 capability 后仍被误判为有效"的安全窗口。
  • nvswitch_os_get_platform_time: 从 ktime_get_raw_ts64 + timespec64_to_ns 简化为直接 nv_ktime_get_raw_ns()，平台时间戳路径统一。

MMU/UVM 模块更新

620.70.06 是 UVM 的重量级版本：prefetch 故障处理、HMM 重构、Blackwell FAULTED 通道清除、ATS PTE 修复与 CC 模式矩阵化；PR #1532 将 VA 映射修复移植到 620

RELEASE 620FIX

可重放故障处理：prefetch 故障不再误标记为致命 — 修复随机应用崩溃

kernel-open/nvidia-uvm/uvm_gpu_replayable_faults.c (+113/-25): fetch_fault_buffer_entries() 中 is_fatal 判定新增 && fault_access_type != PREFETCH 条件。官方注释直接说明动机："prefetch 故障无法被 cancel，将其标记为致命会导致随机应用崩溃" (pushing a cancel … can lead to random application crashes)。

来源: Compare 615.78.08...620.70.06

详细技术方案

  • 背景: 某些硬件单元不支持 prefetch，或 HW/SW 仅在真实访问时解决缺页，此时 prefetch 类型的 fault_type 仍可能达到 UVM_FAULT_TYPE_FATAL 阈值。
  • 修复: prefetch 故障一律不置 is_fatal；真实访问若确需映射，仍会触发致命错误正常终止应用。
  • 例外保留: UNSUPPORTED_APERTURE / CC_VIOLATION / REGION_VIOLATION / POISONED / WORK_CREATION 五类即使 prefetch 也仅 UVM_ERR_PRINT_ALWAYS_RL 记录 (可能指示 PTE 损坏等深层问题)，不再升级为应用终止。
  • 同文件另有 100+ 行 service 路径改进，配合 uvm_gpu_non_replayable_faults.c (+51/-27) 的 ATS PTE 修复 (见下卡)。
RELEASE 620

HMM (Heterogeneous Memory Management) 大规模重构 + ATS PTE 修复框架

kernel-open/nvidia-uvm/uvm_hmm.c (+206/-25) 与 uvm_hmm.h (+113/-1) 为本次 UVM 最大单项变更。新增 hmm_range_fault_for_locked_block() 封装 (锁释放→hmm_range_fault→重新加锁的契约化路径)；uvm_gpu.h 新增 ats_pte_fixup_mask / ats_pte_write_mask 两个页掩码，处理 SMMU/ATS 场景下 CPU PTE 已存在但权限/AF 位需 handle_mm_fault() 修复的情况。

来源: Compare 615.78.08...620.70.06

代码级分析

  • hmm_range_fault_for_locked_block(): 将 mmu_interval_read_begin() 会等待并行失效回调、故不能持有 va_block 锁的约束显式封装，消除散落的解锁/加锁对。
  • 边界修正: uvm_hmm_unregister_gpu() 的 PFN 循环从 <= 改为 < (修复 devmem_end 越界一页)；uvm_hmm_va_block_reclaim() 新增 PAGE_ALIGNED(start/end+1) 断言。
  • ATS PTE 修复: ats_pte_fixup_mask 覆盖 access-flag fault 与 DBM=0 软件脏位追踪场景 (SMMU 无法更新 CPU PTE)；ats_pte_write_mask 覆盖 CoW 等写权限缺页，需在释放 va_block 锁后调用 hmm_range_fault()。该路径对 Grace (SMMU) 类 C2C 平台尤为重要。
  • 掩码初始化防串扰: service_managed_fault_in_block_locked() 每次故障处理前 uvm_page_mask_zero() 清零 ats 掩码，避免上次故障残留。
RELEASE 620

Blackwell 通道 FAULTED 位清除 HAL + 工作提交 token 活性读取

新增 kernel-open/nvidia-uvm/hwref/blackwell/gb100/dev_runlist.h (CHRAM 通道 RAM 寄存器定义, +87 行)；uvm_blackwell_host.c (+53) 实现 uvm_hal_blackwell_host_clear_faulted_channel_register() — Blackwell 起虚拟化 runlist ID，token 不再变化，因此可回退到直接寄存器清除路径。uvm_channel.h 新增 uvm_channel_read_work_submit_token(): 每次写 doorbell 前从 notifier page 的活性指针重读 token (应对 runlist 重绑 / SR-IOV vChId 重映射 / 热迁移)。

来源: Compare 615.78.08...620.70.06

  • CHRAM 定义含 PBDMA_FAULTED / ENG_FAULTED 置位与清除位段，HAL 按故障来源 (MMU_ENGINE_TYPE_HOST vs CE) 选择对应复位值，自旋等待 FAULTED 位置位后再写清除 (避免与中断通知竞态)。

620.70.06 UVM 目录共 37 个文件变更。除上述重点外还包括 uvm_channel.c/.h (token 读取辅助)、uvm_migrate*.c、uvm_pmm_gpu.c、uvm_rubin_fault_buffer.c (Rubin 故障缓冲调整)、uvm_turing_ce.c (-19 清理) 等架构层适配。

来源: Compare 615.78.08...620.70.06

  • src/common/sdk/nvidia/inc/ctrl/ctrl208f/ctrl208fmmu.h: 新增 NV208F_CTRL_CMD_MMU_GET_NUM_HSHUBMMU_L1TLBS_FOR_SUBLOCATION — 按子位置查询 HSHUBMMU 的 ECC-capable L1TLB 数量，MMU 诊断粒度细化。
  • kernel-open/common/inc/nv_uvm_types.h (+15/-1): UvmGpuChannelInfo 增加 pWorkSubmissionToken 活性指针契约 (与 token 重读机制配套)。
  • uvm_turing_host.c / uvm_ampere_host.c: 旧架构 HAL 小幅适配，保持五代架构 (Turing→Rubin) 一致性。
  • 数据中心版 Fixed Issues 同步落地: kvzalloc 拒绝 >2GB 分配的问题改为走 vmalloc 路径 (缓解上周报告的 order-3 高阶分配碎片化/OOM 类问题域)。

趋势展望

短期: R620 节奏与 NVL6 落地 | 中期: NVL576 与开源驱动的数据中心化

短期趋势 (1-3 个月)

  • R620 分支进入高频维护期: 620.70.06 为首发 (Nov 5), 按 R615 节奏 (615.71.09→615.78.08 约 1 个月) 预计 11 月底-12 月初出现 620 分支首个功能更新; PR #1532 已在为新分支预置 VA 修复。
  • NVL6/Rubin 支持从枚举走向功能: NVLINK_DEVICE_VERSION_60 与强制发现逻辑已就位, 后续版本预计补齐 NVLE 加密运行时控制与 timeToLinkUpMs 诊断接口的完整链路。
  • Xid 79 族问题进入官方视野: GB202/203/207 + RTX PRO 6000 案例累积, 若 NVIDIA 在下一版 620.xx 修复, 将是 Blackwell PCIe 稳定性的分水岭。
  • 社区 PR 移植化: NVIDIA 合并节奏慢, 外部贡献者转向"fix + port to new release"双 PR 模式 (#1483→#1532), 预计成为常态。

中期趋势 (3-12 个月)

  • 开源驱动的"数据中心化": 620 引入 fabric manager 校验、SOE 加固、CC/TDISP 矩阵 — 开源模块正从桌面驱动向 NVSwitch 机架栈 (配合 Fabric Manager) 演进。
  • NVL576 / Rubin Ultra (2027H2): NVLink 7 + CPO 交换托盘, Kyber NVL144 机架报道推迟至 2028; 开源侧 gr100/gr102 swref 已在 620 更新, Rubin MMU 支持在 uvm_rubin_fault_buffer.c 持续演进。
  • UVM 故障处理精细化: prefetch 非致命化 + ATS PTE 修复掩码表明 UVM 在向 SMMU/Grace 类一致性平台深度适配; HMM 重构为后续大带宽 C2C 内存池铺路。
  • 专有内核模块走向终局: 数据中心版 release notes 重申专有 flavor 包安装已废弃 (自 615 起不再提供), 开源内核模块成为唯一包管理路径。

核心洞察

1. R620 是"代际接口预埋"版本: 300 文件变更中, NVL6 枚举、NVLE 加密状态、MC 团队协议 v2、GB10C、carveout 内存全是面向 Vera Rubin 世代的基础设施 — 用户可感知的只有 Wayland 同步性能与游戏修复, 但代码面在为 2027 年的机架级栈做准备。

2. UVM 故障处理的"容错哲学"转变: prefetch 故障从"致命"降级为"记录" (五种安全类例外), 本质是承认 GPU 预取与真实访问语义不同 — 这是随机应用崩溃类 issue 的一次系统性修复, 值得所有做 GMMU/缺页管理的团队参考。

3. 开源仓库的"快照式"同步限制了社区贡献: main 一次 release 一个巨型 commit, PR 合并周期以月计; 本周 6 个高质量外部 PR (含完整测试脚本的 #1423) 全部悬置。若 NVIDIA 不改变协作模式, 社区价值将集中在 issue 诊断与移植 PR。

4. 规格口径切换是新的沟通风险: NVLink 6 带宽从 3.6→3 TB/s 的"量产口径"下调伴随 30x 每瓦性能宣传, 意味着后续对开源驱动 NVL6 路径的性能预期应以数据手册 (而非 GTC 幻灯片) 为准。
