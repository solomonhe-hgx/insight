一句话读懂这篇专利

在传统内存模型里，一个虚拟地址（VA）只能对应一个物理地址（PA），这是保证一致性的基础。这篇专利做的事情是：专门划出一类「多播 VA」，让它同时是多个 PA 的别名；当一条访存指令带着这个 VA 进入内存管理单元时，硬件把它翻译成多个目标，交给交换机（switch）向多个设备扇出。于是 all-reduce 这类集合操作不再需要「每个参与者一次请求」，请求数量与参与设备数解耦。

但专利真正精妙的部分在标题的后半句

只做多播是不够的。多播路径要穿出芯片、经过交换机；而同一个设备访问自己的本地内存有一条更短的内部路径。两条路径延迟不同，在弱序（weak ordering）内存系统下就会出现「后发的单播先完成、先发的多播后完成」的诡异结果。专利因此引入反射内存（reflective memory）：把请求刻意送出到交换机再「反射」回发起设备本身，让所有设备被同等对待；并配合访问权限（生产者/消费者）、访问路径、转发规则、软件无竞争提示四类约束，使多播的结果与不用多播时完全一致。

最终目标是一句非常有分量的话：用不用多播，对编程模型是不透明的（opaque）——为只支持单播的内存系统写的代码，可以直接被硬件用多播加速执行。

问题的起点：一个 VA 只能指向一个 PA

专利的背景部分（Background）先陈述了现状约束，再给出后果。这两段是整篇专利的动机基石。

约束：一致性要求「一个 VA → 一个 PA」

在协同处理环境中，多个处理元件（processing element，例如 GPU 的 SM、CPU 核心、SIMD 单元）通过虚拟地址访问内存。为了维持一致性（coherency），每个虚拟地址都映射到一个特定的物理地址。这条规则是内存模型可推理的前提：任何时刻你都能明确知道「写到 VA 的值落在哪块内存上」。

后果：集合操作的请求数量随参与者线性膨胀

问题出在集合通信（collective）上。以 all-reduce 为例：要把所有处理元件的值聚合起来，需要每个处理元件发一次请求把值收集上来；聚合完成后，还要再对每个处理元件发一次请求把结果广播回去。于是请求总数随参与设备/处理元件的数量增长。

"This overhead may be especially impactful in deep learning, where all-reduce has become a key operation that is performed at a high frequency." —— US12326820B2, Background（专利原文）

这句话把整篇专利的商业动机说得很直白：深度学习让 all-reduce 从「偶尔用一下的集合操作」变成了高频关键路径。数据并行训练每个 step 都要 all-reduce 梯度；张量并行每层都要 all-reduce 激活。请求数量的线性膨胀，直接转化成训练吞吐的损失。

把开销拆开看：为什么「请求数」比「数据量」更疼

集合通信的成本通常被拆成两部分：搬运的字节数（bandwidth 项）与发起的请求数（latency / issue 项）。多播优化的是后者。

注意这里的定语

专利用词是「the number of processed requests may be reduced」，而不是承诺某个具体倍数。它保护的是机制，不是性能数字。这也是这类体系结构专利的典型写法：把加速效果写成可能性，把机制写成必要技术特征。

专利想要的最终状态

说明书在讨论约束时给出了一句可以当作全篇目标函数的话：使用多播处理请求得到的结果，必须与不使用多播处理这些请求的结果一致。因此——

"whether multicasting or unicasting is used may be opaque to the programming model" —— US12326820B2, Detailed Description

以及更进一步的推论：为「只支持单播操作的内存系统」编写的代码，可以使用一个或多个多播操作来执行。这意味着多播不是一个需要应用改写才能吃到的新特性，而是一个可以被硬件/驱动悄悄启用的加速手段。

这个目标直接决定了专利后半部分的结构：既然要「对编程模型不透明」，就必须证明多播不会破坏原有的内存序语义。于是才有了 FIG. 3 的四类约束，以及反射内存这个看起来「反直觉地故意走远路」的设计。

两个地址空间：多播 VA 空间 vs 单播 VA 空间

方案 A：分离的地址空间

把多播 VA 放进独立的多播 VA 空间，与单播 VA 空间分开。这样地址本身就编码了语义——内存管理器一看 VA 落在哪个空间，就知道该做单播转换还是多播转换，不需要新的指令编码。

这个方案的最大好处是：单播语法被完整保留。应用照常写 load / store，是否多播由地址决定。这正是「对编程模型不透明」的实现基础。

对应权利要求 3、14

方案 B：由指令或操作数区分

另一种做法是用不同的指令或操作数来指示多播还是单播。专利明确指出，在这种情况下分离的 VA 空间「可能不再需要（但仍然可以使用）」。

这句括号里的补充是典型的专利撰写技巧：既覆盖「用指令区分」的实现，也不放弃「同时用两种机制」的组合，避免竞争对手用「我两个都用了所以不落入」来规避。

说明书 Detailed Description

现实中的答案：两者都用了

看今天的 NVIDIA 实现会发现，产品同时采用了两个方案：CUDA 侧通过 cuMulticastCreate + cuMemMap 建立专门的多播地址（方案 A 的空间分离），PTX 侧又提供专门的 multimem.* 指令族（方案 B 的指令区分），并且规定用普通 load/store 访问多播地址是未定义行为。详见 ⑧ 产业对照。

API 形态：CreateMulticastAlias

说明书给出了应用侧的接口示意，这也是后来成为权利要求 1「mapping instruction」的原型：

VA 116A, VA 116B = Malloc()                        // 常规分配，得到两个单播 VA
VA 118 = CreateMulticastAlias(VA 116A, VA 116B)    // 把它们别名成一个多播 VA

注意 alias（别名）这个词——它在权利要求 6 里被正式使用：「configuring includes allocating memory for the first PA and the second PA and creating the VA as an alias for the first PA and the second PA」。也就是说，多播 VA 的法律定义就是「多个 PA 的别名」。

此外，说明书提到多播组可以由运行在处理元件上的应用来指派（权利要求 4、15：「one or more applications running on one or more of the plurality of PEs assigned the VA to a multicast group」）。这把「谁有权组建多播组」明确划给了应用层。

关键设计：用「地址的类型」向交换机传递语义

说明书给出了一个非常干净的信号机制：内存管理器转换后交给交换机的东西——

  • 如果是一个中间地址 → 交换机知道这是多播操作
  • 如果是一个物理地址 → 交换机知道这是单播操作

不需要额外的控制位或旁路信号，地址本身的种类就是 opcode。这一点被写进了权利要求 5：「a presence of the one or more intermediate address indicates the address translation is a multicasting memory operation」。

中间地址是什么

说明书把它描述为全局虚拟地址空间的 fabric 线性地址（fabric linear address）。它不是任何设备的物理地址，而是 fabric 层面的统一编址。设备侧的 link TLB 负责把它落到本地 PA。

这条 FLA 技术线索有明确的前案渊源：本专利引用的前案里就包括 NVIDIA 自己的 US20200159669A1「Distributed address translation in a multi-node interconnect fabric」（2018-11-21）。也就是说，多播是建立在既有的分布式地址转换体系上的一层扩展，而不是从零设计。

替代实现：交换机自己做全部转换

专利同时覆盖了另一种分工：交换机直接把 VA 或中间地址翻译成多个 PA，不依赖设备侧 link TLB。这对应权利要求 8（「transmitting is to a switch that uses the one or more intermediate address to propagate the instruction resulting in completion of the address translation to the first PA and the second PA」）与权利要求 9（「the one or more translated addresses include the first PA and the second PA」）。

两项权利要求一起，把「转换在设备侧完成」和「转换在交换机侧完成」两种架构都圈了进来。这是撰写上很值得注意的覆盖策略：无论你把 TLB 放在哪一侧，都难以规避。

多播组的层级结构

说明书指出可以存在多个交换机，分别对应不同的多播组；更进一步，多播组可以是分层的（hierarchical）——一个子组的聚合结果，被当作单个设备的结果来对待。

这句话的工程含义很大：它天然对应两级归约拓扑。节点内先用 NVLink 域的交换机把 8 张卡归约成一个结果，这个结果对上层 fabric 而言就是「一个设备的值」，再参与跨节点归约。今天 NVLink SHARP（NVLS）与分层 all-reduce 的做法，正是这个结构。

「单播指令 + 多播 VA」如何确定目标 PA

专利列举了多种确定方式，覆盖面很宽：

  • 由进程指定（process-specified）
  • 由 MMU 选择
  • 使用默认值
  • 在地址空间构建时编程设定（programmed at space construction）
  • 在指令中直接指明

如果以上都无法确定目标 PA，则触发故障。

「多播指令 + 单播 VA」→ 故障

反方向的不匹配同样被处理：说明书明确「a multicast instruction with a unicast VA may trigger a fault」。这条规则被提升成了权利要求 7 的核心：

"…based at least on determining, using the VA, that the instruction is to be processed as a multicast memory access, evaluating whether there is a mismatch between an instruction type of the instruction and the instruction being processed as a multicast memory access, wherein the performing of the one or more address translations is based at least on the evaluating." —— US12326820B2, Claim 7（原文）

换句话说，类型匹配检查本身成了一项受保护的技术特征——地址转换是否执行，取决于这个检查的结果。

来源：US12326820B2 · FIG. 2 / Claim 7

三条多播指令：210 / 212 / 214

这是本专利在指令集层面最具体、也最容易与真实产品对照的部分。三条指令分别覆盖「读并归约」、「写广播」、「原子归约写」。

210 · Reducing Load（归约加载）

行为：把请求多播到 N 个节点 → 收到 N 份响应 → 聚合成一个值 → 交付给一个或多个节点。

聚合运算可以是：求和、平均、最小值、最大值、BITAND、BITOR、其他按位运算、子集选择、统计值等。

聚合位置：可以在交换机中完成、也可以在设备上完成，或两者结合。

细节：发起方自己的值可以走内部路径取得，再与远端返回的值合并。

对应权利要求 20

212 · Multicast Store（多播存储）

行为：把一个值写到多播组内所有 PA。这是最直观的一条——一次请求，N 份副本。

它是「广播同一个值」这类模式的直接硬件化。在训练场景里对应参数广播、以及归约结果的回送阶段。

也正是这条指令，会与后发的单播 store 产生顺序问题——见 ⑤ 反射内存与一致性。

214 · Reduce Multicast（归约多播）

行为：在每个 PA 处执行原子操作，且不返回响应。

它与 210 的区别在方向：210 是「读回来再归约」，214 是「把归约动作推下去，在每块内存上就地完成」。

「不返回值」是关键特征——它让这条指令可以是纯粹的 fire-and-forget，不占用返回带宽。

208 · Reduce（单播归约）的定义值得单独记一下

"…similar to an atomic operation except that a value is not returned to the requester." —— US12326820B2，关于 208 的描述

这条描述精确定义了「reduce」在本专利语境下的含义：它是不带返回值的原子操作。理解了这一点，214（reduce multicast）就很自然——它就是把 208 扇出到多个 PA。

问题：设备内部有一条更短的路

这是全篇最精彩的技术洞察。多播看起来只是「一变多」，但它引入了一个隐蔽的副作用：同一个设备访问自己的内存，有两条延迟完全不同的路径。

"an internal path in a device 102 may have lower latency and bandwidth than a link leaving the device 102" —— US12326820B2, Detailed Description

因此，一个请求到达本地内存 110A，走内部路径会比「送到交换机 104、再反射回设备 102A」更快。这是纯粹的物理事实：片内路径短，出片链路长。

   │  处理元件 106A                    │
   │      │                            │
   │      ├──── 内部路径 ────► 内存 110A  ← 快（低延迟）
   │      │     (internal path)        │
   │      │                            │
   │      └──── 出片链路 ──┐            │
   └──────────────────────┼───────────┘
                          ▼
                    交换机 104
                          │
              ┌───────────┼───────────┐
              │           │           │
         反射回 102A    → 102B      → 102N   ← 慢（但所有设备被同等对待）
              │

一致性被打破的具体例子（专利原文场景）

后发的单播 store 抢在先发的多播 store 之前完成

"a multicast store may be performed on the VA 118, followed by a unicast store by the processing element 106A to the VA 116A. As the internal path for the VA 116A to the PA 120A is shorter, the unicast store to the VA 116A may be completed before the multicast store to the VA 118 even though the request was made later." —— US12326820B2, Detailed Description（原文）

原因很直接：内存系统允许弱序（weak ordering）。在弱序模型下，硬件本来就不承诺两个无依赖访存的完成顺序。但问题在于——从应用的视角看，VA 118 与 VA 116A 是同一块物理内存 PA 120A 的两个名字。应用以为自己在对同一个位置做两次有序的写，硬件却因为路径长度不同把顺序倒过来了。

这个 bug 的性质：别名（aliasing）带来的隐式竞争

它不是普通的数据竞争。普通竞争发生在两个线程之间，程序员知道要加同步。这里的竞争发生在同一个处理元件的两条连续指令之间，而且两条指令表面上访问的是不同的虚拟地址。任何基于「不同地址无需排序」的直觉都会出错。

这就是为什么这篇专利必须由内存模型专家参与撰写——多播 VA 一旦成为 PA 的别名，就在内存模型里引入了一类新的隐式别名关系，必须补上规则。

解法之一：反射内存（Reflective Memory）

故意走远路，换取「所有设备被同等对待」

"However, for some software protocols it may be desirable to reflect the request back so that all devices 102 are treated the same." —— US12326820B2, Detailed Description（原文）

这是反射内存的定义与动机：明知内部路径更快，也把请求送出到交换机再反射回本设备。代价是延迟，收益是路径对称性——发起方对自己内存的访问，与它对远端内存的访问，走的是同一条逻辑路径、经历同一套排序点。

一旦所有设备被同等对待，交换机就成为统一的序列化点。上面那个「后发单播抢先完成」的问题，也就在结构上被消除了。

反射被写进了延续申请的权利要求

授权本主要保护地址转换；反射行为的正面保护在延续申请 US20250272248A1 中，而且写得非常直白：

  • 独立项 1：一致性 fabric 接收指示 VA 的请求 → 映射到多个 PA → 传播，「based at least on reflecting the memory access request to the first device for processing at the first PA」
  • 项 3 / 12 / 19：「the reflecting bypasses a shorter internal path within the first device」——直接把「绕过更短的内部路径」写成技术特征
  • 项 6 / 15：结果被送出到 fabric 再反射回来
  • 项 7 / 16：第二设备通过内部路径本地取得
  • 项 8：设备对多播 VA 转发到 fabric，对单播 VA 本地处理

来源：US20250272248A1 · Claims

解法之二：FIG. 3 的四类一致性约束

反射解决路径对称，但还不够。FIG. 3 给出四类约束，共同保证「多播的结果 == 不用多播的结果」。这些约束可由内存管理器 108、交换机 104、内存 110、页表、TLB、驱动等任意组合来实施。

① 访问权限：生产者 / 消费者角色

对某个 VA 划分角色：生产者（producer）拥有写权限，消费者（consumer）只有读权限。

效果：结构性地排除写-写竞争；并且保证读取发生时，所有 PA 上保存的是同一个值。这是用权限模型代替运行时同步，成本为零。

延续申请项 4/13/20 已将其权利要求化

② 访问路径：谁走反射、谁走本地

生产者把全部（或符合条件的）请求转发到交换机并被反射回来；消费者通过内部路径本地读取，或以其他方式走比生产者更短的路径。

效果：写走长路径统一排序，读走短路径拿到高性能。非对称路径分配是这里的巧思——不是所有人都反射，只有需要被排序的一方反射。

延续申请项 5/14 对应「消费者路径比生产者更短」

③ 转发规则

只有生产者的请求 / 设备 302A 的请求会经过交换机。其余请求不必进入 fabric。

效果：把反射的延迟代价限定在必须被排序的请求上，避免让所有访问都付出出片开销。这是性能与正确性之间的精确切分。

④ 软件无竞争提示（race-free hint）

软件可以告知硬件「这段访问是无竞争的」，并且这个提示可以被限定到给定的 VA 与一个时间窗口。

效果：在软件能保证无竞争的阶段，硬件可以放开约束、走最快路径。带时间窗口的作用域化提示是很实用的设计——它对应真实训练循环里「计算阶段无竞争、同步点前后才需要严格排序」的模式。

延续申请项 9：race-free indication 带 defined time period，可修改多播行为

四类约束的共同目的

专利明确：施加这些约束是为了让「使用多播处理请求的结果，与不使用多播处理这些请求的结果一致」，并且可以根据协同处理环境的配置与能力使用一个或多个额外或替代的约束。

这个「一个或多个额外或替代」的兜底表述，意味着专利并不把自己锁死在这四类上——任何用来保证多播-单播等价性的约束机制，都可能落入其射程。

来源：US12326820B2 · FIG. 3 说明

把多播用起来的两种姿势

专利提出多播不只用于「替换已经在用的单播」，还可以提前布置，为将来的访问铺路。这两条路线的性能收益模型完全不同。

姿势一：加速当前请求（替换单播）

检测到一组处理元件将要把同一个值存储到多个内存（用多个请求），就把这些请求用一个或多个多播操作来处理。收益直接：处理的请求数量减少。

专利用词是「multicasting may be used to accelerate the processing of one or more requests which may otherwise have been processed using unicasting」——注意这个「otherwise」，它强调的是本来会用单播，所以对应用来说是纯加速。

姿势二：加速未来请求（预先复制）

检测到一组处理元件将要从多个内存加载同一个值，就提前用多播把该值复制到每个内存。之后各设备的 load 就可以从本地副本快速完成，而不是从「多个进程映射到同一 PA」的慢路径上去读。

专利在 FIG. 3 的语境下指出：设备 302B、302C、302N 的 load 分别从本地副本 PA 120B / 120C / 120N 完成。

为什么「预先复制」在有同步屏障时特别值钱

"This may be advantageous in various scenarios, such as where a synchronization barrier is enforced across the devices 302, and the devices 302 wait for the slowest load to complete." —— US12326820B2, Detailed Description（原文）

这句话点出了分布式训练的真实痛点：屏障下的整体耗时由最慢的那次 load 决定。如果 N-1 个设备都要跨链路去同一个 PA 读同一个值，尾延迟会被链路争抢放大；把值预先复制到每张卡本地，所有 load 都变成本地读，最慢的那个也快了。这是从「优化平均延迟」转向「压缩尾延迟」的思路，对 barrier-heavy 的负载收益最大。

怎么知道该多播？四类触发机制

专利说「可以使用各种方法来确定、识别、预测或以其他方式预判上述场景」，并明确这可以由内存管理器 108、交换机 104、内存 110、页表、TLB、驱动等的任意组合完成。具体给了以下几条。

① 应用/进程给出提示（hint）

通过 API 调用或驱动层消息提供提示。例如：应用分配单播内存时，附带一个提示，指明哪些 VA 需要用多播复制（以及复制到哪些设备 102）。

② 驱动集合操作建立多播组

当分配发生在设备 302A 上时，可以执行一次 collective：设备 302A 与其他每个待加入多播组的设备上的驱动通信。结果是设备 302A 为所有副本分配后备内存并创建映射，然后——

"with a single pointer being returned for the VA and passed to one or more of devices 302 similar to a unicast pointer." —— US12326820B2（原文）

「像单播指针一样的单个指针」——这是不透明性在 API 层面的体现：应用拿到的东西看起来和普通指针没区别。

③ 计数器 / 监控 / 模式识别

递增计数器，或使用监控与模式识别技术来触发。例如：基于统计或识别出某种模式（如「若干 VA 组频繁把相同的值存到那些或其他 PA」），把对某个 VA 的 store 复制到多个 PA。

这条被提升成了权利要求 16：「a multicast memory access is selected for the request rather than a unicast memory access based at least on analyzing one or more patterns associated with requests for memory access operations…」已权利要求化

④ 故障驱动的 VA 迁移

更节省内存的做法：分配时设备 302A 只为单份副本分配内存（而非所有副本），同样返回单个指针。当模式被识别出来后，设备的驱动判定该 VA 应当被复制，于是——

"the driver may begin taking faults, handling faults, and/or otherwise transitioning the VA for multicasting." —— US12326820B2（原文）

用缺页故障作为迁移机制，把一个原本单播的 VA 在运行时热转换成多播 VA。这与 UVM 的按需迁移是同一套基础设施。

不透明性（Opacity）：这篇专利真正的野心

把前面所有机制串起来，专利想达到的状态是：

  • 多播 VA 在应用看来就是一个普通指针（单个指针返回，类似单播指针）
  • 单播语法被保留，不必改写访存代码
  • 是否启用多播，可以由驱动/硬件根据提示或模式识别自行决定
  • 加了一致性约束后，多播结果与单播结果等价
  • 因此：「为只支持单播的内存系统编写的代码，可以用多播操作来执行」

这是一条很强的主张：它把多播从「一个需要生态适配的新特性」变成「一个可以被硬件单方面启用的优化」。专利保护的不只是多播机制，还包括让多播变得不可见的那套约束。

现实检查：产品并没有做到完全不透明

需要诚实地指出：今天出货的实现是显式的，不是不透明的。PTX 明确规定「只有 multimem.* 操作对多播地址有效，用其他内存操作访问多播地址是未定义行为」；CUDA 侧需要显式调用 cuMulticastCreate / cuMulticastAddDevice / cuMulticastBindMem / cuMemMap 一整套流程。

也就是说，说明书里描述的「不透明多播」目前更像是为未来实现预留的权利范围，而非已落地的产品形态。这一点对判断专利价值很重要：它的射程明显宽于当前产品，覆盖了「编译器/驱动自动把单播改写成多播」这类尚未普及的实现。

来源：PTX ISA §8.2.3 · CUDA Driver API · Multicast Object Management

独立项 1 原文与逐段释义

1. A computer-implemented method comprising:
receiving, from an application, a mapping instruction that specifies to configure a virtual address (VA) as a multicast VA for a first physical address (PA) and a second PA;
responsive to the mapping instruction, configuring the VA as the multicast VA for the first PA and the second PA;
receiving, from the application, an instruction for a memory access operation, the instruction indicating the VA;
based at least on identifying the VA in the instruction and the configuring of the VA as the multicast VA, performing one or more address translations of an address translation that maps the VA to at least the first PA corresponding to a first processing element (PE) of a plurality of PEs and the second PA corresponding to a second PE of the plurality of PEs; and
transmitting one or more translated addresses resulting from the one or more address translations of the address translation, the transmitting causing memory accesses on one or more memories using the first PA and the second PA responsive to the instruction. —— US12326820B2, Claim 1（原文）
要件释义与要点
① 从应用接收映射指令必须有一个来自应用的、明确指定「把某 VA 配置为多播 VA」的指令。这是整项权利要求最强的限定：纯硬件自动决定多播、无应用参与，不落入本项。
② 响应该指令进行配置配置动作与映射指令之间必须有因果关系（responsive to）。
③ 从应用接收访存指令，指令指示该 VA访存指令同样来自应用，且携带这个多播 VA。
④ 基于「在指令中识别到该 VA」+「该 VA 已被配置为多播」执行地址转换双重触发条件。转换目标：至少第一 PA（对应第一 PE）与第二 PA（对应第二 PE）。注意用词是「one or more address translations of an address translation」——刻意允许一次逻辑转换由多个物理转换步骤组成（覆盖 MMU + link TLB 的分段实现）。
⑤ 传输转换出的地址，致使访存传输对象是「一个或多个转换后的地址」。结合项 8（中间地址）与项 9（就是 PA），这个上位表述同时覆盖了两种架构。

关键证据：授权前 vs 授权后的范围收窄

这是本页最有分析价值的一节。把 2023 年公开的申请版权利要求 1 与最终授权版并排看，收窄一目了然。

授权前（US20230229599A1）Claim 1

结构极其简洁，只有三步：

  • receiving first data corresponding to a request（接收请求对应的第一数据）
  • performing an address translation of the VA … to at least a first PA … and a second PA（对 VA 执行地址转换）
  • transmitting second data（传输第二数据）

没有「application」，没有「mapping instruction」，没有「configuring」。

这个版本等于主张：任何把一个 VA 转换成多个 PA 并致使多处访存的机制。范围极宽。

来源：US20230229599A1 · Claim 1

授权后（US12326820B2）Claim 1

前面被插入了两个全新步骤，并给转换加上了双重触发条件：

  • + receiving, from an application, a mapping instruction that specifies to configure a VA as a multicast VA
  • + responsive to the mapping instruction, configuring the VA as the multicast VA
  • + 访存指令也必须 from the application
  • + 转换须 based at least on identifying the VA in the instruction and the configuring

范围从「任何 VA→多 PA 转换」收窄为「应用显式建立的多播映射 + 基于该映射的转换」。

CUDA Multicast Object API：CreateMulticastAlias 的真身

函数作用与约束
cuMulticastCreate(mcHandle, prop)创建多播对象句柄。多播对象允许某些内存操作被广播到一组（team）设备。
cuMulticastAddDevice(mcHandle, dev)把设备加入 team。文档明确：这种关联在多播对象的整个生命周期内是永久的。
cuMulticastBindMem / cuMulticastBindMem_v2把由 cuMemCreate 或 cudaMallocAsync 得到的物理内存绑定到多播对象。所有设备加入 team 前，绑定会阻塞。
cuMulticastBindAddr / cuMulticastBindAddr_v2按地址绑定的变体。
cuMulticastUnbind解除绑定。
cuMulticastGetGranularity查询粒度。CU_MULTICAST_GRANULARITY_MINIMUM 为对齐必需；CU_MULTICAST_GRANULARITY_RECOMMENDED 为性能推荐对齐。

能力查询与错误码

  • 支持性通过 CU_DEVICE_ATTRIBUTE_MULTICAST_SUPPORTED 查询
  • 绑定后通过 cuMemMap / cuMemSetAccess 建立映射；cuMemMap 同样会阻塞直到 team 齐备
  • 可通过 cuMemExportToShareableHandle 跨进程共享
  • 错误码 CUDA_ERROR_SYSTEM_NOT_READY（需确认「all required driver daemons are running properly」）、CUDA_ERROR_ILLEGAL_STATE

与专利的对应关系

专利里 Malloc() + CreateMulticastAlias() 这两步，在产品中被拆成了更细的四步：创建对象 → 加设备成组 → 绑定物理内存 → 映射到地址空间。

而权利要求 6 的「allocating memory … and creating the VA as an alias for the first PA and the second PA」，正好覆盖了「cuMemCreate 分配 + cuMulticastBindMem/cuMemMap 建立别名」这个组合。

另外，说明书提到的「驱动集合操作、跨设备通信建组」也与 cuMulticastAddDevice 的阻塞语义（等所有设备加入才能绑定/映射）严丝合缝。

需要注意的边界：CUDA 官方文档页面没有写明该 API 组引入的具体 CUDA 版本，也没有明文要求必须有 NVLink / NVSwitch。因此本页不对「哪个 CUDA 版本开始支持」「是否强制 NVSwitch」作断言——这些需要另行查证。

影响分析

对系统软件栈

多播把「集合通信」从软件编排的多次点对点下沉为单条访存指令 + fabric 扇出。这改变了通信库的分层：NCCL 之类的库不再只是「组织消息」，而是「选择合适的硬件原语」。当 multimem 可用时，all-reduce / broadcast / all-gather 的实现路径与不可用时完全不同。

对内存模型研究

这篇专利提出了一个此前少见的问题：当 VA 可以是多个 PA 的别名时，弱序内存模型需要补什么规则。它给出的答案（权限角色 + 路径非对称 + 转发限定 + 作用域化无竞争提示）本质上是用架构约束换取语义等价，而不是引入新的同步指令。这个思路对任何做多播/近内存归约的团队都有参考价值。

对竞争者的专利风险

授权项要求应用下发映射指令，这给「驱动自动多播」留了缝隙；但说明书对替代方案的覆盖极广（提示 / 计数器 / 模式识别 / 故障迁移），且项 16 已把模式识别写入权利要求。加上反射行为的延续申请仍在审查，任何计划做「交换机内归约 + 一地址多目标」的厂商，都需要把这两件一起做 FTO 分析。

对硬件架构的启示

专利明确交换机可以在设备内部也可以在外部、可以有多个对应不同多播组、且组可以分层。这实际上给出了一个可扩展的设计模板：把归约能力放进交换层，并允许递归组合。对做 scale-up 域互连的团队，这是一份很直接的架构参考——同时也是一份需要绕开的专利地图。
