Bug Issue #1333 | 2026-09-02

H100 NVL: UVM GPU Unregister 警告导致 NVML 命令挂起NEW

问题描述: 在通过 NVLink 连接的双 H100 NVL 系统上,uvm_va_space_destroy() / nvUvmInterfaceUnregisterGpu 触发 WARNING。Alloc lock 被死线程滞留, 导致所有 NVML 命令进入 D 状态挂起。驱动版本 595.71.05, Ubuntu 24.04.4。
技术分析:
  • 根因: UVM 注销路径中的时序依赖竞态条件
  • 影响: NVLink 双 GPU 系统中 NVML 命令完全挂起
  • 关键函数: uvm_va_space_destroy(), nvUvmInterfaceUnregisterGpu
  • 环境: H100 NVL (NVLink 互联), Driver 595.71.05, Ubuntu 24.04.4
来源: GitHub Issue #1333
Bug Issue #1148 | 更新至 2026-08-24

NVLink 单边关机累积导致 GMMU VA 分配器泄漏

问题描述: S3 挂起间歇性失败。virtualBar2[GPU_GFID_PF].pCpuMapping 唤醒后变为 NULL, 导致内存遍历崩溃。理论认为 NVLink 单边关机路径在 GMMU VA 分配器中造成内存泄漏。值得注意的是, 8月24日有用户在 无 NVLink 硬件的 Blackwell 移动设备 上复现了相同崩溃, 表明根因可能是更广泛的 BAR2/GMMU 恢复路径缺陷。
关键路径:
  • virtualBar2, pCpuMapping == NULL
  • NVLink unilateral-shutdown → GMMU VA allocator leak
  • 跨架构影响: Turing → Blackwell (不限于 NVLink 硬件)
来源: GitHub Issue #1148
本周小结

本周 NVLink 模块在 open-gpu-kernel-modules 仓库中无新的代码提交或 PR。主要动态来自 NVIDIA 官方的 NVLink Fusion 公告以及社区报告的 NVLink 相关 Bug (#1333 H100 NVL UVM 注销问题)。Issue #1148 的分析表明部分 NVLink 相关崩溃可能实际源于更底层的 BAR2/GMMU 恢复路径缺陷。

NVLink-C2C 成为 NVLink Fusion 架构核心互联NEW

核心要点: NVLink-C2C 在 NVLink Fusion 架构中承担 CPU-GPU 统一内存互联角色, 提供 1.8 TB/s 内存吞吐。定制 XPU 通过 NVLink-C2C 连接到 CPU, 集成到 MGX 机架级架构。NVHBM 技术使 HBM 堆栈内存带宽提升 30%, PHY 面积减少 67%。
平台路线图:
  • Vera Rubin 平台: 第六代 NVLink (3.6 TB/s/GPU), NVSwitch 托盘 14.4 TFLOPS FP8
  • Grace Hopper: NVLink-C2C 实现 CPU-GPU 共享内存一致性
  • Grace Blackwell: NVLink-C2C 统一内存架构延续
  • 开源驱动中未发现独立 "NVLink-C2C" 目录, 一致性缓存功能可能使用其他命名
来源: NVLink Fusion Blog | Vera Rubin Platform | NVLink-C2C 官方页面

Vera Rubin 平台: 6th-gen NVLink 与 NVSwitch 托盘详解

核心规格: 6th-gen NVLink 每 GPU 提供 3.6 TB/s 双向带宽, 单机箱连接 72 GPU。NVSwitch 托盘集成网络处理, 提供 14.4 TFLOPS FP8 计算。NVLink-C2C 提供 1.8 TB/s 统一内存吞吐用于 CPU-GPU die-to-die 连接。

本周 NVLink-C2C 模块无开源驱动层面的代码变更。主要动态来自 NVIDIA 官方的 NVLink Fusion 公告 (8月26日), NVLink-C2C 作为定制 XPU 与 CPU 之间的核心互联被重点推广。在开源驱动源码中尚未发现独立的 NVLink-C2C 代码目录, 一致性缓存功能可能以其他命名方式存在。

Bug MMU + UVM Issue #1342 | 2026-09-06

RTX 5090: mmuWalkUnmap 失败导致 UVM 致命错误 0x60NEW

严重问题: 用户在 RTX 5090 上运行 PyTorch LLM 推理时遭遇系统崩溃。内核日志显示 mmuWalkUnmap: Failed to unmap VA Range (Status 0x00000040), 触发 TLB 刷新失败, 随后 UVM 遭遇全局致命错误 0x60。GPU 从总线丢失, nvidia-smi 报告 "Unable to determine the device handle", 需重启系统。驱动版本 610.57.04。
故障链分析:
  • 1. mmuWalkUnmap 无法解除 VA 范围映射 (Status 0x00000040)
  • 2. TLB 刷新失败 → GPU 从总线丢失
  • 3. UVM 全局致命错误 0x60 → 系统不可恢复
  • 关键文件路径: kernel-open/nvidia-uvm/uvm_mmu.c
  • 影响: Blackwell (RTX 5090) + Driver 610.57.04 + CUDA/PyTorch 工作负载
来源: GitHub Issue #1342
Bug GMMU + TLB Issue #1329 | 更新至 2026-09-04

GMMU TLB 刷新导致挂起死锁 — 已确认影响 BlackwellNEW

严重问题: 挂起操作中 kgmmuInvalidateTlb_GM107 在 BAR2 拆除后无限自旋, 而 MMU 仍处于活跃状态。导致 framebuffer 保存损坏, 恢复时黑屏。NV_ERR_INVALID_STATE 断言失败。最初报告于 Turing GPU, 9月4日有用户确认在 Blackwell GPU 上同样复现。
技术分析:
  • 根因: BAR2 拆除期间 GMMU 移除 CPU 映射, 用户空间进程在 mmap 中被困于无限循环
  • TLB 刷新自旋阻塞睡眠服务, 导致 framebuffer 损坏
  • 关键函数: kgmmuInvalidateTlb_GM107, pCpuMapping
  • 跨架构影响: Turing → Blackwell
来源: GitHub Issue #1329

H100 NVL: UVM GPU 注销竞态条件导致系统挂起NEW

Bug MMU + VA Space Issue #1140 | 更新至 2026-09-08

RTX 4090 (AD102): dmaAllocMapping VA 空间耗尽导致看门狗锁死

系统性问题: 桌面使用约一周后, 内核模块停止接受内存映射请求, 导致 GPU 完全冻结。内核日志重复报告 "Failed to assign virtual memory regions"。多位用户在 RTX 4060、RTX 3090、RTX 3060 Ti 上确认, dmesg 中出现明确的 "MMU Fault" 错误。VA 空间损坏持续直到硬重启。
关键信息:
  • 关键函数: dmaAllocMapping_GM107
  • 影响架构: Ada (AD102), confirmed on Ampere 也受影响
  • 根因: VA 空间渐进耗尽, 无有效回收机制
来源: GitHub Issue #1140
Bug MMU + BAR1 Issue #1187 | 更新至 2026-09-05

BAR1 VA 空间耗尽导致全系统硬锁 (Turing, 256 MiB BAR1)

问题描述: 加载高需求 Web 图形耗尽 BAR1 固定孔径。驱动未返回分配错误, 而是发起全系统冻结。用户确认 Turing 显卡出现 "MMU Fault" 错误。禁用 GSP 固件可防止完全锁死。
来源: GitHub Issue #1187
PR #1340 UVM 2026-09-05 | Open

UVM: 挂起时保护 bottom-half 队列刷新NEW

修复方案: 系统挂起时如果进程持有设备打开状态, 会导致内核崩溃。根因: bottom-half 队列仅在支持可重放故障时创建, 但 uvm_suspend() 无条件尝试刷新, 导致空指针解引用。修复方案在刷新前添加条件守卫。已在 Maxwell GPU 上验证。
代码分析:
  • 关键函数: uvm_suspend()
  • 修复: 在 bottom-half queue flush 前添加 replayable fault support 检查
  • 关联: PR #1339 为同一修复的早期关闭版本
  • 作者: tarik0
来源: GitHub PR #1340
PR #1286 Memory 更新至 2026-09-06 | Open

修复 DIFR 预取 GPFIFO 耗尽导致的系统挂死

修复方案: 两个补丁修复确定性系统冻结: (1) 限制等待空闲缓冲区条目的循环次数; (2) 硬件故障后重置通道。多位用户验证补丁消除了冻结现象。
关键文件:
  • nvidia-push.c, nvkms-difr.c, nvkms-evo.c
  • DIFR 预取 → GPFIFO 环形缓冲区耗尽 → 系统冻结
  • 作者: runiter
来源: GitHub PR #1286
安全漏洞 UVM Quarkslab 研究

nvidia-uvm.ko 本地提权漏洞: UVM_MAP_EXTERNAL_ALLOCATION ioctl 利用

安全公告: Quarkslab 披露 nvidia-uvm.ko 中的本地提权漏洞。攻击者通过 UVM_MAP_EXTERNAL_ALLOCATION ioctl 利用进程 fork 操纵虚拟内存分配器, 实现任意内核写入。漏洞源于红黑树中的悬空指针 (栈分配线程状态释放后未清理)。
来源: Quarkslab Blog | Hacker News 讨论

趋势展望

短期趋势 (1-4 周)

  • MMU/UVM 稳定性将成为首要关注点: 本周 4 个严重 MMU/UVM Bug 集中爆发, 涵盖 mmuWalkUnmap 失败、GMMU TLB 死锁、VA 空间耗尽等问题, 预计将推动紧急修复补丁。
  • Blackwell 驱动成熟度提升: RTX 5090 上的 MMU 致命错误 (#1342) 和 GMMU 死锁 (#1329 确认) 表明 Blackwell 架构的开源驱动仍需迭代。预计后续版本将重点修复。
  • 610 驱动分支反馈收集: 610 分支讨论帖刚开放, 预计未来几周将积累更多兼容性反馈。

中期趋势 (1-6 月)

  • NVLink-C2C 开源驱动支持预期: 随着 Vera Rubin 平台和 NVLink Fusion 架构推进, 预计开源驱动中将增加 NVLink-C2C 相关代码支持 (目前源码中尚未发现独立目录)。
  • 开源驱动生态持续扩展: Arch Linux 默认切换、Haiku OS 移植、GPU Operator 默认安装 open modules — 开源驱动生态正在快速扩展。
  • 安全问题推动 UVM 代码审计: Quarkslab 的提权漏洞披露可能推动更广泛的 UVM 代码安全审计和 Rust 重写讨论。

核心洞察

1. MMU/UVM 是本周绝对焦点: 6 个相关 Issue/PR 集中报告了内存管理子系统的稳定性问题。从 mmuWalkUnmap 失败到 VA 空间耗尽, 从 GMMU TLB 死锁到 UVM 注销竞态, 问题覆盖了 MMU 子系统的多个关键路径。这些问题跨越 Turing、Ada、Ampere 到 Blackwell 多个架构, 表明存在系统性设计挑战。
2. GMMU/TLB Bug 跨架构传播: Issue #1329 (GMMU TLB 死锁) 从 Turing 扩展到 Blackwell 的确认, Issue #1148 (BAR2/GMMU 恢复) 在无 NVLink 硬件上复现 — 这些证据表明底层 MMU 硬件交互存在跨代共性缺陷, 不是简单的架构特定问题。
3. NVLink 生态持续扩展但开源驱动跟进滞后: NVLink Fusion 和 NVLink-C2C 在硬件层面快速推进 (第六代 NVLink, 3.6 TB/s), 但开源驱动中尚未发现 NVLink-C2C 的独立代码实现。NVLink 相关的开源问题 (#1333, #1148) 更多集中在 UVM/GMMU 交互层面, 而非 NVLink 协议本身。
4. 开源驱动生态里程碑: Arch Linux 默认切换、Haiku OS 移植、GPU Operator 默认安装 — 开源驱动正在从 "可选" 变为 "默认"。这将对代码质量和稳定性提出更高要求。
